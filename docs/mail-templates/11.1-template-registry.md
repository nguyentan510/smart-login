# 11.1 — The template registry

Spec: [`../mail-templates.md`](../mail-templates.md) (D1, D2, D3). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** One array declares every message the plugin can send, and a password
reset stops being worded as a login code.

## Files

- `includes/Mail/class-mail-registry.php` — new
- `includes/OTP/Transports/class-mail-transport.php`
- `includes/OTP/class-placeholders.php`
- `includes/class-field-registry.php`
- `tests/mail/run-template-tests.php`

## Steps

1. **The registry.** One row per message:

   ```php
   'otp.recover' => array(
       'group'   => 'otp',
       'label'   => __( 'Đặt lại mật khẩu', 'omniwp' ),
       'when'    => __( 'Khi người dùng yêu cầu đặt lại mật khẩu', 'omniwp' ),
       'intent'  => OtpService::INTENT_RECOVER,
       'tokens'  => self::OTP_TOKENS,
       'subject' => 'Mã đặt lại mật khẩu {{code}} - {{site_name}}',
       'body'    => "…",
   ),
   ```

   `tokens` names the set this message may use. Sharing one global list is the
   defect D3 describes, and the constant exists so the four OTP rows share
   theirs without a fifth message inheriting it by accident.

2. **Generated fields.** `FieldRegistry::delivery_fields()` merges
   `MailRegistry::fields()`, which emits a `subject` and `body` pair per row.
   Default is **empty string**, not the row's default text — empty means "use
   the fallback", and pre-filling every box with the default would make the
   fallback dead on arrival and turn one wording into five copies to maintain.

3. **Resolution, in one place.**

   ```php
   MailRegistry::resolve( string $message_id ): array{subject:string,body:string}
   ```

   Override if non-empty, else the shared `email.subject` / `email.body`, else
   the row's own default. Three levels, and the middle one is what keeps today's
   behaviour for every install that never touches this.

4. **`MailTransport` asks by message id.** It currently reads `email.subject`
   and `email.body` directly. It takes the id from `$ctx['intent']` mapped
   through the registry, and keeps doing exactly one thing with the answer.

5. **Per-message token help.** `Placeholders::available_tokens()` gains an
   optional message id and returns only that row's set. The existing callless
   form keeps returning everything, because the SMS section legitimately shows
   the full list.

## Acceptance

Rules 2 and 3 green.

A `recover` OTP renders the reset wording; a `login` OTP renders the login
wording; an intent with no override renders the shared pair byte-for-byte
identically to before this sub-phase — asserted directly, not inferred.

Setting only `email.templates.recover.subject` leaves the other three intents on
the shared text. Clearing it puts `recover` back.

`php tests/run-all.php` — required suites at their previous counts. The
regression suite's per-tab round trip will grow, because generated fields are
fields; that is a count change with a cause, and the cause goes in the outcome.

## Not in scope

The admin alerts (11.3) and the HTML layout (11.2). This sub-phase changes what
text is chosen, never how it is wrapped or who else can send.

### The brief's fallback order could not work, and would have shipped silently

The brief specified *override, else shared pair, else the message default*. That
ordering is unusable, and not marginally:

`email.subject` ships with a **non-empty** default,
`Mã xác thực {{code}} - {{site_name}}`. So `Settings::get()` returns it on every
install, the shared level always matched, and no per-message default was ever
reachable. Every intent would have resolved to the same wording it already had —
the entire point of the sub-phase, absent, with all its tests passing, because
rule 2 only asks that a message resolves to *something*.

Found by asserting the behaviour rather than the plumbing: `resolve('login')`
and `resolve('recover')` had to differ, and they did not.

The middle level now compares the stored shared value against that field's
**registry default**, so it means "the site has its own wording, use it
everywhere" rather than "this field is non-empty". Three levels, all reachable,
each asserted:

- nothing customised → each message uses its own default
- shared pair edited → that wording governs every message
- one override set → it beats both, and its siblings are unaffected
- override cleared → inheritance returns rather than the mail going out empty

### The tester would have broken quietly

The Gửi thử button sends `intent => 'test'`, which has no registry row.
`resolve_intent()` falls back to the shared pair for exactly that reason, and it
is asserted — a tester that cannot render a message is a tester nobody can check
a gateway with, and it would have failed only when someone reached for it during
an outage.

### `delivery-mail` was created here, not in 11.4

The brief put the tab in 11.4. Creating it now means the eight generated fields
land in their final home immediately instead of living on `delivery-email` and
being moved later — and a move is the operation this project has been bitten by
five times. 11.4 keeps the grouping, the per-message `when` text, the scoped
token lists and the inherited-value placeholders; it just no longer has to
relocate anything.
