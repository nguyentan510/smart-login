# 11.2 — The shared HTML layout

Spec: [`../mail-templates.md`](../mail-templates.md) (D5). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Give an HTML message somewhere to be. Today the body *is* the whole
document, so "designing the template" means writing a full HTML file into a
textarea.

## Files

- `includes/Mail/class-mail-layout.php` — new
- `templates/mail/layout.php` — new, overridable by a theme
- `includes/OTP/Transports/class-mail-transport.php`
- `includes/class-field-registry.php`
- `tests/mail/run-template-tests.php`

## Steps

1. **Three settings, and no more.** Logo URL, accent colour, footer text — all
   optional, all on `delivery-email`. A mail template editor is a product; this
   is the smallest thing that makes an HTML message look deliberate.

2. **Table-based, inline-styled markup.** Not a preference: Outlook ignores
   `<style>` blocks and most clients strip `<head>`. The layout is ugly HTML on
   purpose and the file says so, so nobody tidies it into something that renders
   as a wall of unstyled text in the one client that matters to a Vietnamese
   shop's customers.

3. **Wrap once.** `MailLayout::wrap()` is applied by `MailTransport` after the
   body renders, and only when `email.is_html` is on. Rule 5 asserts a body that
   already contains the layout marker does not produce a second one — an
   administrator pasting a complete document is the obvious way this breaks, and
   the answer is to detect and pass through rather than to nest.

4. **Theme override.** `templates/mail/layout.php` goes through the existing
   `TemplateLoader`, so a site can replace it wholesale without touching the
   plugin. That is the escape hatch that keeps the three settings defensible.

5. **Plain text is unaffected.** With `is_html` off nothing wraps, and
   `MailTransport` keeps stripping tags. Rule 6 pins that, because the layout is
   exactly the change that could start leaking markup into text mail.

## Acceptance

Rules 5 and 6 green.

With `is_html` on, a rendered OTP mail contains the layout once, the accent
colour where configured, and the body inside it. With `is_html` off, the same
message is byte-identical to what it was before this sub-phase.

A body that already contains the layout marker passes through unwrapped.

Rendering goes through `tests/integration/` as well: `wp_mail()`, the
`Content-Type` header and the theme override path all need a real WordPress, and
this project has been bitten by template code that no stub executes.

## Not in scope

Per-message layouts. One layout, applied to every HTML message; a message that
needs its own is a theme override.

Dark-mode and client-specific hacks beyond the table structure.

### The brief missed the thing that made HTML useless

It specified wrapping and said nothing about the body. But the shipped defaults
are written as plain text — their blank lines are the *only* structure they have
— so wrapping them unchanged renders the entire message as one run-on paragraph
inside a nice frame. That is what "turn HTML on" already did, and it is the
reason leaving it off was reasonable.

`MailLayout::paragraphs()` splits on blank lines and `nl2br()`s within a block,
and leaves a body that already contains block markup alone. Asserted by counting
`<p` in the output, because "it is wrapped" was never the property that mattered.

### The accent colour is validated, not escaped

It is interpolated into a `style` attribute, where `esc_attr()` is not enough:
`red;background:url(http://…)` survives escaping intact and becomes a second CSS
declaration. It is matched against a hex pattern and falls back to the default
otherwise, asserted with that exact string.

### Two guards against a layout that silently swallows the message

A theme override returning an empty string sends the unwrapped body rather than
an empty mail — worse-looking and correct beats well-framed and blank. And a
body that already contains `<html` passes through unwrapped even without the
marker, since documents written before the marker existed are the ordinary case.

### The template suite caught the new file, correctly

```text
FAIL  every template has a fixture or a written-down exclusion
Templates: 76 passed, 1 failed
```

`templates/mail/layout.php` had neither. It is excluded now with the reason
written down: it *is* rendered — by the mail suite, through `MailTransport` —
and a fixture in the template suite would render it into a browser context it
never sees. The rule wanted a decision, and got one rather than an exemption.

### The mail suite needed the template stubs

`TemplateLoader::locate()` calls `locate_template()`, which only
`tests/template-stubs.php` provides. Loading it was the fix; the alternative —
bypassing `TemplateLoader` — would have cost the theme override that makes three
settings defensible instead of the ten somebody will eventually ask for.

### The admin alerts stay plain text, deliberately

`Mailer` does not wrap. An operational alert is diagnostic, goes to one address,
and is often read on a phone during an incident; a branded frame around
*"kênh sms đang lỗi"* adds nothing and one more thing to render wrong. Recorded
here so the asymmetry reads as a decision.
