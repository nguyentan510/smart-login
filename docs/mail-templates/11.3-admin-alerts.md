# 11.3 — The admin alerts join the registry

Spec: [`../mail-templates.md`](../mail-templates.md) (D4). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Stop the plugin sending two messages nobody can reword, redirect or
switch off.

## The two

```php
wp_mail( $to, sprintf( __( '[%s] Đã tạm dừng gửi mã xác thực', … ) ), … );
```
`includes/Security/class-rate-limiter.php:267` — the site budget halted.

```php
wp_mail( $to, sprintf( __( '[%s] Kênh gửi mã đang lỗi liên tục', … ) ), … );
```
`includes/OTP/Transports/class-circuit-breaker.php:163` — a transport opened.

Both go to `get_option( 'admin_email' )`, both compose their own subject and
body inline, and neither is reachable from any screen. They are also the two
messages most likely to arrive at three in the morning during an incident.

## Files

- `includes/Mail/class-mail-registry.php`

## Steps

1. **A sender for messages that are not OTPs.** `MailTransport` exists to
   deliver a code and is answerable to the router and the breaker; an operational
   alert is neither. `Mailer::send( string $message_id, string $to, array $ctx )`
   resolves through the registry, applies the layout, and calls `wp_mail()`.

   That makes it the second and last caller, which is what rule 1 asserts.

2. **Two registry rows**, group `admin`, with the current wording as their
   defaults and their own token sets — `{{ceiling}}`, `{{window}}`,
   `{{halt_minutes}}` for the budget; `{{transport}}`, `{{cooldown}}` for the
   breaker. Rule 3 checks those defaults against those sets, which is how a typo
   in a default is caught before an incident is the thing that reveals it.

3. **An off switch per message**, default on. The reason to allow off is 10.4:
   both events already reach an automation endpoint through the bus, so a site
   with that configured is receiving each alert twice and can currently silence
   neither.

4. **Recipient stays `admin_email`.** Not configurable here. A recipient field
   invites a distribution list, which invites per-message recipients, which is
   the feature D6 declines for the login alert and the same argument applies.

5. **The breaker keeps its once-per-transition discipline.** `announce()` is
   called at the moment the count crosses so a burst produces one mail rather
   than one each; moving the composition out must not move that.

## Acceptance

Rule 1 green — no `wp_mail()` in `includes/` outside `MailTransport` and
`Mailer`.

Both alerts still fire, with their current wording byte-identical while nobody
has overridden them. Turning one off stops that mail and leaves the audit record
and the bus event untouched — the alert is a notification, not the record.

A burst of concurrent breaker failures still produces exactly one mail.

## Not in scope

New alerts. This sub-phase moves two messages and adds none.
