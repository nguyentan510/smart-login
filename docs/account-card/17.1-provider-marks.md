# 17.1 — The provider's own mark

Spec: [`../account-card.md`](../account-card.md), decision 8. Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Turn rule 1 green. The cheapest sub-phase in the phase and the only one
that adds no new asset: `icon_svg()` has existed since Phase 12 and the account
card has never called it.

## Files

- `includes/Frontend/class-provider-mark.php` — new
- `templates/partials/linked-identities.php`
- `templates/partials/account/providers.php`
- `assets/css/omniwp.css` — one rule for the mark in a row

## Steps

1. `ProviderMark::svg( string $channel ): string` — resolve through
   `ProviderRegistry::get()`, return `''` for a channel no provider claims.
   `get()` and not `available()`: an account can hold a Google identity on a site
   where Google has since been switched off, and that row still has to draw.
2. The linked row renders the mark before the label.
3. The invitation button renders the mark before its text, the way
   `form-auth.php:130-140` already does on the sign-in screen.
4. One CSS rule sizing the mark inside a row. No new colour: the SVGs carry the
   brand's own.

## Acceptance

- Rule 1 green
- A channel with no registered provider renders no mark and no error — asserted,
  because `linked()` returns `email` and `phone` rows too and the helper will be
  handed them
- Every other suite at its previous count

## Not in scope

The card heading icons (17.8) and the row restructure (17.3). This sub-phase adds
a mark to the markup that exists.

---

## Outcome

Green in one helper and two call sites, as predicted. The asset had been on the
interface since Phase 12 and nothing in the account card had ever asked for it.

```text
Rule 1 — the provider's own mark, wherever the provider is named (17.1)
  (green — no output)

Account card: 11 passed, 23 failed, 0 pending   (was 9 / 25)
```

### The filter had one caller, and moving it fixed a divergence nobody had seen

`templates/form-auth.php` was the only place applying
`OMNIWP_provider_icon_svg`. That is the supported way to drop in an
official brand asset — Zalo's wordmark ships as a file this plugin cannot
redistribute — so a site using it would have got its own asset on the sign-in
screen and the plugin's drawing in the account card, from the same hook, in the
same session.

Not something the brief anticipated. It came out of asking where the filter
should live once there were two callers, which is a question that only exists
because there are now two.

### No CSS was needed in a row

`.sl-row` is already a flex container with a gap, so the mark is a sibling of
the label there and needs nothing. It is a child of the control on the
invitation button, which is `display: block` with centred text, and that one
line is the only rule this sub-phase added.

The mark sits *beside* the label rather than inside it. The label column is the
108px one 16.3 gave the contact rows; a mark inside it would have moved where
"Google" starts relative to "Email", which is the misalignment that sub-phase
exists to have removed.
