# 17.4 — The address the card names

Spec: [`../account-card.md`](../account-card.md), decision 4. Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Turn rule 4 green. The card says "giao hàng"; the writer writes
`billing_` and nothing else. Option (a): one address, mirrored, and a heading
that is true.

The only sub-phase in the phase that changes stored data.

## Files

- `includes/Address/class-address-fields.php` — `save_for_user()`
- `includes/Frontend/class-account-form.php` — the heading
- `templates/partials/account/address.php` — the note
- `includes/Auth/class-profile-completion-service.php` — the third name

## Steps

1. `save_for_user()` mirrors each `billing_*` write to its `shipping_*`
   counterpart, through the same `ProfileSeeder::set_many_from_user_input()`
   call, and writes `smartlogin_shipping_ward_code` beside
   `AddressFields::META_WARD_CODE` — the key `WooAddress::stored_ward_code()`
   already reads for the shipping prefix.
2. The heading becomes "Địa chỉ nhận hàng".
3. The note stops saying "sửa ở đây là sửa cả hai" and states what is now true:
   this address is what checkout and delivery both use.
4. `ProfileCompletionService` uses the same words, so the concept stops having
   three names.

## Acceptance

- Rule 4 green, both halves
- **A rename crosses every boundary no test covers.** Grep `Địa chỉ giao hàng`
  across `includes/`, `templates/`, `tests/`, `docs/` and `languages/` before
  claiming completion, and regenerate the string catalogue
- `is_complete()` and `get_for_user()` still read `billing_*` only — asserted, so
  the mirror does not quietly become a second source of truth
- **Integration, not reasoning:** user meta on a real WordPress goes through
  `tests/integration/`. If the WordPress gate cannot be run in this environment,
  that is written down as not run rather than assumed green

## Not in scope

WooCommerce's own Addresses tab. It keeps both forms; this changes what the
profile card writes, not what Woo renders.

## The cost, stated

A customer who has deliberately kept a shipping address different from their
billing address will have it overwritten the next time they save this form. That
is what one address means and what "nhận hàng" promises. It is written in the
spec as a decision rather than discovered later as a bug report.

### A rule from Phase 8.5 that had to be reversed, not deleted

```text
FAIL  the profile form never touches shipping
```

8.5 asserted exactly the opposite of this sub-phase, with a reason written into
the test:

> Shipping is left alone on purpose: a customer may deliver somewhere other than
> they are billed, and the profile card only ever edits the default.

That is true, and it is the cost this brief states. It is paid on purpose — a
heading naming an address the form does not touch is the worse of the two
failures, and 8.5's own note under the card was already telling those customers
that editing here edited both.

The assertion was replaced by its inverse rather than removed, with the history
and the cost in the comment above it, so the next reader finds a decision and
not a gap. Three new checks — state, city, `address_1` — plus the ward code.

### The rename went further than the four strings

`smartlogin_shipping_ward_code` was a string literal in two places in
`WooAddress` and a constant on the billing side only. It is
`AddressFields::META_SHIPPING_WARD_CODE` now, beside the twin it has always had.

Docs corrected rather than left describing something that no longer happens:
`account-surface/8.5-address-boundary.md`, `account-surface.md`, and the
README's storage table — which now also carries the cost, in Vietnamese, where a
site owner will read it.

### Not run, and written down as not run

`tests/integration/run-wordpress-gate.php` reports

```text
SMART_LOGIN_AUTH_INTEGRATION_BLOCKED
reason=SMART_LOGIN_WP_ROOT must point to a WordPress public root
```

There is no WordPress bootstrap configured in this environment, so the meta
writes are exercised against stubs only. The brief asked for this to be stated
rather than assumed green, and it is the one acceptance item this sub-phase did
not meet.
