# 17.7 — The fraction

Spec: [`../account-card.md`](../account-card.md), decision 7. Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Turn rule 7 green. "Hoàn thiện 4/6" needs a denominator, and the
denominator moves with five settings.

## Files

- `includes/Auth/class-profile-completion-service.php` — `status()`
- `templates/partials/account/status.php`
- `assets/css/smart-login.css` — the meter

## Steps

1. Each branch in `status()` that decides a field applies already runs; count
   there. `total` is every field in scope for this account, `done` is
   `total` minus what is missing.
2. The notice renders `done/total` and a meter. Two attributes carry the value
   for anything that is not looking at pixels: `role="progressbar"` with
   `aria-valuenow` / `aria-valuemax`.
3. No template counts anything.

## Acceptance

- Rule 7 green, both halves
- `total` moves when a setting moves — asserted with `profile.dob` off and on,
  because a denominator that is secretly a constant passes every other assertion
- `done === total` exactly when the account is complete and has nothing
  recommended outstanding
- Every other suite at its previous count

## Not in scope

Gamifying it. A meter that says 4/6 is a statement of fact; a badge that
congratulates somebody for reaching 6/6 is a different feature.

## Outcome

```text
Rule 7 — the fraction has a denominator, and one owner (17.7)
  (green — no output)

Account card: 38 passed, 2 failed, 0 pending   (was 36 / 4)
```

`status()` walks `fields_in_scope()` now: every field this account is asked for,
whether it holds one or not. One array per field decides whether it is in scope,
whether it is required and whether it is filled — the `FieldRegistry` shape,
applied to the other place in this plugin where one rule was spread across five
branches.

### Splitting the settings lookup from the missing test made an oddity visible

The old shape had both tangled in the same condition, twice for the address:

```php
if ( Settings::is_on( 'address.required_in_profile' ) ) {
    if ( $address_missing ) { … }
} elseif ( Settings::is_on( 'address.enabled' ) && $address_missing ) { … }
```

Pulled apart, it is clear that `required_in_profile` puts the field in scope on
its own, *without* `enabled`. That was the behaviour and it is kept rather than
tidied: an admin who has marked the address required has said something more
specific than an admin who has merely enabled it. Written down here because a
future reader would otherwise read it as a bug and "fix" it.

### The half that matters

`total` moves when `profile.dob` moves, asserted with the setting off and on. A
denominator that is secretly a constant passes every other assertion in that
section — which is why the acceptance named this one specifically.
