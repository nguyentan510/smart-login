# 17.6 — The password remembers when

Spec: [`../account-card.md`](../account-card.md), decision 6. Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Turn rule 5 green. The security row wants to say "đổi lần cuối 3 tháng
trước" and nothing in the plugin knows when that was.

## Files

- `includes/Security/class-security-meta.php` — new
- `includes/Frontend/class-form-controller.php` — `save_password()`
- `includes/Auth/class-password-reset-handler.php`
- `includes/Identity/class-user-manager.php` — `apply_password_hash()`
- `templates/partials/account/password.php`

## Steps

1. `SecurityMeta` owns the key, the write and the phrasing:
   `record_password_change()`, `password_changed_at()`,
   `describe_password_age()`.
2. All three writers call it. Three, not one: `apply_password_hash()` writes
   through `$wpdb` directly and fires no WordPress hook, so a listener would miss
   it — which is exactly why the rule is a companion rule over the writers rather
   than an assertion about a hook.
3. The password card shows the age beside the disclosure, and shows nothing when
   there is no timestamp.

## Acceptance

- Rule 5 green, both halves
- An account with no stored timestamp renders the control and no age — asserted
  directly, because that is every account that exists today and it is the case a
  test written after the feature would forget
- Buckets asserted separately, not as one "something is returned": 11.1 shipped a
  fallback chain as a no-op with its tests passing
- Every other suite at its previous count

## Not in scope

A password-expiry policy. This records a fact; it does not act on it.

## Why not `human_time_diff()`

It is translated by WordPress core, not by this plugin. On a site whose core is
English the card would read "Mật khẩu · đổi lần cuối 3 months trước". Ten lines
of our own strings buy the whole sentence in one language.
