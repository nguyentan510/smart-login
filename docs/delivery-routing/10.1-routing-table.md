# 10.1 — The routing table

Spec: [`../delivery-routing.md`](../delivery-routing.md) (D1). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Make the transport a configured fact instead of a property of the
destination string — while changing no site's behaviour.

This sub-phase ships alone and must be invisible. Nothing routes anywhere new
yet; the only difference is that routing has become something a setting can
answer.

## Files

- `includes/OTP/Transports/class-transport-router.php`
- `includes/class-field-registry.php`
- `tests/delivery/run-routing-tests.php`

## Steps

1. **Two settings**, tab `delivery`, section `otp` for now (10.6 moves them):

   | Path | Type | Choices | Default |
   | --- | --- | --- | --- |
   | `delivery.route_phone` | select | `sms` | `sms` |
   | `delivery.route_email` | select | `email` | `email` |

   One choice each at this point. 10.3 adds `automation` to both. A select with a
   single option is deliberate: it renders, it is saved, and it proves the path
   exists before anything depends on it.

2. **Split `transport_for()` in two.** The channel derivation is legitimate and
   stays; the transport decision moves to the table:

   ```php
   public function channel_for( string $destination ): string {
       return ( false !== strpos( $destination, '@' ) ) ? 'email' : 'phone';
   }

   public function transport_for( string $destination ): string {
       $channel = $this->channel_for( $destination );
       $routed  = (string) Settings::get( 'delivery.route_' . $channel, '' );

       return $this->get( $routed ) ? $routed : self::FALLBACK[ $channel ];
   }
   ```

   `FALLBACK` is `array( 'phone' => 'sms', 'email' => 'email' )` — the values the
   defaults already produce. It is not redundant with the defaults: a stored
   option can name a transport that a filter used to register and no longer does,
   and falling back beats resolving to nothing.

3. **Do not touch `send()`.** It already prefers `$ctx['transport']` when present
   (`class-transport-router.php:62`), which is what keeps the admin tester and
   any caller with an explicit choice working unchanged.

4. **Rule 5 goes green** — the choices and the resolvable transports are now the
   same set, and stay so because both read the registry.

## Acceptance

Rule 5 green, rule 1 still green. Behaviour identical: a phone destination
resolves to `sms` and an email destination to `email`, asserted both through
`transport_for()` directly and through a full `OtpService::issue()` on each
channel.

`php tests/run-all.php` — **all** required suites must be at their previous
counts, not merely passing. A changed count here means the routing change was not
invisible and must be understood before it lands.

## Not in scope

The `automation` choice, and any UI reorganisation. Both need something to route
to, and there is nothing yet.
