## Steps

Seven rules. Each names the defect it exists to prevent, in the test's own
message, so a future failure explains itself without this document.

1. **One routing authority.** No file outside `TransportRouter` decides a
   transport from the shape of a destination. Grep for `strpos` against `'@'`
   across `includes/`, with a per-file allowlist that must be justified in
   writing inside the test:
   - `OTP/class-otp-service.php:343,375` — derives the *identity channel*, which
     is legitimately a property of the identifier
   - `OTP/class-placeholders.php:26` — presentation, decides which token blanks
   - `OTP/Transports/class-transport-router.php` — the authority itself

   Red today: `class-transport-router.php:41` is inside the allowlist, so this
   rule passes at 10.0 and only bites if 10.3 or 10.6 reintroduces the shortcut
   elsewhere. Declared here anyway — the rule's job starts later than the others.

2. **`store_secret()` holds no per-path branch.** Extract the method body with
   the `token_get_all()` helper 9.0 added and assert it contains no string
   literal ending in `_secret`. Red today: `class-settings.php:227`.

3. **Every `secret` field round-trips.** For each `type => 'secret'` row in the
   registry, save a value through `Settings::sanitize()` and assert it comes back
   out of the store. Red the moment a secret field is declared without being
   wired — which is the defect D5 describes, and which no current test catches.

4. **Signed sends only.** No `wp_remote_request`/`wp_remote_post`/`wp_remote_get`
   call inside the automation namespace outside the single signing sender.
   Red from 10.3 onward; asserts nothing before that, and says so.

5. **The route table cannot dangle.** Every value offered by
   `delivery.route_phone` / `delivery.route_email` must be an id the router
   actually resolves via `get()`. A choice pointing at a transport that does not
   exist would fail closed at send time with no admin-visible cause.

6. **Bus failures stay inside the bus.** Drive the bus with an endpoint that
   errors and assert `OtpService::issue()` still returns an array, not a
   `WP_Error`, and that the OTP row survives. This is the rule that protects the
   D2 two-breaker decision from being "simplified" into one.

7. **`automation.url` refuses `http://`.** Save a plaintext URL and assert the
   stored value is empty and the previous value is not overwritten. Red from 10.3.

### The brief predicted rule 5 would pass. It was wrong, and the fix is the point

This brief said rules 1 and 5 would pass at 10.0. Rule 5 checks that every value
offered by `delivery.route_phone` / `route_email` resolves to a real transport —
and with those fields not yet declared, the loop has nothing to iterate, so it
would have reported PASS.

A rule that passes because its subject does not exist states the opposite of the
truth, and it would have gone on stating it right up until 10.1 declared the
fields. Changed to PENDING with the missing fields named as the blocker. The
harness already had `ow_pending()` for exactly this and the brief simply failed to
reach for it.

### Rule 1 could not see the defect it was written for

The allowlist form of the rule — no file may test a destination for `'@'` outside
a justified list — cannot fail on `TransportRouter`, because `TransportRouter` is
necessarily on the list. It guards the *spread*, not the original.

So the section carries a second, direct assertion: `transport_for()`'s body must
mention `delivery.route_`. That one fails today. Both are kept; they guard
different things, and dropping the allowlist rule would leave 10.3 and 10.6 free
to re-scatter the test.

### The allowlist is six files, not three

The brief named three. A full scan found six — `Phone::is_valid()` rejecting an
email offered as a phone, `Phone` finding the local part when masking,
`UserManager` building and recognising synthetic addresses, and
`RateLimiter::mask_identity()`. None decides a transport, all are legitimate, and
writing the reasons into the allowlist is what the rule is for.

### A brief was corrected before it was executed

Rule 3 needed to know where a secret is stored, and reading that turned up two
stores with two key schemes — `OMNIWP_captcha_secret` keyed `'captcha'`, and
`OMNIWP_provider_secrets` keyed by provider slug. Neither is keyed by field
path. 10.2's claim of "no migration" was therefore false: a generic path-keyed
store would strand every existing captcha secret.

10.2 has been rewritten with the table, a read fallback, and an acceptance
criterion that writes a fixture through the *old* path. Found by writing the test
first, which is the argument for this sub-phase existing.
