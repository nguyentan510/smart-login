# 10.6 — The Delivery tab

Spec: [`../delivery-routing.md`](../delivery-routing.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Split twenty-eight controls on one flat page into four screens that
each answer one question.

Sequenced last, deliberately. A screen can only present a routing model that
exists, and every earlier attempt to design this tab was really an attempt to
design the model — which is why the answer kept coming out as "more headings".

## The problem with the current tab

Three unrelated axes share one page (`class-field-registry.php:273-514`):

| Axis | Fields | Applies to |
| --- | --- | --- |
| OTP policy | `otp.*` (7) | every channel |
| Channel configuration | `sms.*` (15), `email.*` (4) | one transport each |
| Message content | `sms.body`, `email.subject`, `email.body` | one transport each |

Splitting by transport — the obvious reading of "chia SMS riêng, Mail riêng" —
separates the second axis and leaves the first and third still mixed in.

## Files

- `includes/class-field-registry.php` — `tabs()`, and the `tab` key on the
  delivery rows
- `includes/Admin/class-settings-page.php` — second-level nav
- `includes/Admin/Screens/class-settings-screen.php` — `after_section()` routing
- `assets/` — nav styling
- `tests/identity/run-admin-tests.php`

## Steps

1. **Four tabs, each a real slug.** This is a constraint, not a preference:
   `Settings::sanitize()` writes only the fields carried by the tab named in the
   POST (`class-settings.php:309`), which is what stopped every screen echoing
   gateway credentials back through hidden inputs. A JS show/hide over one form
   would post all twenty-eight fields together and dissolve that boundary — and
   the assertion at `tests/identity/run-admin-tests.php:340-356` is what would
   catch it.

   | Slug | Label | Holds |
   | --- | --- | --- |
   | `delivery` | Chính sách mã | `otp.*`, both route selects |
   | `delivery-sms` | Kênh SMS | `sms.*`, preset, Gửi thử |
   | `delivery-email` | Kênh Email | `email.*`, Gửi thử |
   | `delivery-automation` | Automation | `automation.*`, events, Gửi thử |

2. **Second-level nav.** `SettingsPage::nav()` renders one flat strip
   (`class-settings-page.php:179-190`); six tabs becoming nine would make the
   strip the worst thing on the page. Add a `parent` key to the `tabs()` rows and
   render children as a `subsubsub` list under the active parent — the WordPress
   idiom for exactly this, already styled by core.

   The existing test "the tab strip covers the registry" must be extended to
   assert every child is reachable, or a sub-tab can exist in the registry and be
   linked from nowhere.

3. **The route selects lead.** They go at the top of `delivery`, above the OTP
   policy, because they are the setting that decides which of the other three
   tabs matters. Each option's help text names the tab that configures it.

4. **State the role.** On `delivery-automation`, show which of D2's two roles is
   currently active — "đang gửi OTP cho: SĐT" / "chỉ gửi sự kiện" / "chưa dùng".
   Configured-but-not-routed is a valid state and must not read as broken.

5. **Default the SMS preset to `generic`.** `sms.preset` defaults to
   `GatewayPresets::CUSTOM` (`class-field-registry.php:350`), so a fresh install
   opens on all fifteen raw fields including a free-text JSON body — the hardest
   screen in the plugin, presented to the person who has configured the least.
   `generic` asks for one URL.

   This is a default change on an existing key. Only new installs are affected —
   `Settings::sanitize()` writes the stored value, so a site that has saved this
   tab keeps `custom`. Assert that.

6. **Move `otp.sms_unit_cost`** to `delivery` alongside the policy it belongs
   with. Grep for the key across `includes/`, `tests/` and `docs/` before
   claiming completion; 10.5 changed its meaning and this changes its home.

## Acceptance

Every delivery field is drawn on exactly one tab, asserted by walking
`FieldRegistry::all()` and rendering each tab — the property `FieldRegistry`
exists to guarantee and the one that must survive being split four ways.

Saving `delivery-sms` leaves `automation.*` and `email.*` byte-identical.
No tab except the one owning a credential renders it — the existing leak
assertion, extended to the new slugs.

A fresh install opens `delivery-sms` on the `generic` preset with one visible
credential field; a site with `custom` saved still opens on `custom`.

`php tests/run-all.php`, and the render assertions run where they already do, in
`tests/identity/run-admin-tests.php`.

## Not in scope

Email template groups — the one shared `email.subject`/`email.body` pair serving
all four intents. That is Phase 11 and it is a content problem, not a layout one;
folding it in here would make this sub-phase a redesign of two things at once.

Any change to the OTP policy fields themselves. They move tab and change nothing
else.
