# 10.3 — The automation transport

Spec: [`../delivery-routing.md`](../delivery-routing.md) (D2 transport role, D3,
D4). Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** A transport that hands the OTP to the administrator's automation
platform as a signed envelope, and is answerable for the delivery.

This is the sub-phase that lets the plaintext code leave the site. The spec's
"Security position" section is the argument for doing it; this brief is the set
of controls that make it defensible.

## Steps

1. **Settings**, tab `delivery`, new section `automation`:

   | Path | Type | Notes |
   | --- | --- | --- |
   | `automation.url` | url | sanitise `https_url`; empty means not configured |
   | `automation.secret` | secret | HMAC key, sealed by 10.2's generic store |
   | `automation.headers` | headers | reuses the existing repeater and sanitiser |
   | `automation.timeout` | number | min 2, max `WebhookTransport::MAX_TIMEOUT` |
   | `automation.success_path` | text | optional, same semantics as `sms.*` |
   | `automation.success_value` | text | optional |

   Then add `automation` to both route selects from 10.1.

2. **`https_url` sanitiser.** Reject anything not `https://`, returning the
   field's current stored value rather than empty — clearing an endpoint by
   fat-fingering the scheme would silently route OTPs nowhere. Add a settings
   error naming the reason; the administrator is present at save and nowhere
   else.

   The one documented exception: `wp_get_environment_type()` of `local` or
   `development` may accept `http://`, because a local n8n has no certificate and
   refusing it makes the feature untestable. Written down here and in the help
   text, per the deferrals rule.

3. **The signer**, used by this sub-phase and by 10.4:

   ```php
   EnvelopeSigner::sign( array $payload ): array  // [ body, headers ]
   ```

   `wp_json_encode` once, HMAC-SHA256 the exact bytes sent, and return both — so
   the signature can never be computed over a different serialisation than the
   one transmitted. Constant-time comparison is the receiver's problem, but the
   help text must show the verification snippet, because a signature nobody
   verifies is decoration.

4. **`is_available()`** is `'' !== automation.url && '' !== automation.secret`.
   No secret means no signature means an unauthenticated endpoint receiving live
   OTPs; that configuration is not offered.

5. **`send()`** builds the `otp.send` envelope of D3, posts it blocking with the
   clamped timeout, and applies the same success test `WebhookTransport` uses —
   2xx, plus the optional JSON path check. Reuse `WebhookTransport::dig()` by
   lifting it to a shared helper rather than copying it.

6. **Redaction is not optional.** The new transport's debug output goes through
   the same `redact()` discipline (`class-webhook-transport.php:302-308`) and the
   same secret-header masking. Rule 4 in 10.0 asserts the send goes through the
   signer; a separate assertion checks the code never appears in the returned
   debug structure.

7. **Breaker.** Nothing to do — `TransportRouter::send()` already constructs
   `new CircuitBreaker( $transport_id )` (`class-transport-router.php:102`), so
   registering under the id `automation` gets an isolated breaker for free. Assert
   it: the point of D2's two-breaker rule is that this one is *not* shared.

## Acceptance

Rules 4, 5 and 7 green. Rule 1 still green — this sub-phase must not add a ninth
place that inspects a destination for `@`.

Concretely: with `delivery.route_phone = automation`, a phone OTP produces one
signed HTTPS POST whose body verifies against the stored secret, and the OTP row
survives; with the endpoint returning 500, `issue()` returns a `WP_Error` and the
row is rolled back (`class-otp-service.php:138-155`); five consecutive failures
open the `automation` breaker and leave the `email` breaker untouched.

`php tests/run-all.php`, plus one `tests/integration/` case — the HTTP layer,
`wp_remote_request` arguments and the settings-error path all need a real
WordPress. Four gates once missed a fatal that only a real WordPress could show.

## Not in scope

The event bus (10.4). This sub-phase sends exactly one event, `otp.send`, and
only when routed to.

Per-channel endpoints. One endpoint serves both channels; the envelope's
`channel` field is how the receiver tells them apart. If a site genuinely needs
two, that is a second automation profile and a later argument.

### Rule 4 was wrong, and it was 10.0 that wrote it wrong

The rule said *only the signer may call `wp_remote_*`*, which assumed the signer
would also be the sender. `EnvelopeSigner::sign()` returns a body and its
headers and puts nothing on the wire — a class that signs *and* sends can only
ever be asked to do one of those by whoever next needs the other.

So the structural half became "exactly one file puts an automation request on
the wire", and the property that actually matters — that the sender signs — is
asserted on behaviour: the HMAC is recomputed over the transmitted string and
compared to the header. Recomputing it from a re-encoded payload would have
passed against any implementation and proven nothing, which is the classic way a
webhook signature becomes decorative.

### The regex hit a docblock

`TransportProbe`'s `@param` said "Result of `wp_remote_request()`", which the
rule read as a call. Fixed by rewording the comment rather than by allowlisting
the file: an allowlist entry earned by a comment would silently cover a real call
added there later.

### Two things the brief did not anticipate

**`channel_for()` had to become static.** `AutomationTransport` needs the channel
for the envelope, and rule 1 forbids it deriving that from the destination
itself. Asking `TransportRouter` is the right answer, but the transport has no
router instance and building one inside a transport the router owns is a loop.
The method has no state, so it is static now and the call is a lookup rather than
a construction.

**A routed-but-unconfigured transport needed its own rule.** Nothing asserted
what happens when a channel points at `automation` and no endpoint is set.
Falling through to the built-in would make the routing table advisory — an
administrator who pointed a channel somewhere would never learn it did not go
there. Rule 10 pins the failure closed.
