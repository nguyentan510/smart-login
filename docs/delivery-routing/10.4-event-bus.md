# 10.4 — The event bus

Spec: [`../delivery-routing.md`](../delivery-routing.md) (D2 bus role). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Push the events the plugin already records to the same automation
endpoint, so an external system can react to registrations, logins, resets and
abuse trips without polling anything.

The plugin has nineteen event constants and no way to tell anyone about them
(`includes/Security/class-audit-log.php:19-39`). Once 10.3 has a signer and a
sender, carrying them costs almost nothing — and it is the answer to "cảnh báo
đăng nhập" that does not require the plugin to grow a mail composer.

## Files

- `includes/OTP/Transports/class-event-bus.php` — new
- `includes/Security/class-audit-log.php` — one dispatch point
- `includes/class-field-registry.php`
- `tests/delivery/run-routing-tests.php`

## Steps

1. **One dispatch point, not fifteen.** Every event already funnels through
   `AuditLog::record()`. Hooking the bus there means a new event constant is
   automatically busable and cannot be forgotten — the same argument
   `FieldRegistry` makes for settings. Do **not** scatter `do_action` calls
   through the handlers.

2. **Setting** `automation.events`, a checkbox list built from the `AuditLog`
   constants, tab `delivery`, section `automation`. Default: empty. The bus is
   off until an administrator picks events; a plugin that starts POSTing a site's
   login stream somewhere on upgrade would be indefensible.

   The choices are generated from the constants, not typed out, so a constant
   added later appears without a second edit. Assert that the option can hold
   only known constants, or a stale stored value keeps firing an event nobody
   recognises.

3. **Never the code.** The bus envelope omits `code` entirely — not blank, not
   masked, absent. Destinations use the same masking `AuditLog` already applies
   (`RateLimiter::mask_identity()`), because the bus inherits the audit log's
   privacy posture rather than inventing a looser one.

4. **Non-blocking.** `'blocking' => false`. The consequence is stated, not hidden:
   the site cannot know whether a bus event arrived. That is the correct trade —
   `WebhookTransport::MAX_TIMEOUT`'s comment explains what synchronous outbound
   calls do to a PHP-FPM pool (`class-webhook-transport.php:18-25`), and doubling
   them on every login is the version of this feature that takes a site down.

   The admin tester sends blocking, since a test the administrator cannot read
   the result of is not a test.

5. **Its own breaker,** id `automation_bus`. A non-blocking call still costs a
   connection, so a dead endpoint on a busy site is still worth stopping. It must
   never be consulted on the OTP path — rule 6 exists for this.

6. **Its own audit event.** `AUTOMATION_BUS_FAILED`, and it must be in
   `NEVER_SAMPLED` — a sampled failure record on a fire-and-forget channel is the
   worst of both, since it is the only evidence there is. Guard against recursion:
   a bus failure recording an audit entry must not dispatch a bus event.

## Acceptance

Rule 6 green: a bus endpoint returning 500 leaves `OtpService::issue()` returning
an array and the OTP row intact. Rule 4 still green — bus sends go through the
same signer.

An event not ticked produces no request at all. A ticked event produces one
request whose body verifies and contains no `code` key, asserted by
`array_key_exists`, not by checking the value is empty.

Recursion: forcing a bus failure produces exactly one audit record and exactly
one outbound attempt.

`php tests/run-all.php`. The abuse-boundary suite is the one to watch — the bus
hooks the same `AuditLog::record()` that 9.1 and 9.3 depend on.

## Not in scope

Retry and delivery guarantees. Fire-and-forget is the design, and a site needing
at-least-once semantics should point the endpoint at a queue it controls. Written
here rather than left to be discovered.

Event filtering by user, role or intent. One checklist, whole events.
