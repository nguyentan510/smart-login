# 10.7 — Consume ordering and the worker-hold ceiling

Spec: [`../delivery-routing.md`](../delivery-routing.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Stop a failed send from destroying a code the user is already holding,
and give the email channel the same ceiling on worker time the SMS channel has
had since 9.3.

**Numbered last, sequenced first.** Both defects are in the tree now, neither has
anything to do with routing, and both get worse the moment 10.3 adds a third
transport — more transports is more failure surface, and an automation endpoint
is the one piece of delivery infrastructure the site does not operate. Sub-phase
numbers in this repo are allocation order, not execution order; 9.10 landed
before 9.8 for the same kind of reason.

## Defect A — the code is invalidated before the send is attempted

```php
:100   $this->repo->consume_open_codes( $destination, $intent );
:106   $row_id = $this->repo->insert( … );
:136   $sent = $this->router->send( $destination, $code, $send_ctx );
:142   $this->repo->delete( $row_id );          // only on failure
```
`includes/OTP/class-otp-service.php`

The old code dies at `:100`, before anything knows whether the new one can be
delivered. On failure the new row is rolled back and the old one stays consumed,
so the user is left with neither.

Reachable through the ordinary Gửi lại button, `OtpService::resend()`
(`:278-296`) → `issue()`. The full chain:

1. User holds a valid code A and presses Gửi lại.
2. `consume_open_codes()` kills A.
3. The gateway fails; the new row is deleted.
4. `handle_resend_otp()` keeps the old token in the session, under the comment
   `// Keep the user on the OTP screen; the old code may still be valid.`
   (`includes/Frontend/class-form-controller.php:713`). **That comment is
   false** — A was consumed at step 2.
5. `restore_otp_step()` → `peek()` returns null (consumed) → the screen renders
   with `expires_in = 0`.
6. If the user types A anyway, `verify()` takes the `consumed_at` branch
   (`class-otp-service.php:216-218`) and answers *"Mã xác thực đã được sử
   dụng"* — telling them they used a code they never got to use.

The rollback at `:142` was written to protect the user's quota, and its comment
says so. It protects the quota and destroys the credential.

## Defect B — only one of the two channels has a time ceiling

`WebhookTransport::MAX_TIMEOUT` is 15 seconds, with the arithmetic spelled out at
`class-webhook-transport.php:18-25`: at ten sends a second a ten-second timeout
occupies a hundred workers and a typical PHP-FPM pool has twenty to fifty.

`MailTransport` calls `wp_mail()` and the plugin registers no `phpmailer_init`
callback, so the defaults apply. Verified against the WordPress this project runs
on:

```
wp-includes/PHPMailer/SMTP.php:181   public $Timeout   = 300;
wp-includes/PHPMailer/SMTP.php:189   public $Timelimit = 300;   // doubled for DATA END at :879
```

Twenty times the SMS ceiling, on the channel that is enabled by default.

The circuit breaker does not cover this. It opens after five consecutive
failures, and each of those five may hold a worker for the full five minutes —
it bounds *how often* a dead channel is called, not *how long* one call may take.
The comment at `class-transport-router.php:97-101` claims the breaker sits in the
router because a hanging SMTP server holds a worker exactly as a hanging HTTP
gateway does. True, and exactly why the ceiling is the missing half.

## Steps

1. **Guard rails first, red.** Rule 8 asserts that after a failed `issue()` the
   previously issued row is still unconsumed, driven through the seams
   `OtpService` already offers — it takes its repository, router and limiter by
   constructor. Rule 9 asserts the SMTP send is bounded.

2. **Move the consume below the send.** The new row is inserted *after* the
   consume today, so it never consumed itself; moving the consume to the success
   path preserves that and removes the need for the rollback entirely:

   ```php
   $sent = $this->router->send( $destination, $code, $send_ctx );

   if ( is_wp_error( $sent ) ) {
       $this->repo->delete( $row_id );
       …
       return $sent;
   }

   // Only now is the newest code the one that works. Doing this before the
   // send meant a gateway failure destroyed a code the user was holding and
   // left them with nothing — the rollback below protected their quota and
   // took the credential with it.
   $this->repo->consume_open_codes( $destination, $intent, $row_id );
   ```

   `consume_open_codes()` gains an exclusion parameter for the row just issued.
   Doing it by `id` rather than by ordering is deliberate: two concurrent issues
   for one destination would otherwise race to consume each other.

3. **Delete the false comment** and replace it with what is now true — the old
   code *is* still valid, because nothing consumed it. `restore_otp_step()` then
   renders a live `expires_in` instead of zero, which is the user-visible half of
   the fix.

4. **Clamp the SMTP send.** One `phpmailer_init` callback on the same ceiling:

   ```php
   $mailer->Timeout   = WebhookTransport::MAX_TIMEOUT;
   $mailer->Timelimit = WebhookTransport::MAX_TIMEOUT;
   ```

   Registered only while the plugin's own mail is in flight, not globally — the
   site's other mail is not this plugin's to reconfigure, and a 15-second ceiling
   on a WooCommerce invoice with attachments would be a regression the site owner
   never asked for.

## Acceptance

Rules 8 and 9 green.

Behaviourally: issue a code, make the transport fail, issue again — the first row
is unconsumed and still verifies; the second row does not exist. Then make the
transport succeed and issue again — now the first row *is* consumed, because that
is the property the consume exists to hold.

The clamp applies to the plugin's own send and is gone afterwards, asserted by
checking the filter is not still registered once `send()` returns.

`php tests/run-all.php` — required suites at their previous counts. The
regression and abuse suites both drive `issue()` and are where an ordering change
would show up first.

## Not in scope

Delivery confirmation for email. `wp_mail()` returning true means PHP handed the
message to an MTA, not that anything was delivered, and no ceiling or ordering
change makes that claim any truer. Reporting it honestly belongs with the
readiness work in 10.5.

### The stub registry had to grow, and that broke a suite

`MailTransport` now registers and removes `phpmailer_init`, and `tests/stubs.php`
had `add_filter` but no `add_action`, `remove_filter` or `remove_action`. A stub
that cannot express *registered, then removed* cannot assert the half of rule 9
that matters — the clamp is right for a six-digit code and wrong for a
WooCommerce invoice, so leaving it registered would be a regression the site
owner never asked for.

Adding them turned `Admin screens` red with a redeclaration fatal:
`tests/admin-stubs.php` carried its own no-op `add_action`. That file already
contained the answer — a comment written in 9.0 explaining why `add_filter` had
been removed from it for exactly this reason. The no-op is gone and the comment
now covers both.

Worth noting the shape: a harness change broke a suite in a way that was loud and
immediate. The alternative — a no-op `add_action` silently winning over the real
registry — would have made rule 9 pass while asserting nothing.

### What the fix does not fix

The rollback comment at `class-otp-service.php:138` said the row is deleted so
the failed attempt does not eat the user's quota. That was true and stays true.
What it did not say is that the code the user was holding had already been
destroyed twenty lines earlier, and the screen then told them it had "already
been used". Moving one call fixes the behaviour; the comment at
`class-form-controller.php:713` had to be rewritten too, because it asserted the
property the code path removed.

That comment is the second time this project has found a sentence describing a
control that did not exist. The first two were in the README.
