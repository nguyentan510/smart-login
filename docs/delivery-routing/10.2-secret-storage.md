# 10.2 — Generic secret storage

Spec: [`../delivery-routing.md`](../delivery-routing.md) (D5). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Make a `type => 'secret'` field that nobody wired impossible, rather
than merely absent today.

Smallest sub-phase in the phase, and it is sequenced before 10.3 because 10.3
declares the second secret field the plugin has ever had — and the current code
would accept its input and throw it away.

## Files

- `includes/class-settings.php`
- `includes/Security/class-captcha.php`
- `tests/delivery/run-routing-tests.php`

## Steps

1. **Read the current failure before changing it.** `absorb_secret_fields()`
   prunes the plaintext from the option array unconditionally
   (`class-settings.php:219`), then hands the value to `store_secret()`, which
   stores it only when the path matches one literal (`:226-234`). A new secret
   field therefore loses its value with no error, no notice and no log entry.
   Pin that in the test first — rule 3, red.

2. **Route by path, not by name:**

   ```php
   private static function store_secret( string $path, string $secret ): void {
       if ( '' === $secret ) {
           SecretBox::forget( self::SECRET_OPTION, $path );
           return;
       }

       SecretBox::put( self::SECRET_OPTION, $path, $secret );
   }
   ```

   and the matching `read_secret( string $path ): string` over `SecretBox::get()`.

3. **There are already two secret stores, and neither is keyed by field path.**
   Found while writing 10.0's rule 3 — this brief originally claimed the key was
   unchanged and that claim was wrong:

   | Store | Option | Key |
   | --- | --- | --- |
   | Captcha | `smart_login_captcha_secret` | `'captcha'` (`class-captcha.php:66-76`) |
   | Providers | `smart_login_provider_secrets` | the provider slug (`class-provider-credentials.php:42-81`) |

   `ProviderCredentials` is the better model: one option, many keys, no branch
   per key. The generic store follows it — option `smart_login_field_secrets`,
   keyed by the registry path.

4. **Captcha keeps its accessor and gains a read fallback.**
   `Captcha::secret()` reads the new store first and falls back to the legacy
   `'captcha'` key, writing through on the next save. Without the fallback every
   existing install silently loses its captcha secret — including the
   author's local site, so "never run in production" does not excuse it.

   Grep before claiming completion — `captcha_secret` and `SECRET_OPTION` across
   `includes/`, `tests/` and `docs/`. This is a storage-key change and this
   project has been bitten five times by exactly that shape.

5. **Assert the fallback, not just the round trip.** Write a fixture through the
   *old* path, then read it through the new accessor. A test that only exercises
   save-then-load passes on a store that lost every existing value.

## Acceptance

Rules 2 and 3 green — including the four PENDING lines rule 3 currently emits,
which must become assertions rather than disappearing.

A captcha secret written through the old path is still readable after the change.
Every `type => 'secret'` row in the registry round-trips through
`Settings::sanitize()` and back out through `Settings::read_secret()`.

`php tests/run-all.php` — the regression suite is the one that must not move; it
owns the existing captcha round trip at `run-tests.php:360-372`.

## Not in scope

Key rotation, and any change to `SecretBox`'s envelope format. The sealed record
shape stays exactly as it is (`class-secret-box.php:34`).

## Outcome

Rules 2 and 3 green, and with them the last failing rule in the suite:
`Delivery routing: 22 passed, 0 failed, 4 pending`. The suite is **promoted to
`required`** in `run-all.php`, for the reason Phase 5 promoted the identity
suites — a passing suite left non-blocking can only hide the next regression.
The four PENDINGs belong to 10.3 and 10.4 and do not block.

Every required suite at its previous count; phpcs back to the 17/15 baseline.
The regression suite's existing captcha round trip (`run-tests.php:360-372`) went
through the new store untouched, which is the cheapest possible evidence that the
delegation works on the real path rather than only on the new test's.

### The legacy fallback is a lookup, not a branch

Rule 2 forbids a per-field branch inside `store_secret()`, and a legacy location
is per-field information. Resolved by shape: `LEGACY_SECRETS` is a constant map
consulted by `read_secret()` and by a `forget_legacy_secret()` helper, so the
storage method itself stays branch-free and the history lives in a table that
shrinks to nothing when the last entry is retired.

### Clearing had to reach the old copy, and nearly did not

The first working version cleared only the new location. Because `read_secret()`
falls back to the legacy one, an administrator ticking *xoá secret đã lưu* would
have had the secret **come back on the next read** — a delete that looks like it
worked and did not. `store_secret()` now drops the legacy copy on every write,
clear or not.

### The test proved nothing until it was reordered

`a secret sealed by the old code is still readable` passed while asserting
nothing: the round-trip block earlier in rule 3 had already written to the new
store for the same path, so the fallback never ran and the assertion compared the
round-trip value to itself. It only failed once the new location was emptied
first. Exactly the failure the brief warned about — *a test that only exercises
save-then-load passes on a store that lost every existing value* — reproduced by
the test written to prevent it.

### A rename sweep found two things the change was responsible for

Grepping `SECRET_OPTION` and `captcha_secret` across `includes/`, `tests/`,
`docs/` and the root scripts, as the working agreement requires:

- `uninstall.php` deleted `smart_login_provider_secrets` but never
  `smart_login_captcha_secret`, so an uninstall left an encrypted secret behind.
  Pre-existing, and this sub-phase would have added a second orphan. Both are now
  in the list.
- The same file gates everything on a **flat** `delete_data_on_uninstall` key
  while the setting has been `advanced.delete_data_on_uninstall` since the
  settings rewrite, so the opt-in never opens and nothing is ever deleted.
  Recorded in the tracker and left for its own commit — it is not about secret
  storage, and making an uninstall routine start destroying data deserves its own
  guard rail rather than a line inside this one.
