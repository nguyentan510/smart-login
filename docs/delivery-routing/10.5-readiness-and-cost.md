# 10.5 — Readiness and cost accounting

Spec: [`../delivery-routing.md`](../delivery-routing.md) (D6, D7). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Stop two admin-facing numbers from going quietly wrong the moment a
channel is routed somewhere new.

Both defects are introduced by 10.1–10.3 and neither is visible: one reports a
site as ready when it cannot send, the other reports a spend of zero while money
is being spent.

## Files

- `includes/Admin/class-readiness.php`
- `includes/OTP/class-otp-repository.php`
- `tests/identity/run-admin-tests.php`
- `tests/delivery/run-routing-tests.php`

## Steps

1. **Readiness asks the router.** Replace the two hard-coded constructions
   (`class-readiness.php:136-142`) with, for each enabled identity channel, the
   transport the router resolves for it, checked through `is_available()`.

   This is strictly better than what it replaces even before routing existed: it
   cannot drift from what actually happens at send time, because it asks the same
   object.

2. **The new dangerous configuration.** A channel routed at `automation` with no
   URL or no secret is a FAIL, not a WARN, and the message says which channel and
   which setting. Without this the failure surfaces as "Kênh SMS chưa được cấu
   hình" to a visitor — the precise scenario `Readiness` was written for
   (`class-readiness.php:5-9`).

3. **Count phone OTPs, not `sms` rows.** `count_recent_by_transport( 'sms', … )`
   (`class-readiness.php:220`) becomes a count by identity channel.

   The `identity_channel` column is not trustworthy: `class-otp-service.php:110`
   writes `''` when neither the payload nor the context supplies a channel. Use
   the derivation `OtpService:336-345` already applies for the same reason —
   column when set, destination shape when empty. Do **not** add a third place
   that inspects `@`; call the router's `channel_for()` from 10.1, or rule 1 goes
   red and rightly so.

4. **Rename the cost setting's label, not its key.** `otp.sms_unit_cost` now
   means "cost per phone OTP however it was sent". Change the label and help
   text; leave the key. A key rename here would cross `includes/`, `tests/` and
   `docs/` for no functional gain, and this project has been bitten five times.
   Record the mismatch in a comment at the declaration so the next reader is not
   surprised.

## Acceptance

With `identity.mode = both`, `delivery.route_phone = automation` and no
`automation.url`: readiness reports FAIL naming the phone channel, and the
aggregate is false. With the endpoint configured: OK.

With three phone OTPs sent through `automation` and a unit cost set, the estimate
reads three, not zero. The existing admin-suite assertion on the `delivery` check
(`tests/identity/run-admin-tests.php:177-214`) must be extended, not replaced —
its current cases still describe valid configurations.

`php tests/run-all.php`, and the readiness cases run under
`tests/integration/` where a real options table exists.

5. **`MailTransport::is_available()` must mean something.** It returns
   `Settings::is_on( 'email.enabled' )` and nothing else
   (`class-mail-transport.php:24-26`), so the email channel can never report
   itself unready — and readiness calls exactly that function
   (`class-readiness.php:140`). A site that has never configured SMTP is told
   **Đã sẵn sàng**. The SMS channel cannot lie the same way because its check
   also requires a URL.

   There is no honest synchronous probe for "can this site send mail", so the
   check reports what it can stand behind: enabled, plus whether anything has
   actually been delivered through it, plus a WARN naming the absence of an SMTP
   plugin on a host with no `sendmail`. Found while evaluating the three
   channels' flow; scoped here because 10.5 already opens both files.

## Not in scope

A per-transport cost table. One unit cost is what the estimate has always been
and widening it is a separate argument.

Delivery confirmation. `wp_mail()` returning true means the message reached an
MTA. Nothing in this sub-phase makes that claim stronger, and `AuditLog::OTP_SENT`
recording the same event for both channels stays as it is until something can
tell the difference.

## Outcome

Green, and qualified.

```text
Admin screens:     61 → 66 passed
Delivery routing:  45 → 46 passed, 0 failed, 0 pending
```

Every other required suite at its previous count; phpcs at the 17/15 baseline;
the whole integration chain re-run, all six markers OK.

### The fix was at write time, not read time

The brief planned to compensate for an unreliable `identity_channel` column by
deriving the channel when reading. That is the wrong end. `OtpService` was
storing `''` whenever no handler happened to pass a claim — login and password
reset among them — so the column was blank on most rows for no reason other than
nobody filling it.

It now derives from `TransportRouter::channel_for()` at insert, which keeps the
`'@'` test inside the one file allowed to make it and makes
`count_recent_by_channel()` a plain `WHERE`. Rows written before this are not
counted, recorded in the method's docblock with the reason it is acceptable
rather than left for someone to find as a discrepancy.

### A guard rail from Phase 9 caught this sub-phase

`Readiness::delivery()` first read the route as
`Settings::get( 'delivery.route_' . $channel, '' )`, and the abuse suite went red:

```text
  FAIL     no Settings::get() reads a key FieldRegistry does not declare
Abuse boundary: 27 passed, 1 failed
```

A key assembled from a literal prefix is a key nothing can check against the
registry — which is exactly the defect 9.9's rule exists to catch, and the same
trap 10.1 avoided deliberately and this file walked into anyway. Fixed by reading
through `TransportRouter::ROUTES`, so the path comes from the same table the
router uses.

Twice now a rule written in an earlier phase has caught new work on the first
run. That is the argument for guard rails, demonstrated on the author.

### `is_available()` was left alone on purpose

The obvious fix for "the email channel can never report itself unready" is to
make `MailTransport::is_available()` stricter. That would be wrong: the router
consults it to decide whether to attempt a send, so a stricter version would
refuse to send mail on hosts where `wp_mail()` works perfectly well through
`sendmail`.

The dishonesty was in readiness *treating it as proof*, not in the method. So
readiness now reports what it can stand behind — nothing has ever gone out
through the channel, the host declares no `sendmail_path`, and no SMTP plugin has
registered `phpmailer_init`, `pre_wp_mail` or `wp_mail_from` — and says it as a
WARN. A FAIL would cry wolf on every fresh install, and there is no honest
synchronous probe for "can this site send mail" that does not cost a real send.

`MailTransport`'s own `phpmailer_init` clamp from 10.7 is added around its send
and removed in a `finally`, so it cannot produce a false negative here. That is
the second time that `remove_action` has mattered for a reason other than the one
it was written for.

### Two test-shaped findings

**The readiness assertions belong in the admin suite.** They were written into
the delivery suite first and fatalled on `admin_url()`, which only
`tests/admin-stubs.php` provides. The brief had already said to extend the admin
suite's existing block; writing them elsewhere was the shortcut. The two original
cases are untouched — they still describe valid configurations — and the new ones
sit beneath them.

**The suite's service helper registered one transport.** `ow_service_with()` built
a router holding only `sms`, so an email destination resolved to a transport that
was not there, the send failed and the row was rolled back. Every earlier rule
used phone destinations, so nothing noticed until a rule asserted on both
channels — a helper that quietly made one channel untestable.
