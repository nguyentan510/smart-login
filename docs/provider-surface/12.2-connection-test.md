# 12.2 — The connection test

Spec: [`../provider-surface.md`](../provider-surface.md) (D3). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Let an administrator find out that their redirect URI is wrong before a
customer does.

## Why this cannot be a cheap check

Every other channel's test sends something and reads the answer. A provider's
common failure is a redirect URI registered with one character different, and
nothing exposes that: Google will not answer "is this URI registered", and the
plugin cannot inspect the provider's console. The only honest test is to perform
the exchange and report what comes back.

So the test is a real OAuth round trip, and the entire design is the sentence
that has to stay true while it is:

> A test round trip must never issue a session, create a user, or link an
> identity.

`callback()` consumes the transaction and reaches `SessionIssuer::issue()`
(`class-provider-auth-controller.php:139`), with account provisioning before it.
Reusing that path would mean a diagnostic that signs the administrator in and, on
an account that does not exist yet, creates one. Nobody would notice until it had
happened, because signing in successfully is what success looks like.

## Steps

1. **A third mode on the transaction.** The store already carries `linking`,
   which is how it means "attach this to the signed-in user" rather than "sign
   somebody in". Add `mode` with `login` | `link` | `test`, and derive `linking`
   from it rather than keeping two flags that can disagree — two booleans meaning
   three states is how the third state gets forgotten.

   Migration: transactions live in a transient with a short TTL, so an in-flight
   one from before this change may lack `mode`. Absent means `login`, and that
   default is asserted.

2. **`callback()` branches before anything that writes.** Immediately after
   `consume()` and the identity read, a test transaction renders its result and
   returns. It never reaches the resolver, the provisioner or the issuer.

   Placed there rather than earlier because everything up to that point is what
   the test exists to exercise: the code exchange, the token, and the identity
   the provider actually returned.

3. **The result is the provider's own words.** A mismatched redirect URI comes
   back as `redirect_uri_mismatch` with a description; an app still in Testing
   comes back as `access_denied`. Both are more useful than anything this plugin
   could write, so they are shown verbatim alongside the callback URL that was
   sent, which is the pair an administrator needs to compare.

4. **A third tab on the card.** Thiết lập / **Kiểm tra** / Hướng dẫn. The panel
   holds one button that opens the flow in a new window, and the result lands
   back on the screen.

5. **The test is available whether or not the provider is enabled.** It is how
   somebody checks a configuration *before* switching it on, and requiring the
   switch first would make the badge's new middle state — configured, not
   enabled — a state you cannot test your way out of.

## Acceptance

Rule 3 green, both halves.

A test round trip against a provider returning a valid identity reports success,
and: no session cookie is issued, no user is created, no identity row is written.
Asserted on the collaborators rather than on the outcome, because "no user
appeared" also passes when the exchange failed for an unrelated reason.

A provider error is reported verbatim with the callback URL beside it.

A transaction with no `mode` behaves as `login`, so an in-flight redirect across
the deploy still signs its user in.

`tests/integration/run-provider-gates.php` covers the callback branch against a
real WordPress: `wp_safe_redirect`, the transient round trip and the admin
screen's nonce all need one, and the provider gates already own that ground.

## Not in scope

Automating the round trip. It needs a human at the provider's consent screen by
construction, which is also why it is a button rather than a check that runs on
page load.

Testing a provider the plugin does not ship. `smart_login_providers` can register
one; whether its errors read well is its own author's problem.
