# 12.1 — Where the two controls sit

Spec: [`../provider-surface.md`](../provider-surface.md) (D1, D2). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Put the switch next to the badge that reports on it, and the policy
that governs both cards above both cards.

Presentation only. No schema change, no new setting, no behaviour change — which
is also the acceptance: every count in every suite stays where it is except the
two assertions this turns green.

## Files

- `includes/Admin/class-provider-cards.php`
- `includes/Admin/Screens/class-settings-screen.php`
- `assets/css/admin.css`
- `tests/identity/run-admin-tests.php`

## Steps

1. **The switch moves into the header.** `ProviderCards::card()` renders
   `providers.<slug>.enabled` beside the title, and stops passing it to the
   `form-table` loop.

   It keeps its registry row and its name attribute unchanged. This is where a
   layout change becomes a data change if nobody is careful: the field must still
   post under `FieldRenderer::name()`, or the admin suite's every-field-is-drawn
   walk catches it — which is the point of that walk.

2. **A checkbox with no `<tr>` around it.** `FieldRenderer::checkbox()` emits a
   whole table row. The header needs the control without the row, so the input is
   rendered directly here rather than by teaching the renderer a second mode for
   one caller.

   The hidden companion input comes too. Without it an unticked box posts nothing
   and `sanitize()` reads absence as "not on this tab", so a provider could never
   be switched *off* — the same trap 10.4's checkbox list hit, and the reason
   that partner input exists at all.

3. **The linking policy moves above the grid.** `ProviderCards::render()` draws
   it in the intro block, framed as applying to every card below it. The
   `linking` section stops being rendered separately by `SettingsScreen`, which
   means its heading goes with it — the framing sentence replaces it.

   Its registry row keeps `section => 'linking'`, because the section is still
   what groups it; only who draws it changes.

4. **CSS for a header that now holds a control.** The header is already a flex
   row with the title on one side and the badge on the other; the switch joins
   the title side.

## Acceptance

Rules 1 and 2 green.

Every field the `providers` tab claims is still drawn — the existing walk, which
is what would catch step 1 going wrong.

Saving the tab with the box unticked stores `0`, and with it ticked stores `1`.
Asserted through `Settings::sanitize()` rather than by reading the markup,
because the markup is exactly what changed.

No other suite moves.
