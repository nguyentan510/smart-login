# 19.9 — The cart that already survives

Spec: [`../sign-in-anywhere.md`](../sign-in-anywhere.md), finding 13.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**This sub-phase was scoped as a feature and is being delivered as a proof.**
That is the honest outcome of checking before building, and it is written here
rather than quietly absorbed.

**Goal.** Assert that "add to cart as a guest → sign in through the dialog →
still on the product page, both carts intact" holds, so it cannot regress.

## Why there is no cart code here

The plan was to make an interrupted add-to-cart resume after sign-in. It does
not need to:

- `WC_Cart_Session::get_cart_from_session()` merges the guest session cart with
  the member's saved cart when `_woocommerce_load_saved_cart_after_login` is set
  (`woocommerce/includes/class-wc-cart-session.php:115-124`)
- that meta is written by `wc_user_logged_in()` on **`wp_login`**
  (`wc-user-functions.php:1096-1100`)
- `SessionIssuer::issue()` fires `wp_login` (`class-session-issuer.php:43`), and
  `wp_set_auth_cookie` appears nowhere else in `includes/` — every sign-in this
  plugin performs goes through that one method

So the cart already survives. What did not survive was the visitor's **place**:
finding 1 sends them off the product page, and to `wp-admin` if they are new.
19.5 fixes that. Writing cart code on top of a working merge would have been
inventing work, and shipping it would have made `wp_login` load-bearing without
anything asserting it.

## Files

- `tests/integration/` — one scenario
- `tests/run-sign-in-anywhere-tests.php` — one rule

## Steps

1. **The rule:** every path that mints a session fires `wp_login`. Asserted over
   the writers — `wp_set_auth_cookie` has exactly one call site — rather than by
   listening for the action, so a second issuer added later fails the rule
   instead of silently breaking the cart. This is the shape 17.6 used for the
   password-hash writers and for the same reason.
2. **The scenario**, against a real WooCommerce: guest adds an item, signs in
   through the fragment endpoint, and afterwards holds both items and is
   returned to the product page.
3. Run with `woocommerce_enable_guest_checkout` off as well, which is the
   configuration where a visitor meets the dialog involuntarily.

## Acceptance

- The rule fails when `do_action( 'wp_login', … )` is removed from
  `SessionIssuer` — verified by removing it, because a rule that has never
  failed is a comment
- Integration scenario reports `OK`, not `BLOCKED`
- Guest cart + saved cart both present after sign-in; the visitor is on the
  product page, not on my-account
- Every other suite at its previous count

## Not in scope

Resuming anything that is not a cart. Replaying an interrupted POST means
replaying a request the visitor did not re-authorise; that is a CSRF decision,
it needs its own spec, and the spec's deferral list says so.
