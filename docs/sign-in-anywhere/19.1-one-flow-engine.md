# 19.1 — One flow engine

Spec: [`../sign-in-anywhere.md`](../sign-in-anywhere.md), decision 2.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Turn rules 1 and 2 green. The identifier-first state machine currently
exists once, in `FormController`, on the HTML path only. Extract it so the popup
can drive the same code rather than a copy of it.

This is the sub-phase the phase stands on. Everything visible is downstream of
it, and building the dialog first would mean building it against an endpoint
that does not exist.

## Files

- `includes/Auth/class-flow-engine.php` — new
- `includes/Frontend/class-form-controller.php` — handlers delegate
- `includes/Frontend/class-rest-controller.php` — `identify` route added

## Steps

1. `FlowEngine` takes a step name and an input array and returns a **decision**:
   the next step, its data, and any notices. It performs no output, sets no
   cookies it does not already own, and issues no redirect. It is the thing both
   controllers ask.
2. The six handlers `FormController` owns — `identify`, `signup`, `verify_otp`,
   `resend_otp`, `login`, `forgot`, `reset_password` — move their decision bodies
   into it. `FormController::dispatch()` (`:63-124`) keeps the routing, the
   `RequestGuard` verification and the redirect; those are HTTP concerns and
   belong to a controller.
3. `POST smart-login/v1/identify` is registered, calling the same engine. This
   is the route finding 3 says is missing; it is added here rather than in the
   fragment sub-phase so the parity rule can go green against JSON before any
   HTML is involved.
4. **The guards stay where they are.** `RateLimiter::check_identify()` runs
   before the lookup for the reason `handle_identify()` already documents at
   `:113-116` — the lookup is the enumeration oracle, so a limit applied
   afterwards leaves the oracle intact. The engine must not reorder this.
5. `Captcha::check()` likewise keeps its position.

### The plan was wrong about where the guard goes

The brief said `RequestGuard::verify()` stays in the controller, "an HTTP
concern". Porting the handlers showed it is not one. `signup()` reacts to a
guard failure by re-rendering *with the unspent grant*, and `login()` picks its
failure step from `sl_from_password` — both are decisions about the flow. A
controller owning the guard would have had to own those too, which is the
duplication the sub-phase exists to remove.

So the guard moved into the engine, with a switch: `FlowEngine::for_rest()`
skips the HTML form verifier because `RestController::check_permission()` has
already run `verify_rest()`. Neither client goes unguarded, and the fragment
endpoint in 19.2 is deliberately on the *form* side of that switch — it posts
the fields of a real rendered form.

### Three suites went red, and all three were rules reading a moved body

This is the sixth time in this project a rename crossed a boundary, and the
second time a guard rail caught it in the same run rather than a phase later.

| Suite | Rule | Why |
| --- | --- | --- |
| Regression | `after_registration was located` | the wrapper was inlined into its two callers |
| Abuse boundary | `check_identify() before the lookup` | body moved to `FlowEngine::identify()` |
| Account surface | address refusal is reported | `save_onboarding()` moved, and now reports via the decision |

All three were **repointed, not relaxed**, and two came out stricter:

- the registration rule now reads **both** places a registration can finish
  rather than one wrapper the callers were trusted to use
- the address rule now accepts `->notice(` alongside `wc_add_notice()` and
  `Notices::flash()` — the same property through three transports

Counts: regression 332 → 337 (three checks became six), abuse 30 → 31 (a
subject-found assertion added), account surface unchanged at 10.

### Two of 19.0's own rules were wrong, and 19.1 is what exposed them

Both were false positives of the kind 19.0's preamble promises to design out,
and both were caught by this sub-phase's run:

- **Rule 1 went green for the wrong reason.** It matched `/'step'\s*=>/`, and
  19.1 added `array( 'step' => $decision->step )` to a response body. A rule
  reporting that a route exists because an array key is spelled the same way.
  Now reads the registered callback.
- **Rule 2 could not go green at all.** It looked for the literal `FlowEngine`
  in a handler body, which a delegating handler has no reason to name — it
  calls `$this->engine()`. Worse, a handler that *named* the class and then set
  its own step would have passed. Now two assertions: the handler asks the
  engine, and it contains no `Flow::set(` or `Notices::` of its own.

### What did not move

`save_profile` and `unlink_identity`. They are account-surface actions performed
by somebody already signed in, not steps of the sign-in flow. Drawing the line
at "is this a step of the flow" rather than "is this in this file" is what keeps
the engine's name honest.
