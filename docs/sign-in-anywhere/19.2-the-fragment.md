# 19.2 — The fragment

Spec: [`../sign-in-anywhere.md`](../sign-in-anywhere.md), decisions 1 and 2.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Turn rule 7 green. One endpoint that renders any step of the flow as
HTML, from the same templates the shortcode uses, with a fresh nonce every time.

## Files

- `includes/Frontend/class-fragment-renderer.php` — new
- `includes/Frontend/class-rest-controller.php` — `step` route
- `includes/Frontend/class-shortcodes.php` — `render_flow()` gains a render
  context; the shortcode path is unchanged

## Steps

1. `GET smart-login/v1/step?step=…&page=…&redirect_to=…` returns
   `{ step, html, title }`. `POST` to the same route runs a step through
   `FlowEngine` and returns the **next** fragment, or `{ redirect }` when the
   flow is finished.
2. **The renderer is given the host page explicitly.** `Flow::url()` computes
   step links with `remove_query_arg()` against the current request
   (`class-flow.php:125`), which inside a REST request is the API URL. A render
   context carries the host page URL, and `Flow::url()` reads it when set. Same
   for `redirect_to`, which `form-auth.php:30` reads from `$_GET`.
   `page` is passed through `wp_validate_redirect()` — it is request input that
   ends up in an `href`.
3. `Assets::enqueue()` is not called on this path. A REST request has no
   `wp_enqueue_scripts`, and calling it there is a silent no-op that looks like
   it works.
4. Notices ride in the fragment, not in a separate field: `partials/notices` is
   already inside every template and a second channel would be a second source
   of truth.
5. The captcha widget needs its provider script present *before* the fragment
   arrives. `Assets::register_assets()` registers `CAPTCHA_HANDLE` only when
   `Captcha::script_url()` is non-empty (`class-assets.php:80-84`); the launcher
   loads it alongside the main script on first open, so the fragment never
   contains a widget with no script.
6. Rendering `STEP_OTP` requires the `smart_login_flow` cookie; without it the
   endpoint returns the identify step rather than an OTP form with nothing behind
   it. `otp_args()` already handles the reload case (`class-shortcodes.php:238-270`)
   and is reused rather than reimplemented.

## Acceptance

- Rule 7 green
- A fragment fetched for a given host page contains that page's URL in
  `redirect_to` and in every step link; `/wp-json/` appears nowhere in it
- An `off-site` value for `page` is rejected, asserted directly
- Two fragments fetched a second apart carry **different** stamps and both verify
- The identify fragment fetched over REST is byte-identical to the shortcode's,
  once the host-page base is accounted for — the single-template contract Phase
  8.2 established
- Every other suite at its previous count

## Not in scope

The dialog, the trigger contract, the redirect policy. This sub-phase can be
exercised entirely with `curl`.
