# 19.5 — Finishing in place

Spec: [`../sign-in-anywhere.md`](../sign-in-anywhere.md), decision 3.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Turn rule 3 green. This is the sub-phase the request was actually
about: registering from a product page must finish on the product page, and
onboarding must happen there rather than in `wp-admin`.

## Files

- `includes/Auth/class-auth-context.php` — one fact
- `includes/Auth/class-post-auth-redirector.php` — the branch
- `includes/Frontend/class-fragment-renderer.php` — `onboard` over REST
- `templates/onboarding.php` — the two exits

## Steps

1. `AuthContext` gains `in_place` — whether this authentication is running
   inside a flow that owns its own surface. Set by the fragment endpoint, unset
   everywhere else. It is a fact about the request, which is what `AuthContext`
   is for; a global or a query parameter would be a second channel.
2. `PostAuthRedirector::redirect()` (`:28-34`) branches on it. The existing
   behaviour is untouched for every existing caller: a new user on the shortcode
   path still goes to `profile_url()` with `?smartlogin_welcome=1`. In place, the
   response carries `step: onboard` instead of a redirect.
3. `mark_seen()` keeps moving to where the welcome is actually shown, not to
   where it was decided — `Shortcodes::onboarding_args()` already makes that
   argument at `:212-216` and the popup path must not mark it earlier.
4. `onboarding.php`'s two exits both close the dialog and reload the host page.
   Reload, not a DOM patch: on a WooCommerce site the price, the cart fragment
   and most nonces on the page are role-dependent, and a popup that closes
   without one leaves a signed-in visitor looking at a signed-out page.
5. `email_missing` still points at the profile page (`:228-231`). Changing an
   email needs its own OTP round trip and that is not something this phase adds
   to a dialog.

## Acceptance

- Rule 3 green
- A registration driven through the fragment endpoint returns `step: onboard`
  and **no** redirect; the same registration through `FormController` still
  returns today's redirect, byte-identical
- On a site with WooCommerce **deactivated**, the in-place path never produces a
  `wp-admin` URL — the specific defect finding 1 names
- `has_seen()` is false until the onboarding fragment has actually been rendered
- Every other suite at its previous count

## Not in scope

Onboarding's field set, its copy, or `ProfileCompletionService`. What is
collected does not change; only where.
