# 19.12 — The picker the dialog never loaded

Spec: [`../sign-in-anywhere.md`](../sign-in-anywhere.md).
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Not in the plan.** Reported from the running site: on the welcome screen inside
the dialog, choosing a Tỉnh/Thành phố leaves Phường/Xã empty and disabled, with
the hint *"Chọn Tỉnh/Thành phố trước…"* still on screen underneath it. Third
defect in this phase found by looking at the rendered dialog rather than by a
rule, after 19.10 and 19.11.

**Goal.** A fragment may not need a script the dialog cannot load.

## What is actually broken

Not the REST route and not a query. `assets/js/address.js` never runs.

- `templates/onboarding.php:114` renders the picker through
  `AddressFields::render()`, which calls `Assets::enqueue_address()`
  (`class-address-fields.php:71`)
- on the dialog path that render happens **inside a REST request**, where there
  is no `wp_enqueue_scripts`. `Shortcodes::render_step()` already says so in
  writing (`class-shortcodes.php:160-163`) — the sentence was about
  `Assets::enqueue()` and the address handle inherited the same fate unnoticed
- the dialog's own asset list is four files, none of them `address.js`
  (`class-login-dialog.php:133-138`, `smart-login-launcher.js:92-99`)
- and `Assets::maybe_enqueue()` cannot cover it: it needs `is_singular()` **and**
  a shortcode in `post_content` (`class-assets.php:32-49`), which is the exact
  gate 19.4 rejected for the launcher

So the two `<select>` elements stay raw, the ward one stays `disabled` with a
single empty option, and the hint stays visible — `address.js:372-378` is what
removes it.

**A second defect sits behind the first.** `address.js` initialises on
`DOMContentLoaded` (`address.js:492-496`) and exports nothing. The dialog's
fragment arrives long after that, and `paint()` hands it only to
`window.SmartLoginEnhance` (`smart-login-dialog.js:59`) — the hook 19.3 created
for precisely this class of problem, which `address.js` never joined. Loading the
file would not have been enough.

Page-hosted onboarding is unaffected: there the enqueue happens during a real
page render and WordPress prints the script in the footer.

## Decision: loaded on demand, not added to the bundle

`address.js` joins the dialog as a **third-stage** asset — fetched when a painted
fragment actually contains `[data-sl-address]`, which today is the welcome screen
and nothing else. Adding it to the first-open bundle would put the whole picker
on every identify and OTP open that has no address field in it, and declining
that cost in writing is what `class-login-dialog.php:6-11` already does for the
dialog itself. The loader it needs is the one 19.4 wrote.

Its configuration travels the same way. `SmartLoginAddress` is localized onto a
handle that is never enqueued here, so `restUrl` and the i18n strings are absent
too — the config becomes `Assets::address_config()` and both the localize call
and `LoginDialog::contract()` read that one array. Two builders for one config is
rule 9's defect wearing different clothes.

## Files

- `tests/identity/run-sign-in-anywhere-tests.php` — rule 16
- `includes/Frontend/class-assets.php` — `address_config()`
- `includes/Frontend/class-login-dialog.php` — the contract carries it
- `assets/js/address.js` — expose the enhancement hook
- `assets/js/smart-login-dialog.js` — load on demand, then enhance

## Steps

1. **The rule first, landed red.** Render the welcome fragment and assert the
   dialog can enhance what came out.
2. `Assets::address_config()`, read by both callers.
3. `window.SmartLoginAddressEnhance( scope )` in `address.js`, same shape as
   `SmartLoginEnhance` — `initAll()` becomes scope-aware and the Woo half stays
   document-only.
4. `paint()` loads the script when the fragment needs it, once, then calls every
   hook.

## Acceptance

- Rule 16 fails before step 2 and passes after step 4, with both outputs recorded
- The rule is not satisfied by a filename appearing in a string: it renders the
  fragment, and it walks every `window.SmartLogin*Enhance` the plugin exposes and
  requires the dialog to call each one — so a hook added later and left unwired
  fails it
- On the running site: open the welcome screen in the dialog, choose Tỉnh/Thành
  phố, and the ward list fills, the hint disappears, and both fields become
  searchable comboboxes
- No identify-step open downloads `address.js`
- Every other suite at its previous count (sign-in anywhere was 51/0/0)

## Not in scope

Moving the address picker out of onboarding, changing the dataset, or the
`address.quick_search` setting. The picker is correct; nothing was loading it.

### What the plan got wrong

**The gate's first ward check asked for province `79`.** That is Hồ Chí Minh's
official code and not one this dataset uses — the merged dataset numbers
provinces `11`–`44`. The route answered `200` with an empty list and the check
read as a broken endpoint. It now takes the first code from
`AddressRepository::provinces()`: a rule carrying its own copy of the data stops
testing the data. Worth recording because the same mistake, made in production
code rather than in a check, is exactly the bug this sub-phase was reported for.

**Two stub gaps, not one.** Reading `LoginDialog::contract()` as an array needed
`rest_url()` and `SMART_LOGIN_URL`, neither of which the unit stubs had — no rule
had ever inspected the contract's values before, only `captured_urls()`. Added,
so rule 16 compares real arrays instead of grepping a file for a filename.

**`initAll` was being handed events.** Making it scope-aware turned two existing
call sites into bugs: `DOMContentLoaded` and jQuery's `updated_checkout` both
pass an event as the first argument, which would have arrived as the container to
search. Both are wrapped now. Caught by reading the call sites while changing the
signature — no rule would have.

Mid-implementation, `Regression (pure logic)` failed two checks about

reproduced against the untouched tree (`git stash` → 335 passed, 2 failed), so

It is neither now: `3653fb0 A rule that outlived the shape it was describing`

progress, and *two runs are not a comparison* was the rule that caught it. The
count changed as well as the result — 335 checks to 342 — which is what a
rewritten rule looks like and what a flaky one does not.
