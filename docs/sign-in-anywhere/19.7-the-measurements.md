# 19.7 — The measurements

Spec: [`../sign-in-anywhere.md`](../sign-in-anywhere.md), "What this phase does
not claim".
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Take the readings, promote the suite, and write down what the plan got
wrong. Phase 18 exists because three phases in a row wrote acceptance that said
*measured* and then did not measure. This one has the tool.

## Files

- `tests/visual/render.php` — one surface: the dialog
- `tests/visual/README.md` — the readings, as commands
- `tests/integration/` — the round trip
- `tests/run-all.php` — promote to `required`

## Steps

1. Add the dialog as a surface to the renderer 18.1 committed, so the shell can
   be opened from anywhere without a WordPress.
2. Take the readings at **375, 480 and 1400**: no horizontal overflow, the
   backdrop covers the viewport, the panel is reachable by scroll when the
   content is taller than the screen, and the close control clears WCAG 2.2 AA's
   24 × 24 floor — the measurement 18.3 had to make twice because the prediction
   from the source was wrong in magnitude *and* direction.
3. Keyboard walk: `Tab` from the trigger enters the dialog, cycles inside it,
   `Esc` closes, focus returns to the trigger. Recorded as a control count and
   an order, not as a tick.
4. `tests/integration/`: launcher enqueued on an archive (finding 7), fragment
   fetched over a real REST request, a full registration finishing in place, and
   the provider return from 19.6.
5. Promote `run-sign-in-anywhere-tests.php` to `required`. A green suite left
   non-blocking can only hide the next regression — the argument Phase 5 made
   and 15.4 found being ignored for four phases.
6. Restate the **coding-standards baseline** as a number. It was `18 ERRORS AND
   20 WARNINGS ... IN 16 FILES`; a baseline nobody restates has stopped meaning
   anything.

## Acceptance

- Readings recorded as numbers in the `## Outcome` section, not as ticks
- Integration gate reports `OK`, not `BLOCKED`
- Suite `required` and green
- Baseline stated either way, including if it moved
- An `## Outcome` section in every brief of this phase: what happened, what the
  plan got wrong, what turned up along the way

## Not in scope

Automating the browser. 18.1 declined that in writing and the README is what
replaces it; this sub-phase adds readings to that protocol, not a second
toolchain.

### The gate reports OK, not BLOCKED

Run against the Local install with WooCommerce active, which is the item Phase
18's spec says three phases in a row wrote and did not deliver:

```text
PASS  the fragment endpoint is a real REST url  (http://localhost:10004/wp-json/omniwp/v1/step)
PASS  the step allowlist arrives from PHP  (identify,login,register,otp,forgot,reset)
PASS  every alias resolves to an allowed step
PASS  capture names at least one url the plugin can resolve
        (http://localhost:10004/wp-login.php  http://localhost:10004/my-account/)
PASS  the fragment route answers 200
PASS  the fragment carries markup  (2773 bytes)
PASS  the fragment carries a fresh nonce
PASS  the fragment does not link into the API
PASS  the fragment returns the visitor to the host page
PASS  an off-site host page is refused
PASS  a signed-out visitor cannot request the welcome screen  (identify)
PASS  the dialog-open variant is noindex
PASS  an ordinary page is not
PASS  WooCommerce still hangs its cart merge on wp_login
PASS  the session issuer fires wp_login
```

Getting there needed `mysqli`, `openssl`, `sodium` and `mbstring` in the CLI —
none of which the PHP on this machine loads by default. That is worth writing
down: without them five suites fail for reasons that have nothing to do with the
code, which is a very convincing way to be wrong.

Input and submit measure 47px, matching 18.4's reading for the same controls on

### The first run measured the wrong thing, and it looked like a defect

The surface came out unstyled: close control **24 × 21**, backdrop
`rgba(0, 0, 0, 0.1)`. Read as a product defect that would have been fixed by
editing CSS that was already correct.

The cause was the tool: it inlined only `omniwp.css`, and the dialog ships
its own stylesheet *because* of the two-stage asset load — the shell has to be
styled before the fragment arrives. Phase 18 exists because measurements were
claimed and not taken; this is the adjacent failure, a measurement taken against
the wrong thing, and it is now a paragraph in the protocol.

### The coding-standards baseline was stale, and this is the note that says so

`--strict` still refuses this tree, and the number moved — **down**.

| | errors | warnings | files |
| --- | --- | --- | --- |
| documented in `refactor-plan.md` | 18 | 20 | 16 |
| `main`, re-measured here with a cleared cache | 23 | 25 | 19 |
| this branch | **21** | **20** | **16** |

The documented figure does not match what `main` actually produces in this
environment. Recording both is the point: *"compare, do not assume"* is
worthless if the thing being compared against was written down once and never
re-taken.

**And two runs are not a comparison.** The first attempt reported `main` at
23/25/19 and the branch at 21/20/16 — but `.phpcs-cache` was serving results
from the previous tree. The table above was taken with the cache deleted between
runs. This project's own rule caught it: *if a result alternates, isolate it
before concluding anything.*

### Suite promoted

`spec` → `required`. Three of its rules had to be rewritten from a structural
form to a behavioural one during the phase, and a suite that can no longer block
would hide the next regression in exactly those three.
