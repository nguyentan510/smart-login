# 19.8 — Capturing the links that exist

Spec: [`../sign-in-anywhere.md`](../sign-in-anywhere.md), decision 8.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** The theme's own "Đăng nhập" button opens the dialog, on a site where
nobody edited a single template.

Every trigger in 19.4 requires markup to be edited. This is the one that does
not, and it is therefore the sub-phase that decides whether the feature is
received by most installs or by the ones with a developer.

## Files

- `assets/js/omniwp-launcher.js`
- `includes/Frontend/class-login-dialog.php` — the captured URL list, localized
- `README.md` — the filter and the opt-out attribute

## Steps

1. PHP resolves the list; JS only matches against it. The URLs the plugin can
   name without guessing:
   - `Flow::login_url()` — the page hosting the shortcode
   - `wp_login_url()`
   - WooCommerce's my-account permalink — the surface this plugin already
     replaces at `class-woo-integration.php:77`
   `OMNIWP_capture_links` filters the list, and returning `array()` is the
   off switch.
2. **Click interception only. `href` is never touched.** With the script
   blocked, removed, or simply not loaded yet, every captured link is the
   ordinary link the theme wrote. There is no state in which this sub-phase can
   strand a visitor — which is the entire reason it is allowed to default on.
3. Four refusals, structural rather than heuristic:
   - the visitor is signed in
   - the URL is `wp-login.php` carrying an `action` — `logout`, `postpass`,
     `resetpass` are not sign-in and must reach the real screen
   - the element or an ancestor carries `data-no-omniwp`
   - the click is modified (middle, ⌘, ctrl, shift) — opening a new tab is the
     visitor asking for the page, not the dialog
4. A captured link's own `redirect_to`, when it has one, becomes the dialog's.
   A link that says "sign in and come back to the cart" must keep meaning that.
5. Comparison is on the resolved absolute URL, path-normalised. A string match
   on `href` would miss a relative link and would fire on a query string that
   merely mentions the path.

## Acceptance

- The theme's login link opens the dialog with **no markup change**, measured on
  a stock theme
- **No `a[href]` in the document differs before and after the launcher runs** —
  asserted over the DOM, because this is the property the whole safety argument
  rests on
- Each of the four refusals asserted separately; `wp-login.php?action=logout`
  specifically, because capturing it would trap somebody trying to leave
- `OMNIWP_capture_links` returning `array()` restores today's behaviour
  exactly
- Signed in: nothing captured
- Every other suite at its previous count

## Not in scope

Guessing. A link is captured because the plugin can name its URL, never because
its text says "Đăng nhập" — a heuristic over link text would fire on an article
about signing in.

### The safety argument is split across two rules on purpose

Capture defaults on, and that is only defensible because of two separate
properties, each with its own rule:

- **rule 10** — the launcher never assigns to `href`, so a blocked script leaves
  every captured link exactly as its author wrote it
- **rule 13** — the list is *named* in PHP rather than guessed in JavaScript, and
  the filter returning `array()` restores today's behaviour exactly

Neither alone is enough. A named list that rewrote `href` would still strand
somebody; an intercepted click matched by a guess would still claim links the
plugin does not own.

### The comparison is on resolved URLs, not on the attribute

`link.href` is absolute by the time the DOM hands it over, so origin and
normalised path are cheap to compare. A string match on the `href` *attribute*
would miss `/my-account/` written relatively and would fire on any URL that
merely mentions the path.

### A missing stub read as a missing feature

`captured_urls()` came back empty in-process and the rule failed. Nothing was
wrong with the code: `wp_login_url()` had no stub, and `Flow::login_url()`
answers `''` when no page hosts the shortcode, so all three sources were empty.

That is worth writing down rather than fixing quietly, because the failure mode
is the dangerous one — an empty list reads as *"capture is off"* rather than
*"the stub is missing"*, and a rule that cannot tell those apart is the kind
that gets believed. The stub is now there, and the rule asserts the default list
is non-empty precisely so this cannot be mistaken again.

### What was declined

Matching on link text. `textContent` appears nowhere in the launcher, and rule
13 asserts it: a heuristic over "Đăng nhập" fires on an article about signing
in, and the links a guess would catch are worth less than the property of never
claiming one the plugin cannot name.
