# 19.6 — The provider round trip

Spec: [`../sign-in-anywhere.md`](../sign-in-anywhere.md), decision 6.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** "Tiếp tục với Google" from a product page returns to the product page
— and, for a new account, returns with the popup already open at onboarding.

Sequenced after 19.5 because the return lands in the redirect policy that
sub-phase writes. Shipping it first would mean routing a provider signup at a
destination that does not exist yet.

## Files

- `templates/form-auth.php` — the return url
- `includes/Auth/class-provider-auth-controller.php` — the marker on return
- `assets/js/omniwp-launcher.js` — re-open on the marker

## Steps

1. `form-auth.php:127` calls `ProviderAuthController::start_url( id, $ow_redirect )`
   and `$ow_redirect` comes from `$_GET['redirect_to']` (`:30`) — empty for a
   popup on a product page. In a fragment render it comes from the render
   context 19.2 introduced, so the return url is the host page.
2. `start_url()` already passes it through `wp_validate_redirect()` (`:47`) and
   `start()` re-validates (`:99-101`). Nothing about that changes; the value is
   simply no longer empty.
3. On return, a **new** account gets the flow marker appended to the host page
   URL rather than a redirect to the profile page — the same in-place decision
   19.5 made, reached through the provider path instead of the OTP one.
4. The launcher reads that marker on load, opens the dialog at `onboard`, and
   strips it with `replaceState` so a reload does not reopen the welcome screen.
5. An existing account returns to the host page signed in, with no dialog.

## Acceptance

- A provider login started from a fragment rendered for page *P* has *P* in its
  transaction return url — asserted on the stored transaction, not on the link
- An off-site `page` still resolves to `''`, unchanged
- A new provider account returns to *P* with the marker; an existing one returns
  to *P* without it
- The marker survives exactly one load
- Run against a real WordPress through `tests/integration/` — a provider
  round trip is the shape of thing four gates once missed a fatal in
- Every other suite at its previous count

## Not in scope

`window.open` and `postMessage`. Declined in the spec with its reasons; the
full-page redirect is the decision.

### Half of this sub-phase had already shipped in 19.2

Step 1 — the return url being the host page — was done the moment
`templates/form-auth.php` stopped reading `$_GET['redirect_to']` and started
asking `Flow::redirect_to()`. The provider link takes the same value it always
took; what changed is that the value is no longer empty for a fragment.

### The interface was the constraint, and it decided the design

The obvious way to carry "a dialog started this" is a parameter on
`LoginProviderInterface::begin()` and a column on the transaction. That
interface is implemented by third-party providers through
`OMNIWP_providers`, and widening it would break every one of them for a
fact only this controller reads.

So the marker rides on the return url — `ow_place=1`, added by `start_url()`
and stripped by `callback()` before the url is used for anything. One controller
writes it, the same controller reads it, and nothing else has to know it exists.

### The reopen flag is `OmniWP_welcome`, deliberately

Not a marker of this phase's own. `PostAuthRedirector` has always written that
flag for a finished registration and `Shortcodes::is_welcome_request()` has
always read it, so a second spelling would be two names for "this member has
just registered". Rule 9's argument, applied to a URL instead of a script — and
rule 12 asserts it, because this is exactly the shape of the rename that has
crossed an untested boundary six times in this project.

### Two collisions that only appear when both surfaces answer the same flag

Both found by reasoning about the flag rather than by a failing test, and both
would have been visible immediately in a browser:

- **The launcher was not on the page.** `LoginDialog::enabled()` returned
  `! is_user_logged_in()`, and a member returning from Google is signed in *and*
  still owed a welcome screen. It now also returns true for a welcome request.
- **Two welcome screens.** A page hosting `[OMNIWP]` draws onboarding from
  the same flag. The template carries `data-sl-onboarding`, and the launcher
  skips the dialog when it finds one — otherwise the visitor is asked the same
  questions twice, once in a dialog and once behind it.

### `onboard` is reachable by request now, and checked because of it

The launcher opens a step that is deliberately absent from
`Flow::PUBLIC_STEPS`, because a round trip through a provider cannot carry a
decision home. `FragmentRenderer` therefore refuses it for anybody not signed
in and falls back to the identify step — the exact protection the allowlist was
providing before, moved to where the exception is.
