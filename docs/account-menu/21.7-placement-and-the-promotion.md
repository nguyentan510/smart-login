# 21.7 — Placement, the documentation, and the promotion

Spec: [`../account-menu.md`](../account-menu.md), decision 11.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** A site with a classic theme can put the button in its header without
editing a template. Then the phase closes: the contract is written down, and the
suite stops being allowed to fail.

## Files

- `includes/class-field-registry.php` — one field row
- `includes/Frontend/class-nav-menu-item.php` — new
- `README.md` — the shortcode, the filters, the tokens
- `tests/run-all.php` — `spec` → `required`

## Steps

1. `account_menu.nav_location` — `type => 'select'`, choices built from
   `get_registered_nav_menus()` plus an empty first option, `default => ''`.
   **Off by default**: spec decision 11, and the reason it differs from Phase
   19's capture is written there.
2. A theme that registers no locations gets the row with only the empty option
   and a sentence saying so. A select with nothing in it is a control that looks
   broken when it is merely inapplicable.
3. Inject through `wp_nav_menu_items`, filtering on the chosen location only.
   The item is wrapped in a single `<li class="menu-item sl-account-item">` — the
   filter's contract is a string of `<li>`, and returning anything else breaks
   the theme's own markup.
4. **The same renderer as the shortcode.** `Shortcodes::render_button()` produces
   the markup; this class wraps it. Two entry points with two markups is the
   drift this phase exists to prevent, applied to placement.
5. A stored location that the theme no longer registers injects nothing, and does
   not warn. Themes get switched, and a stale option is not an error condition.
6. `README.md`: the shortcode and its attributes, `smart_login_account_menu`,
   the `IconSet` names, the `--sl-*` tokens and how to override one. The tokens
   are the answer the refused colour picker points at, and an answer that is not
   documented is not an answer.
7. ~~Promote the suite to `required`.~~ **Already done, in 21.5.** Every rule
   went green when the button landed, and the working agreement promotes a
   `spec` suite the moment that happens rather than at a scheduled point. Holding
   it here for two more sub-phases would have been 15.4's mistake with a shorter
   fuse. What remains for this sub-phase is that the suite must still be
   `required` and green when the phase closes.

## Acceptance

- **Integration gate:** with a location selected, the rendered menu contains
  exactly one `.sl-account-item`, and it is a direct child of the `<ul>` — a real
  WordPress and a real theme, because `wp_nav_menu_items` fires inside markup no
  fixture reproduces
- **Integration gate:** with no location selected, no theme menu changes at all
- Selecting a location, then switching to a theme without it, injects nothing and
  logs nothing
- The markup injected into the menu and the markup the shortcode renders are the
  same string, asserted by comparing them rather than by inspection
- `README.md` documents every public name this phase added — asserted against the
  filters and shortcode attributes actually registered, not by reading
- **Every rule from 21.0 green**, and the suite row reads `required`
- Full `php tests/run-all.php` output pasted into the brief's Outcome

## Not in scope

Widgets and block-editor blocks. `wp_nav_menu_items` covers the classic-theme
case the shortcode cannot reach; a block is a third placement surface and it
needs the same "one renderer" argument made again, with block.json and an editor
script behind it.
