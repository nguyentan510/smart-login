# 21.5 — The button, two states

Spec: [`../account-menu.md`](../account-menu.md), decisions 1, 7, 8.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Turn rules 10, 11 and 12 green. `[smart_login_button]` renders as a
button, knows who is looking at it, and works with the script blocked.

This is the sub-phase that fixes finding 1: the trigger built for people who
cannot edit templates has never had a stylesheet.

## Files

- `includes/Frontend/class-shortcodes.php` — `render_button()` rewritten
- `includes/Frontend/class-assets.php` — register the stylesheet, and add the
  shortcode to `maybe_enqueue()`'s tag list
- `assets/css/smart-login-button.css` — new
- `templates/account-button.php` — new
- `tests/integration/run-account-menu-gate.php` — its first rules

## Steps

1. `render_button()` branches on `is_user_logged_in()` and renders through
   `TemplateLoader`, not `sprintf()`. A template is what a theme can override,
   and every other surface in this plugin is already overridable.
2. **Signed out** — an `<a>` whose `href` is the real sign-in page, carrying
   `data-smart-login`, exactly as today (`class-shortcodes.php:63-69`). The
   `href` is not touched by anything, for the reason 19.4 wrote down.
   Default label `Đăng nhập`.
3. **Signed in** — `<details class="sl-account">` with a `<summary>` carrying the
   label from `account_menu.label_source`, and the `AccountMenu` list inside.
   No `data-smart-login` anywhere in this branch: rule 10.
4. `auto` resolves to `UserManager::META_PHONE` when set, else `display_name`.
   Never the email: spec decision 12.
5. Markup carries `.sl-account-btn`, and **no `sl-btn`** — rule 11, spec
   decision 7. The stylesheet makes it `inline-flex`, so it is the size of its
   contents wherever it is put.
6. `smart-login-button.css` declares `smart-login-tokens` as its dependency and
   restates no colour. It is registered and enqueued whenever the shortcode
   renders, and `smart_login_button` joins the tag list in
   `Assets::maybe_enqueue()` (`class-assets.php:43`) so the stylesheet is in the
   head rather than the footer — the flash of unstyled form that comment already
   describes, applied to a button in a header where it is more visible.
7. The logout entry gets a separator above it, in CSS. It is a design constant,
   not a setting, and it is how the reference reads.
8. No JavaScript in this sub-phase. `<details>` opens and closes on its own.

## Acceptance

- Rules 10, 11, 12 green
- Rendered signed-out markup contains `data-smart-login` and no `<details>`;
  rendered signed-in markup contains `<details>` and no `data-smart-login`
- The signed-in `<summary>` shows the phone for a member who has one and the
  display name for one who does not, asserted with both fixtures
- A member with a synthetic email never sees that address in the button
- **Integration gate:** a page hosting only `[smart_login_button]` has the button
  stylesheet in its enqueued styles, and does not have `smart-login.css`. This is
  finding 1's rule and it is measured in a real WordPress, because an enqueue is
  the class of defect a fixture reports as fine
- **Integration gate:** the token stylesheet is enqueued ahead of the button's
- Every other suite at its previous count

## Not in scope

Outside-click, `Escape`, `aria-expanded`, and the mobile sheet — 21.6. The
dropdown must be demonstrably useful with no script before any script is added,
or decision 8 is a claim nobody checked.
