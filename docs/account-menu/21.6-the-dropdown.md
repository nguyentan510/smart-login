# 21.6 — The dropdown, and the small screen

Spec: [`../account-menu.md`](../account-menu.md), decisions 8, 9.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** The menu behaves the way a menu is expected to — closes when you click
away, closes on `Escape`, announces its state — and reads correctly at 375px.
Everything here is an **upgrade** to something that already worked in 21.5.

## Files

- `assets/js/omniwp-account.js` — new, small
- `assets/css/omniwp-button.css` — the responsive half
- `includes/Frontend/class-assets.php` — enqueue alongside the stylesheet

## Steps

1. One delegated listener on `document`, matching the launcher's shape
   (`omniwp-launcher.js:137`): markup added after load works too, and there
   is one listener rather than one per button.
2. Outside click closes; `Escape` closes and returns focus to the `<summary>`.
3. `aria-expanded` is kept in step with the `toggle` event. `<details>` does not
   maintain it, and a screen reader reading a collapsed menu as expanded is worse
   than one reading nothing.
4. The script **adds behaviour and removes none**. No `preventDefault` on the
   summary, no `open` attribute management beyond what the element does. If the
   file fails to load, 21.5's behaviour is what remains — that is the whole
   argument for the ordering of these two sub-phases.
5. Responsive, in CSS, over the same DOM (decision 9):
   - below the breakpoint the panel is full-width and anchored to the viewport
     edge rather than to the button, so a button near the right edge does not
     open a panel off-screen
   - `collapse="mobile"` hides the text label and leaves the icon, with the
     accessible name preserved — an icon-only control still has to say what it is
   - hit target at least 44×44 on touch
6. ~~The breakpoint is a custom property in the token file.~~ **Not possible** —
   a custom property cannot appear in a media query condition, so
   `@media (max-width: var(--x))` is invalid and the whole rule is dropped. The
   breakpoint is `782px`, written once, and a theme moves it by re-declaring
   those rules at its own width. Still not a setting: spec's refused list, whose
   replacement column is corrected in the same commit.

## Acceptance

Measurements, taken and recorded, not reasoned about:

- Click outside closes; `Escape` closes and focus is on the `<summary>`
- `aria-expanded` matches the `open` attribute after each of: click, `Escape`,
  outside click
- Tab order through the open menu is the visual order, and leaving the last item
  does not trap
- With `omniwp-account.js` blocked, the menu still opens and closes — 21.5's
  acceptance re-run with the script removed, which is the only way decision 8 is
  a fact rather than a claim
- At 375px: the panel is fully on-screen with the button at the right edge, no
  horizontal scroll appears on the document, and the hit target measures ≥44px
- At 1280px: the panel is anchored to the button's right edge
- Every other suite at its previous count

## Not in scope

A focus trap. The menu is not a modal — `Escape` and outside-click are the exits,
and trapping focus in a navigation dropdown is a behaviour visitors do not expect
from one. The dialog is where a trap belongs, and it already has one.

### The 44px floor was missing on the axis nobody checks

At 375px with the label collapsed the button measured **43.60 x 44.00**. An 18px
icon plus 12px padding either side plus two borders lands just under the touch
target, and only the height had a floor to catch it — `min-height: 44px` looks
deliberate enough that the width never gets questioned.

0.4px is still a miss. `min-width: 44px` and `justify-content: center` now hold
both axes, re-measured at 44.00 x 44.00.

This is the one thing in the sub-phase that reading the CSS would not have
found, and it is the reason the acceptance was written as readings.

### Decision 8 is now a fact rather than a claim

The same page built twice, once with the script inlined and once with nothing.
On the scriptless copy `document.querySelectorAll('script').length` is `0` and
`aria-expanded` is `null` — so the file genuinely is not running — and the menu
still opens, shows all three destinations, and closes.

21.5 shipping the markup a sub-phase before this script existed is what made
that measurable. Had both landed together, "it works without JavaScript" would
have been an assertion about a state that never existed.

### A correction to an approved decision

The spec's refused-settings table said the replacement for a breakpoint setting
was "a CSS variable the theme sets", and step 6 of this brief repeated it.
**That is not possible.** A custom property cannot appear in a media query
condition; `@media (max-width: var(--x))` is invalid and the browser drops the
whole rule. A variable there would have looked like a knob, changed nothing when
turned, and failed silently — worse than no knob.

The refusal itself stands and its reason is unchanged. The breakpoint is 782px,
written once, and a theme moves it by re-declaring those two rules at its own
width. Corrected in `account-menu.md` in the same commit rather than fixed
quietly, because it was approved.

### `toggle` is asynchronous, which nearly produced a false bug report

The first measurement read `aria-expanded` immediately after `.click()` and got
`"false"` while `open` was already `true`. That is not a defect in the script —
`toggle` is queued rather than dispatched synchronously, so the measurement was
reading before the handler had run. Every reading above waits a tick.

Worth recording: the same shape of mistake, read as a real finding, would have
produced a "fix" for a bug that was not there.
