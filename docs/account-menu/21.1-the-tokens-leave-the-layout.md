# 21.1 — The tokens leave the layout

Spec: [`../account-menu.md`](../account-menu.md), decision 13.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Turn rule 1 green. The design tokens become a thing any surface can
read; `.omniwp` keeps only the layout it is actually describing.

**This goes first, and alone.** Every later sub-phase needs a colour, and the
alternative — a second stylesheet with its own copy of `#e30613` — is two reds
that were meant to be one.

## Files

- `assets/css/omniwp-tokens.css` — new
- `assets/css/omniwp.css` — the token block leaves, the layout stays
- `assets/css/omniwp-dialog.css` — declares the dependency
- `includes/Frontend/class-assets.php` — register the handle, make it a dep
- `includes/Frontend/class-login-dialog.php` — the lazy path loads it first

## Steps

1. Move the twenty custom properties out of the `.omniwp` rule
   (`omniwp.css:6-66`) into the new file, declared on `:root`. **No value
   changes.** Same hexes, same pixel counts, same names.
2. `max-width: 460px`, `margin: 0 auto`, `padding: 8px 0 32px`, `color`,
   `font-size`, `line-height` and `box-sizing` **stay** on `.omniwp`. They
   are the page-layout block, and they are what the header button must not
   inherit.
3. Register the new handle in `Assets::register_assets()` and make it a
   dependency of `Assets::HANDLE`, so no caller has to remember it.
4. The launcher's lazy path loads stylesheets by URL rather than by handle
   (`class-login-dialog.php:133-137`), so it gets an explicit third entry, loaded
   **before** the two that depend on it.
5. Do not change how any theme overrides anything. A theme setting
   `.omniwp { --sl-accent: … }` outranks `:root` on specificity, so today's
   overrides keep winning without a compatibility shim.

## Acceptance

- Rule 1 green
- **The rendered-surface baseline does not move.** Its pinned count of off-scale
  declarations (`omniwp.css:36-40`) is identical before and after, and the
  suite is run on both sides of the commit with both outputs in the message
- Every `var(--sl-*)` in both stylesheets still resolves — asserted by there
  being no custom property referenced that the token file does not declare
- A page loading only `omniwp-dialog.css` still resolves its tokens
- Every other suite at its previous count

## Not in scope

Renaming a token, adding one, or converting any of the 40 off-scale declarations.
This commit moves a block between selectors. A diff that also changes a value
cannot be reviewed as "nothing should look different", which is the only claim
that makes a change with this reach safe.

### The account-card suite caught the rename, which is the system working

Five assertions went red the moment the tokens left `.omniwp`:
`the scale declares --sl-space-1`, and four like it. They read
`assets/css/omniwp.css` and asked whether the token was declared there.

CLAUDE.md's warning is that a rename crosses every boundary no test covers. This
one crossed a boundary a test *did* cover, and the suite said so within a minute
of the change — 41 passed became 36 passed, 5 failed.

**The property those rules assert has not changed**: a token used but never
declared resolves to nothing and the declaration silently drops. Only where the
declaration lives has. So they now read the token file, and the rest of that
suite keeps reading the stylesheet it was written against. This is not a rule
narrowed to make a change pass; it is a rule whose subject moved.

### `--sl-dlg-*` stays where it is, and rule 1 got sharper for saying so

`omniwp-dialog.css` declares eight variables on `.sl-dialog`. Rule 1's first
phrasing — "no `--sl-*` declaration outside the token file" — would have swept
them into a global file.

Checking rather than assuming settled it: the dialog stylesheet references
**only** its own `--sl-dlg-*` and no shared token, and `<dialog class="sl-dialog">`
is not inside `.omniwp`. So the eight never cross a stylesheet boundary, and
promoting them to global names would be the opposite of the scoping this plugin
keeps.

Rule 1 is now three assertions and the middle one is the sharp version: **a token
a stylesheet reads without declaring must come from the token file.** That is the
property decision 13 needs, and it still failed loudly before the file existed.

### Two consumers the brief did not list

- `tests/visual/render.php:221` inlines the stylesheet into a standalone HTML
  file, and there is no dependency graph there to resolve a registered handle.
  Without the token file added, every picture it produces would have had every
  colour, space and font size unresolved — and it would have looked like a CSS
  defect rather than a missing include. Smoke-tested after the change: the output
  carries `:root`, `--sl-accent: #e30613` and `--sl-space-3: 12px`.
- The launcher injects `<link>` elements by URL for the same reason, so the
  contract gained `tokensCss` and the array loads it first.

### One self-inflicted false red

The new assertion `.omniwp declares no design token of its own` failed
against a file that was already correct: the pattern stopped at `--sl-` and
matched `color: var(--sl-text)` *inside the rule it was checking*. A declaration
is `--sl-x:` and a reference is `--sl-x)`; the colon is the whole difference.
