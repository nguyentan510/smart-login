# 21.3 — The registry

Spec: [`../account-menu.md`](../account-menu.md), decisions 2, 3, 4, 5.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Turn rules 4–9 green. One list of account destinations exists, it is
useful before anybody configures anything, and no second one can appear without
failing a rule.

## Files

- `includes/Frontend/class-account-menu.php` — new
- `includes/class-plugin.php` — wiring, if the class needs registering

## Steps

1. `AccountMenu::items( int $user_id = 0 ): array` returns a list of
   `array{ key: string, label: string, icon: string, url: string }`. Four keys.
   The icon value is an `IconSet` **name**, not markup — markup is the renderer's
   job, and an array carrying SVG is an array nobody can compare in a test.
2. Assembly order, and it is the whole design:
   1. the pinned head — `account`, label `Thông tin cá nhân`, icon `user`, URL
      from `AccountForm::edit_url()` (`class-account-form.php:363`)
   2. the configured middle — read from settings, which do not exist until 21.4;
      until then this reads an empty list and the pinned pair is the whole menu
   3. the pinned tail — `logout`, label `Đăng xuất`, icon `log-out`, URL from
      `wp_logout_url( home_url( '/' ) )`
3. Then, **last**, `apply_filters( 'OMNIWP_account_menu', $items, $user_id )`
   — over the assembled array, so a developer can remove a pinned end. Running
   last is what makes it one escape hatch instead of a second configuration
   surface.
4. Re-validate after the filter: drop entries missing a `key`, `label` or `url`,
   drop keys that do not match `[a-z0-9_-]+`, and resolve an unknown icon through
   `IconSet`'s fallback. A filter is not a reason to stop checking.
5. An entry whose URL resolves to `''` is dropped, not rendered dead.
   `AccountForm::edit_url()` returns `''` on a site with no account page, and a
   menu item that goes nowhere is worse than one that is absent.
6. `AccountMenu` does not call `sections_meta()`, does not import `AccountForm`
   for anything but `edit_url()`, and does not know what a section is.

## Acceptance

- Rules 4, 5, 6, 7, 8, 9 green
- With the option cleared, `items()` returns exactly the two pinned entries, both
  with non-empty URLs on a site that has an account page
- On a site with **no** account page, `items()` returns `logout` alone — asserted,
  because it is the branch step 5 exists for
- A filter adding `array( 'key' => 'Bad Key!', … )` yields a list that does not
  contain it; a filter adding a five-key entry fails rule 6
- The logout entry's URL differs between two users, which is what proves it came
  from `wp_logout_url()` and not from a stored string
- Every other suite at its previous count

## Not in scope

Any surface that renders the list. The registry lands with no consumer for one
commit; 21.5 is the commit that proves it. Also out: `capability`, `badge`,
`children` — spec decision 5, and rule 6 is what enforces it.

### Rule 4 failed against a class that was obeying it

`AccountMenu never calls sections_meta()` was a substring search, and the class
explains at length *why* it must not make that call. The rule was punishing the
documentation of its own intent.

Comments are stripped before the search now. Third time in three sub-phases that
a rule matched a construct's spelling rather than the construct — after the
`--sl-` pattern catching `var(--sl-text)` in 21.1, and the empty-render false
green in 21.0. The pattern is consistent enough to be worth naming: **a rule
about code should read code, not text that mentions code.**

### Rule 6 is now guaranteed rather than asserted, and that is an improvement

`normalise()` builds every returned entry from four literal keys, so a filter
handing back a fifth gets it dropped — asserted directly, with a `capability`
key that does not survive. Rule 6 therefore cannot fail by a filter misbehaving.

That is the working agreement's preference in action: making a bug class
unrepresentable beats guarding one instance. The rule is kept because it still
has a real subject — it fails if `normalise()` is removed, or if somebody adds a
fifth key to the literal inside it.

### What the pure suite cannot prove, and is not pretending to

The brief's acceptance included *"the logout entry's URL differs between two
users, which is what proves it came from `wp_logout_url()`"*. It is not asserted
here, because `tests/template-stubs.php` returns a fixed string with no nonce —
the assertion would be measuring the stub.

What is asserted is that the URL equals whatever `wp_logout_url()` returns, which
is the checkable half. **The nonce being real, and per-session, moves to
`tests/integration/run-account-menu-gate.php`.** Recording the gap rather than
letting a green run imply it, since a silent exception is a lie with a longer
half-life.

### The empty-URL branch is driven through the filter, not by breaking a stub

`AccountForm::edit_url()` returns `''` on a site with no account page, and the
fixture has one — `wc_get_account_endpoint_url()` is stubbed. Rather than
dismantle that, the test sets the head entry's URL to `''` through the public
filter and asserts the list collapses to `logout` alone.

The property under test is "an entry with no URL is dropped"; a missing account
page is one cause of it, not the property itself.

### One stub gap found

The filter stub has no `remove_filter()`, so a filter added for one assertion
stays attached for the next and the second result silently measures the first
test. The suite saves and restores `$GLOBALS['ow_filters']` around each case.
