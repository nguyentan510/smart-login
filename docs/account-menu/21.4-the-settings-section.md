# 21.4 — The settings section

Spec: [`../account-menu.md`](../account-menu.md), decisions 3, 6, 12.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** An administrator can add a row to the middle of the menu — icon, text,
link — and choose what the signed-in button calls the member. No new machinery:
this is finding 6's repeater with a third column.

## Files

- `includes/class-field-registry.php` — one section, two field rows
- `includes/class-settings.php` — one sanitiser
- `includes/Admin/class-field-renderer.php` — one control
- `includes/Frontend/class-account-menu.php` — step 2 of its assembly wakes up

## Steps

1. `FieldRegistry::sections()` gains `account_menu => 'Menu tài khoản'`, on the
   `profile` tab. The tab already holds "Trường hồ sơ" and "Địa chỉ 2 cấp"; the
   account menu is the same family.
2. `account_menu.items` — `type => 'menu_items'`, `sanitize => 'menu_items'`,
   `default => array()`. The row lives in `profile_fields()` alongside the rest
   of the tab, because membership and rendering read the same row
   (`class-field-registry.php:13-16`) and a key placed anywhere else is the
   defect that class exists to prevent.
3. `account_menu.label_source` — `type => 'select'`, choices `auto` / `phone` /
   `name`, default `auto`. Three choices, and **no email**: spec decision 12.
4. `FieldRenderer::menu_items()`, modelled on `headers()`
   (`class-field-renderer.php:458-502`): a `widefat` table, `max( 5, count + 1 )`
   rows, always one spare, no JavaScript. Columns: icon `<select>` built from
   `IconSet::names()`, text `<input type="text">`, link `<input type="url">`.
5. `Settings::sanitize_menu_items()`, modelled on `sanitize_headers()`
   (`class-settings.php:706-750`):
   - a row with an empty label **or** an empty URL is dropped, silently, the way
     a blank header row is
   - `key` is derived with `sanitize_title()` from the label when absent, then
     de-duplicated with a numeric suffix — an administrator does not type a key,
     but decision 4 still needs every entry to have a stable one
   - `key` is refused if it collides with `account` or `logout`; the pinned ends
     own those names
   - `icon` is passed through `IconSet`, so an unknown name becomes the fallback
     and never survives as a string
   - `url` through `esc_url_raw()`
6. `AccountMenu` now reads the stored list for the middle of its assembly. It
   remains the only reader of the option — rule 9.

## Acceptance

- Saving three rows and reloading the tab shows three rows and one spare
- Saving a row with a label and no URL stores nothing, and does not error
- Saving two rows both labelled `Đơn hàng` yields two distinct keys
- A row whose label is `Đăng xuất` does **not** take the pinned tail's key
- Posting `icon=<script>` stores the fallback name; the string appears nowhere in
  the rendered admin screen or the rendered menu
- Clearing every row returns `AccountMenu::items()` to the two pinned entries —
  rule 7 still green, which is the regression this step could most easily cause
- The admin-screens suite passes with the new controls drawn
- Every other suite at its previous count

## Not in scope

Reordering by drag, a page picker, and the live preview beside the table — all
three are spec deferrals with their reasons written there. Row order in the table
is menu order.
