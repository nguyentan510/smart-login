# 8.5 — Address boundary

Spec: [`../account-surface.md`](../account-surface.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** End the presentational duplication between the profile's address
section and WooCommerce's Addresses tab, without losing what that tab does.

The data is already unified — `AddressFields` writes `billing_state`,
`billing_city` and `billing_address_1` through `ProfileSeeder`
(`class-address-fields.php:176`), which is exactly right and does not change.
What is duplicated is the *interface*: two forms, two field sets, no
cross-reference.

## Files

- `includes/Frontend/class-woo-integration.php` — billing form field rendering
- `templates/partials/address-fields.php` — reused, not forked
- `templates/partials/account/address.php`

## Steps

1. The profile section is labelled as what it is: the default delivery address,
   the one that prefills checkout.
2. Woo's Addresses tab keeps existing. Its **billing** form renders the same
   `partials/address-fields.php`, so there is one picker component with two
   hosts.
3. Shipping is left alone entirely.

## Why the tab is not taken over

Woo's Addresses tab manages two addresses and carries fields the plugin's picker
does not have: recipient name, company, `address_2`, postcode. Replacing it would
cost a customer the ability to ship somewhere other than the billing address.
That is a regression for a real shop, and design ownership does not justify it.

## Acceptance

- An address saved in the profile prefills checkout
- A shipping address differing from billing survives an order end to end
- Editing in either place produces the same stored values, verified against the
  database rather than the screen
- Shipping zones still match — `billing_state` holds the province **code**, not a
  name, and that must remain true

## Not in scope

Adding postcode or `address_2` to the plugin's picker. If they are wanted, that
is a separate decision about the Vietnamese address model, not a boundary fix.
