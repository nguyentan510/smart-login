# 8.5 — Address boundary

Spec: [`../account-surface.md`](../account-surface.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** End the presentational duplication between the profile's address
section and WooCommerce's Addresses tab, without losing what that tab does.

The data is already unified — `AddressFields` writes `billing_state`,
`billing_city` and `billing_address_1` through `ProfileSeeder`
(`class-address-fields.php:176`), which is exactly right and does not change.
What is duplicated is the *interface*: two forms, two field sets, no
cross-reference.

## Files

- `includes/Frontend/class-woo-integration.php` — billing form field rendering
- `templates/partials/address-fields.php` — reused, not forked
- `templates/partials/account/address.php`

## Steps

1. The profile section is labelled as what it is: the default delivery address,
   the one that prefills checkout.
2. Woo's Addresses tab keeps existing. Its **billing** form renders the same
   `partials/address-fields.php`, so there is one picker component with two
   hosts.
3. Shipping is left alone entirely.

## Why the tab is not taken over

Woo's Addresses tab manages two addresses and carries fields the plugin's picker
does not have: recipient name, company, `address_2`, postcode. Replacing it would
cost a customer the ability to ship somewhere other than the billing address.
That is a regression for a real shop, and design ownership does not justify it.

## Acceptance

- An address saved in the profile prefills checkout
- A shipping address differing from billing survives an order end to end
- Editing in either place produces the same stored values, verified against the
  database rather than the screen
- Shipping zones still match — `billing_state` holds the province **code**, not a
  name, and that must remain true

## Not in scope

Adding postcode or `address_2` to the plugin's picker. If they are wanted, that
is a separate decision about the Vietnamese address model, not a boundary fix.

---

## Outcome

**Step 2 as written above was wrong, and was not done.** "Its billing form
renders the same `partials/address-fields.php`" would have been a regression, not
a unification.

`Address\WooAddress` does not render the plugin's markup on Woo's screens, and
must not. It reshapes Woo's own field *definitions* — `woocommerce_states`,
`woocommerce_billing_fields`, `woocommerce_get_country_locale` — and lets
WooCommerce render them, so every third-party filter on those fields keeps
firing. Substituting our partial would bypass the whole pipeline, which is
exactly the "own the layout, but reserve the slots by name" rule in the spec,
broken from the other direction.

So the boundary was already unified where it counts. Both hosts share the
dataset, the combobox in `address.js`, and one set of keys:

| Key | Holds | Why that shape |
| --- | --- | --- |
| `billing_state` | province **code** | shipping zones match on it |
| `billing_city` | ward **name** | order emails and invoices print it |
| `OmniWP_ward_code` | ward **code** | the code Woo has nowhere to put |

What this sub-phase actually delivers is the proof of that, and the one
presentational gap 8.4 left behind.

### The boundary is now asserted, not assumed

`run-tests.php` drives both writers against stubbed user meta and compares what
they leave behind: the profile form through `AddressFields::validate()` +
`save_for_user()`, and WooCommerce's tab through
`WooAddress::store_customer_ward()`. Four keys must match, the province must
still be a code, the ward must still be a name, and the profile form must not
touch shipping — a customer may deliver somewhere other than they are billed.

> **Reversed in 17.4.** The last of those is no longer true, and the reversal
> was a decision rather than a drift. The card was headed "Địa chỉ giao hàng"
> while writing `billing_*` only, so it named an address it did not touch — and
> the note under it claimed editing here edited both, which was false for
> exactly the customers this paragraph was protecting. Phase 17 takes option
> (a): one address, mirrored into both books, heading true, with the cost
> stated. See [`../account-card.md`](../account-card.md), decision 4. Billing
> remains the only side that is read.

Two writers for one address is the arrangement most likely to rot quietly:
nothing errors when they drift, the data just stops agreeing with itself.

**Demonstrated to bite.** Running the same setup with
`store_customer_ward()` skipped leaves host 1 holding `Xã Minh Châu` and host 2
holding `00267` — the check fails, which is the point of writing it.

### The ward select says why it is inert

The remaining item from 8.4. It rendered `disabled` with no explanation, so a
first-time visitor met a grey box that reads as broken rather than as waiting.
It now carries a hint, tied to the control through `aria-describedby` rather than
merely sitting near it, and `address.js` removes the hint when the ward list
arrives — an instruction that no longer applies is worse than none.

Four assertions in `run-template-tests.php` render the partial in *both* states.
The existing fixture only ever exercised the one with a province already chosen,
which is the state where there is nothing to explain.

### Not verified in a browser

The JS half — the hint disappearing as wards load — is asserted only in its
rendered-markup form. The browser pane lost its session between sub-phases and
signing back in needs a password, which is not mine to type.
