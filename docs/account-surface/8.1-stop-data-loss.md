# 8.1 — Stop the data loss

Spec: [`../account-surface.md`](../account-surface.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Four live defects that throw away what a member has typed. All of them
land in `assets/js/smart-login.js`, which the 8.2 extraction does not rewrite —
so this ships alone, early, and does not wait on the architecture.

## Files

- `assets/js/smart-login.js`
- `includes/Frontend/class-rest-controller.php` — only for the resend change
- `templates/woocommerce/form-edit-account.php` — only if the pending block must
  render open; keep the edit to that one condition

## Steps

1. **`window.location.reload()` after `contact/verify`** (`smart-login.js:373`)
   discards every unsaved field on the page — name, DOB, address, the password
   boxes. Replace with an in-place update: rewrite the affected row's displayed
   value and its verified badge, clear the OTP input, collapse the confirm block.
2. **Enter inside `[data-sl-contact-value]`** triggers implicit form submission.
   Those inputs carry no `name`, so the typed value is discarded *and* the
   account saves. Bind Enter to the start-OTP handler and `preventDefault()`.
3. **A `beforeunload` guard while the form is dirty.** This is also what makes
   the provider `<a>` links safe to leave in the page — today clicking "Tiếp tục
   với Google" mid-form navigates away silently.
4. **Resend after a reload.** `ContactVerificationService::pending()` already
   returns the type and masked destination server-side, but the token lives only
   in a JS variable (`smart-login.js:302`). So the notice promising "gửi lại một
   mã mới bên dưới" points at a button inside a `hidden` block. Either render the
   confirm block open when a pending row exists, or let `contact/resend` accept a
   type instead of a token. The second is cleaner and survives 8.2 unchanged.

## Acceptance

Measured in a browser, not reasoned about:

- Edit the name field, leave it unsaved, verify an OTP — the edit survives
- Press Enter in both contact inputs — no navigation, OTP is sent
- Reload mid-flow — a working resend control is present
- Start editing, click a provider link — the browser asks before leaving

## Not in scope

Any change to markup structure, section order or CSS. This sub-phase must be
reviewable as a behaviour diff.

---

## Outcome

All four defects fixed. Five structural assertions added to
`run-fitness-tests.php` — the **required** suite, not the spec one, because 8.1
is a bug fix and the value of pinning it is that the reload cannot come back
without the build saying so. `Identity fitness: 25 passed, 0 failed.`

**The reload was hiding a second bug, not just discarding edits.** `verify()`
changes `user_email` server-side. The form still showed the previous address in
the `account_email` field it posts, so without the reload the next save would
have tripped `block_unverified_email_change()` — the account holding one address
while the form insisted on another. Writing the accepted value back into the
field is therefore required for correctness, not only for tidiness. The reload
had been papering over this by discarding the whole page.

**The value written back comes from the server.** `verify()` now returns a
`display` key alongside `value`: a phone is stored E.164 and was rendered with
`Phone::to_local()`, so echoing the raw input would have changed `0969789475`
into `+84969789475` on screen. Formatting server-side keeps the client from
reimplementing that rule and then drifting from it.

**Resend by type, with the token kept server-side.** `start()` and the new
`resend()` share a `remember_pending()` helper that stores the token in the
pending meta. `pending()` deliberately still does not return it — a token a
template can print is a token that ends up in a page. `resend()` re-stores the
new token, without which a second resend would fail against a row that
`OtpService::resend()` had already superseded.

**Dirty tracking excludes the contact inputs.** They carry no `name`, so
submitting never saves them and their own flow clears them; counting them would
prompt about "unsaved changes" that submitting could not have saved anyway.

Template edit kept to the sanctioned minimum: two `data-sl-contact-target`
attributes and a conditional `data-sl-contact-pending`.

### Server-side behaviour, measured on the same install

Fifteen checks against real WordPress and MySQL, covering everything in this
sub-phase that source scanning cannot assert: the token is stored server-side and
`pending()` still does not return it; `resend( user, type )` succeeds with no
token at all, which is the state every reload leaves the browser in; the stored
token is replaced rather than left stale, so a second resend still finds the row;
a resend for a type with nothing in flight fails as `smart_login_contact_session`
rather than silently; `verify()` returns `display`, updates the account and
clears the pending row.

```text
8.1 server side: 15 ok, 0 failed
```

Three things the run corrected, none of them defects in the shipped code:

- **The resend cooldown is enforced for real**, by `RateLimiter`, not merely
  advertised through `resend_after`. A script that resends immediately after
  `start()` is refused — correct behaviour, and it means a member who reloads
  within the cooldown sees a wait message rather than a new code. The check
  neutralises `otp.resend_cooldown` through the settings filter rather than
  sleeping through it.
- **`Phone::to_local()` takes canonical without a leading `+`.** The first
  version of the check fed it `+84969789475` and read the unchanged return as a
  bug in `display`. It is not: `verify()` passes `$claim->subject()`, which
  `Phone::normalize()` produces as `84969789475`, and `to_local()` turns that back
  into `0969789475`. The check now asserts the round trip rather than a guess at
  the format.
- **`dev_mode_active()` needs three conditions**, one of which is
  `wp_get_environment_type() !== 'production'` — and that constant defaults to
  `production`. The check defines `WP_ENVIRONMENT_TYPE` in its own process, so
  the site's configuration is untouched.

### Client behaviour, measured in a browser

Signed in at `http://localhost:10004/my-account/edit-account/`.

**The unsaved-changes guard.** A synthetic cancelable `beforeunload` returns
`defaultPrevented === false` on a clean form and `true` after editing Họ tên. It
stays `false` after typing into the contact box, which is the deliberate
exclusion: those inputs carry no `name`, so submitting could never have saved
them.

**Enter no longer submits the form.** A listener registered *after* the plugin's
own, so it observes the outcome, recorded `key: "Enter"` with
`prevented: true`, the start button being clicked, and **no** submit attempt on
`form.sl-form`. A marker on `window` survived, so the page did not navigate, and
the OTP panel opened with `Mã OTP đã được gửi tới ki•••••••@example.test.` This
is the path that used to discard the typed address and save the rest of the form
as a side effect.

**Resend survives a reload.** After a full page load with a pending row, the
panel carries `data-sl-contact-pending`, the confirm block renders open rather
than `hidden`, and "Gửi lại mã" is reachable. Clicking it sent:

```json
{"type":"email"}
```

No token — the state every reload leaves the browser in — and the server resolved
the pending row from the type alone.

**Not measured: the in-place row update after a successful verify.** Completing
that flow permanently changes the signed-in account's email and retires the
previous address, and the account available was the developer's own. Deferred by
choice rather than blocked. Its server half *is* measured — `verify()` returning
`display`, updating the account and clearing the pending row are four of the
fifteen checks above — so what remains unproven is only the DOM write that
consumes it.

Test state was cleaned up afterwards: the pending contact row created during
these checks was deleted, leaving two OTP rows that expire on their own.

### Two findings from running it, neither caused by this sub-phase

**The provider gate is failing on a stale settings vocabulary.** It reports
`Zalo provider-only account did not enter required email onboarding`, and does so
identically on a pristine `HEAD` worktree, so it predates this work. The cause:
`run-provider-gates.php:108` filters `smart_login_setting` for
`google_enabled`, `zalo_enabled`, `provider_auto_link_email` and
`field_email_optional` — every one of them a **legacy** key. The migration map in
`class-installer.php:107-135` renamed them to `providers.google.enabled`,
`providers.zalo.enabled`, `providers.auto_link_email` and
`profile.email_optional`. The filter therefore never matches what the runtime
asks for, silently does nothing, and the gate inherits whatever the live site has
configured — here `profile.email_optional = 1`, which makes the assertion false.

Note what this means: the gate would pass on a site configured with
`email_optional = 0`, not because the override worked but because the live config
happened to agree. This is the fourth time in this refactor a rename has crossed
a boundary no test covered — after `purpose`/`intent` (Phase 4) and
`$default`/`$fallback` (Phase 7), both recorded in the tracker.

**`run-wordpress-gate.php` crashes instead of reporting BLOCKED when the plugin
is not already active.** `wp-settings.php` uses `$plugin` as its own loop
variable and `unset()`s it, and the gate `require`s that file into the same
scope, so its `$plugin` at line 76 is gone. The guard reads
`if ( ! class_exists( … ) ) { if ( ! is_file( $plugin ) ) … }` — reachable only
when the plugin is *not* already loaded, which is exactly when `$plugin` has been
clobbered. Result: `TypeError: is_file(): Argument #1 must be of type string,
null given` in place of the intended clean blocker.

### Method note

The first reading of the gate result was wrong, and worth recording. A run from
the working copy failed at `the first unlink failed: Mật khẩu không đúng` while a
`HEAD` worktree passed, which looked like a regression from this sub-phase.
Copying the changed files into the clean tree one group at a time showed it was
not: baseline plus every change still passed, and the working copy then passed
twice in a row unmodified. The unlink failure has not reproduced since and
remains unexplained — a flaky gate, recorded here rather than explained away.

The alternation of pass and fail was coincidence, and it was persuasive enough to
have stopped the investigation at the wrong answer. Two runs are not a
comparison.
