# 8.4 — The layout

Spec: [`../account-surface.md`](../account-surface.md) — section order, CSS
inventory and field-level corrections are normative there, not repeated here.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** The first sub-phase where anything looks different. Everything before
it was structural.

## Files

- `templates/partials/account/*.php` — the six sections from 8.2
- `templates/partials/linked-identities.php` — first styling it has ever had
- `templates/partials/password-field.php` — the autocomplete fix
- `templates/partials/address-fields.php` — the ward hint
- `assets/css/smart-login.css`
- `assets/js/smart-login.js` — dirty state feeding the save bar

## Steps

1. **`.smart-login--account` gets its own width.** It currently has no rules at
   all, so the page inherits `max-width: 460px; margin: 0 auto` from
   `.smart-login` — a login-card width on a profile page inside a full-width Woo
   column. Largest single visual improvement in the phase, and one rule.
2. Reorder the sections per the spec, with real headings replacing
   `<p class="sl-lead">`.
3. Collapse contact editing into one "Đổi" per row that expands in place.
4. Providers render from `linked()` with masked subject and unlink; only
   `unlinked_providers()` get an invitation. The button copy stops saying "Tiếp
   tục với Google" — that is login copy on a profile page — and becomes "Liên
   kết Google".
5. Write CSS for the ten unstyled `linked-identities` classes listed in the spec.
6. Save bar pinned to the viewport bottom, reading dirty state, excluding
   sections whose `saves_own` is true and badging them instead.
7. Apply the field-level corrections from the spec — read-only treatment, the
   dropped country row, ward hint, the red email hint, the
   `password_current` autocomplete bug.

## Acceptance

- Desktop and 480px
- Keyboard-only pass over every control, including the collapsed password section
  and the expanding contact rows
- `prefers-reduced-motion` respected by the save bar and the expansions
- Screen-reader pass: no `disabled` used to mean read-only; every section has a
  heading in the outline
- `php tests/run-all.php` green, template smoke included

## Not in scope

The address tab reconciliation (8.5) and the msgid language (8.6).

### The section boundaries moved, and that was the substance of it

`identity` and `profile-extra` are gone as sections. The wireframe groups by the
question each card answers, not by which table a field lives in:

- **profile** — name, DOB, gender. What you are called.
- **contact** — phone, email, and the linked providers folded in. How you get in
  and how we reach you. `providers` stays a section for `profile-summary`, but
  `FORM_SECTIONS` leaves it out of the loop so the editing surface renders it
  inside the contact card rather than as a fifth box.

### Two defects the browser found that the suites could not

Both were green in every test and wrong on screen.

- **`label()` is a call to action, not a name.** `GoogleProvider::label()` returns
  "Tiếp tục với Google", so composing it produced **"Liên kết Tiếp tục với
  Zalo"**. Fixed at the root by adding `name()` to `LoginProviderInterface` —
  the bare brand — and leaving `label()` for the entry screen, where sign-in copy
  is correct. Adding an interface method immediately failed the regression
  suite's `FakeLoginProvider`, which is the interface doing its job.
- **A width reading that meant nothing.** The first measurement said 469px and
  looked like the CSS had not applied. It had: `max-width` computed to `760px`
  and the margin to `0`. The constraint was the browser pane at 783px, which
  gives WooCommerce's content column 469px. Re-measuring at 1400px gave 680px.
  A number from a viewport nobody uses is not a measurement.

### Field-level corrections applied

The hardcoded "Quốc gia: Việt Nam" row is gone. The address card states that it
shares its values with the Addresses tab. The required asterisk is `aria-hidden`
with a screen-reader text alternative beside it.

Referral was made read-only-once-set here and then **removed from the codebase
entirely** in a later change, along with the address quick-search — see the
removal note in the spec. Both are recorded rather than edited out of this file,
because a decision reversed is worth more in the history than a tidy page.

### A regression this sub-phase caused, and the older bug it exposed

Saving on the WooCommerce page failed with four errors: *First name*, *Last
name*, *Display name* and *Email address* each "is a required field". Found by
using the page, not by any suite.

**The direct cause is 8.4's own.** Email is no longer an input — it is text with
a "Đổi" beside it — so nothing posts `account_email`, and
`prepare_account_post()` only backfilled it for *synthetic* addresses. Every real
account therefore submitted no email at all. The backfill is now unconditional,
which is also the honest description of this form: it cannot change an email,
so the address on file is always what it is submitting.

**The name errors were an older bug that 8.4 merely surfaced.** The hook carried
the comment "runs before `WC_Form_Handler::save_account_details`
(template_redirect @20)". WooCommerce 10.9.4 registers it with
`add_action( 'template_redirect', array( __CLASS__, 'save_account_details' ) )` —
**no priority, so it runs at 10**, which is exactly where this ran too. Equal
priorities fall back to registration order, and WooCommerce registers during
`plugins_loaded` while this registers later. So WooCommerce validated the request
before the field names had been translated for it, and had done so since the
adapter was written; nothing in this refactor had ever pressed Save on that page.

Now priority 5, matching `FormController::dispatch()`, so the ordering is a
property of the code rather than an accident of load order. Two assertions in
`run-account-surface-tests.php` pin both halves: the priority must be below 10,
and the `account_email` backfill must not be conditional on the address kind.

Verified against the database afterwards: `display_name=Cai Hoa`,
`first_name=Hoa`, `last_name=Cai`, email unchanged.

### Not done here

The `readonly` / `disabled` unification listed in the spec no longer applies to
this card: the email and phone values are no longer inputs at all, they are text
with an action beside them, so there is nothing left to mark read-only. The
`disabled` ward select in `partials/address-fields.php` is untouched and still
carries no explanation — it belongs to the address picker rather than this
layout, and 8.5 is where that picker is next opened.
