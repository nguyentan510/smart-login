# 8.3 — A save path the plugin owns

Spec: [`../account-surface.md`](../account-surface.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Make the plugin whole without WooCommerce. Today there is no
`save_profile` case in `FormController` at all — the cases are identify, signup,
onboard, register, verify_otp, resend_otp, login, forgot, reset_password,
unlink_identity — so profile editing exists only where `WC_Form_Handler` runs.

This must land **before** 8.4, or the redesign has nowhere to live except the
WooCommerce page, which is the dependency the whole phase exists to remove.

## Files

- `includes/Frontend/class-form-controller.php` — new `save_profile` case
- `includes/Frontend/class-shortcodes.php` — `[smart_account]`
- `templates/profile-summary.php:25` — the wp-admin fallback

## Steps

1. Add the `save_profile` action. `save_onboarding()` (line 364) already handles
   name, DOB, gender and address correctly and is reusable nearly as-is — the
   gaps are the referral code and the password change.
2. Password change goes through `PasswordPolicy::validate()`. A Phase 4 fitness
   rule already requires it at every site that sets a password, so skipping it
   fails the suite rather than shipping.
3. Email is **not** handled here. It moves only through the OTP flow; the
   `block_unverified_email_change` filter rejects every other route and that
   stays true in the standalone context.
4. `[smart_account]` renders the same sections with context `standalone`.
5. `profile-summary.php:25` stops falling back to `admin_url( 'profile.php' )`.
   Point it at the standalone page when WooCommerce is inactive — sending a
   customer into wp-admin is not a fallback, it is a leak.

## Acceptance

Deactivate WooCommerce entirely, then from a shortcode page:

- edit and save name, DOB, gender, referral and address
- change the password, and confirm a weak one is rejected by the policy
- change the email through OTP and confirm it cannot be changed any other way
- confirm no link anywhere on the surface points into wp-admin

## Not in scope

Reproducing Woo's billing/shipping split. The standalone surface edits the same
`billing_*` keys the Woo page does — see the address boundary in the spec.

## Outcome

`FormController::handle_save_profile()` and `save_password()`, the
`[smart_account]` shortcode, and `templates/account.php` — the same renderer and
the same six partials as the WooCommerce page, differing only in the wrapper,
because the two surfaces are saved by different things.

Sixteen checks against a real WordPress with **WooCommerce genuinely absent**
(`WP_PLUGIN_DIR` points at the plugin's own parent, so
`wp_get_active_and_valid_plugins()` resolves smart-login and fails to find
woocommerce):

```text
8.3: 16 ok, 0 failed  →  SL_83_OK
```

Covering: name, DOB stored as `Y-m-d`, gender and referral all save; an address
missing its ward is refused rather than half-stored; a wrong current password, a
mismatched confirmation, and a policy-failing password each change nothing; a
correct change is applied; a bad nonce saves nothing; and blank password fields
save the rest of the form while leaving the password alone.

**The whole suite is now green and promoted.** `run-account-surface-tests.php`
moved from `spec` to `required` in `run-all.php`, for the reason Phase 5 gave
when promoting the identity suites: leaving a passing suite non-blocking can only
hide the next regression.

### Decisions worth recording

**A plain nonce, not `RequestGuard`.** The guard's honeypot and two-second
minimum fill time are aimed at anonymous forms. On a profile page the visitor is
already authenticated, and the timing check would reject somebody who flipped one
radio button and pressed save. `handle_unlink_identity()` set the precedent.

**`wp_update_user()`, not `wp_set_password()`.** For the current user,
`wp_update_user()` re-issues the auth cookie (`user.php:2932-2945` in the
installed WordPress 7.0.2), so changing your own password does not sign you out
mid-edit. `wp_set_password()` would, and re-authenticating afterwards would mean
minting a session outside `SessionIssuer` — which a Phase 3 fitness rule forbids
for good reason.

**Field names are normalised, not renamed.** The form posts
`smartlogin_full_name` and friends because WooCommerce's page is the surface that
cannot change. `handle_save_profile()` maps them to the internal names
`save_onboarding()` already understands — the same trick
`WooIntegration::prepare_account_post()` plays in the other direction. One set of
markup, two save paths.

**`edit_url()` returns `''` rather than wp-admin.** Resolution order is an
explicit `smart_login_account_url` filter, then WooCommerce's endpoint, then a
published page containing `[smart_account]` (cached in an option). When there is
nowhere to send anybody, the honest answer is no link, and every caller already
renders nothing for an empty string.

### Two test failures that were the test's fault, not the code's

Both are recorded because each looked exactly like a product defect first.

- **`$base + array( … )` keeps the LEFT side on a duplicate key.** The case that
  changes the name while leaving the password blank was silently re-submitting
  the *old* name, so working code reported as broken. `array_merge` fixes it. The
  PHP array-union operator is a trap precisely because it fails quietly.
- **An address with a province and no ward is refused**, by
  `AddressFields::validate()`, with `smart_login_no_ward`. That is correct — half
  an address cannot be delivered to — and the check now asserts the refusal
  instead of asserting a save with fabricated codes.
