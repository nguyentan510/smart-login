# 8.0 — Guard rails

Spec: [`../account-surface.md`](../account-surface.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Land the rule that detects duplicated section markup *before* the
duplication is removed, so the rule can be demonstrated red on the current tree.

Per the Postscript in the tracker: rules of the form "the old thing is gone" are
half a rule, and a rule assumed to work is not a rule. This sub-phase exists
because 8.2 would otherwise ship a green rule that has never been observed
failing.

## Files

- `tests/identity/run-fitness-tests.php` — new rule
- `tests/identity/run-template-tests.php` — extend fixtures

## Steps

1. Add a fitness rule: each of the markers `sl-provider-buttons`,
   `recommended_missing` and `data-sl-contact` may appear in **exactly one**
   file under `templates/`.
2. Run it against the current tree. It must name, by path:
   - `templates/profile-summary.php` and
     `templates/woocommerce/form-edit-account.php` for the first two markers
   - `templates/woocommerce/form-edit-account.php` for the third
3. Record that red output in the commit message. It is the evidence.
4. Extend `run-template-tests.php` so it can render section partials with
   fixtures once they exist — it already covers 11 templates and is the only
   gate that executes template code rather than reading it as a string.

## Acceptance

The rule names both offending files on the current tree. It stays red until 8.2
lands, and no allowlist entry is added to silence it in the meantime.

## Not in scope

Removing the duplication. That is 8.2 — this sub-phase only proves the detector
works.

---

## Outcome

Delivered as `tests/identity/run-account-surface-tests.php`, plus
`sl_require_single_template()` in `harness.php` and a coverage guard in
`run-template-tests.php`. Four assertions red, one green:

```text
Account surface: 1 passed, 4 failed, 0 pending
```

Both 8.2 rules name exactly `templates/profile-summary.php` and
`templates/woocommerce/form-edit-account.php`. The two 8.3 assertions were added
while writing the suite — the same file is the natural home for "the Woo template
is the only editing surface", and stating it as an assertion is cheaper than
restating it in prose.

**The first draft of the provider rule was wrong, and the run said so.** It
matched the shared `.sl-provider-buttons` class and named a third file,
`templates/form-auth.php`. That block is `data-sl-provider-mode="login"` — a way
into the site, not a way to attach a provider to an account you are already
signed into. Same markup, different concern. Re-anchoring on
`data-sl-provider-mode="link"` dropped the false positive. This is the third time
in this refactor a source-scanning rule has had to be narrowed from a name to a
syntax; the pattern is now clear enough to state as a habit: **scan for the thing
that distinguishes the concern, never for the token both concerns share.**

**Registered `spec`, not `required`.** The two rules must stay red until 8.2, and
a red required suite would block the gate through all of 8.1. `run-all.php`
already documents `spec` as the kind for "a specification that lands ahead of its
implementation" and noted it was being kept for the next such case. This is that
case. Promote at 8.2/8.3.

**The coverage guard found something worth writing down.** Of nineteen templates,
four have no fixture, and two of those are the WooCommerce pair — so *the most
complex template in the plugin has never been executed by any test*. That is
where the drift accumulated, and it is not a coincidence. The exclusion for
`woocommerce/form-edit-account` carries an instruction to delete it at 8.2, and a
companion assertion fails if the exclusion list ever names a template that no
longer exists.

Required gate unaffected: `php tests/run-all.php` exits 0, with Coding standards
and Account surface reported as RED (spec).
