# 8.6 — Interface language

Spec: [`../account-surface.md`](../account-surface.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**This is a decision, not a task.** It may be declined — but in writing, in this
file, rather than by default.

## The situation

Every string is a Vietnamese `msgid`. On an `en_US` site the form renders in
Vietnamese under WooCommerce's English "Account details" heading, beside an
English account menu. That mixture is not a misconfiguration by the site owner;
it follows directly from how the strings are written.

`languages/omniwp.pot` holds 445 strings with 36 translator notes, generated
by `bin/build-pot.php`.

## If taken

Convert msgids to English and ship a `vi_VN` catalogue, which is the conventional
arrangement and what makes the plugin distributable outside Vietnam.

**Sequenced last, and deliberately.** This refactor has twice been bitten by a
blind `str_replace` desynchronising a signature from its body:

- Phase 4, `purpose` → `intent`: `PendingSession` kept returning the old key
  while controllers read the new one; REST verify and resend would both have
  broken. Neither suite caught it — it was found by grepping for leftovers
- Phase 7, `$default` → `$fallback`: `Settings::get()` and `Flow::old()` read a
  variable that no longer existed, which PHP treats as `null`, so **every
  configuration default silently became null** while `php -l` stayed green

A 445-string sweep is the largest mechanical rename yet attempted here, and both
prior failures crossed a boundary no test covered.

### Acceptance if taken

- `bin/build-pot.php` regenerates cleanly
- A `vi_VN` load renders identically to today, screen by screen
- A dangling-string scan over every changed msgid reports zero
- `tests/identity/run-template-tests.php` green — it executes template code,
  which is where the Phase 3 fatal survived four other gates

## If declined

Record the reason here and close the item. "The plugin ships only to Vietnamese
sites" is a legitimate answer. What is not legitimate is leaving it open
indefinitely, because every new string written in the meantime enlarges the
eventual sweep.

---

## Decision: declined for 1.0.1

The plugin targets Vietnamese sites. Vietnamese `msgid`s are the honest encoding
of that, and an `en_US` install rendering Vietnamese is a configuration this
project does not currently serve.

**What the delay cost, measured rather than guessed.** The brief was written
against 445 strings. Phase 9 added its own, and `bin/build-pot.php` now reports:

```text
Wrote languages/omniwp.pot
  605 strings from 113 files
```

That is the sweep growing by 36% while the decision stayed open — exactly the
effect the brief warned about, and the reason this is being closed now rather
than deferred again.

**Reopen when**, and only when, a concrete non-Vietnamese deployment exists.
Then the acceptance criteria above still apply, and the two rename failures they
were written from — `purpose`/`intent` and `$default`/`$fallback` — are still the
reason a 605-string sweep needs a dangling-string scan rather than confidence.

The `.pot` is regenerated and current as of 1.0.1, so a translator can supply a
catalogue for any locale today without the msgids changing. That is the part of
the value this decision does not forfeit.
