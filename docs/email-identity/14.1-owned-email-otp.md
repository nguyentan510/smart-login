# 14.1 — Do not spend an OTP on an address somebody already holds

Spec: [`../email-identity.md`](../email-identity.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Turn a three-step dead end into a first-step refusal. Ships alone, and
before the model changes, because it is the harm that is live today.

## Files

- `includes/Auth/class-register-handler.php` — `validate_identity()`
- `tests/identity/run-contract-tests.php`

## Steps

1. In `validate_identity()` (`:412-438`), after the claim resolves to
   `CREATE_USER` / `CREATE_NEW_USER` and **before** `start_identity()` reaches
   `$this->otp->issue()` (`:128`), refuse an `email` claim whose address is already
   held in `wp_users`. **`email_exists()`** — it returns the owner id, which is
   what the audit record wants, so `get_user_by()` buys nothing here. 14.0's
   Outcome records why the stub side of that mattered too.

2. The message is the one the last step already gives — *"Tài khoản đã tồn tại.
   Vui lòng đăng nhập."* — moved to where it is actionable. Vietnamese UI string,
   `omniwp` text domain.

3. Record it. `AuditLog::REGISTER_STARTED` fires before this point today; the
   refusal needs its own trail or the drift becomes invisible again.

## Acceptance

- 14.0's rule 1 goes green — **both halves**: the error code, and the write count
  dropping from 5 to 0. The second half is the one that measures the harm.
- 14.0's two gate doors stay **red**. This sub-phase deliberately does not fix
  them; a green gate here would mean the guard had been mistaken for the cure.
- Registration with a genuinely unused address is unchanged — asserted, because
  this guard sits on the happy path of every new signup and a wrong predicate here
  closes registration for everyone.

## Not in scope

Saying *why* the account exists, or which provider it uses. The refusal names the
state, not the method — see the spec's last section. The enumeration position is
unchanged: the identify screen already reveals registration status by which screen
returns (`class-form-controller.php:309-311`), and this moves that reveal earlier
in the same flow rather than adding a new one.

### 14.0's second rule was measuring the wrong thing

It asserted that **nothing** is written while refusing, and it went red at
`actual: 1` after the guard was in place — because the guard writes an audit row,
which is correct behaviour. The rule now counts inserts into the OTP table
specifically: the harm is a code being spent, not a record being kept.

Changing a guard rail after the fact is the move this project distrusts, so it was
checked in both directions rather than assumed: the refined rule still fails on the
pre-14.1 tree at `actual: 1`, and the failure is now the OTP row rather than an
undifferentiated write count. Verified by stashing `includes/` and re-running, not
by reading the diff. The 14.0 brief's own wording was right about this and the
implementation was looser than the brief — the correction goes towards the brief,
not away from it.

### The guard refuses exactly what the last step already refused

This is what makes it safe on the happy path, and it is worth stating because the
first instinct was to worry about the `CREATE_NEW_USER` (recycled subject) branch.
Both branches reach `UserManager::create_verified_user()`, which asks
`email_exists()` at `:116` before creating anything. So the set refused here is the
set that was already refused two steps later. No registration that could have
succeeded is lost — only the code and the budget are saved.

### `AuditLog::REGISTER_REFUSED`, deliberately sampleable

A new constant rather than `REGISTER_STARTED` with a flag. Two consequences worth
naming: 10.4's bus fans out every constant, so a site with automation on will begin
receiving a new event type; and it is deliberately **not** in `NEVER_SAMPLED`,
because a visitor retrying a known address is the ordinary case and one aggregated
row an hour says everything a flood of identical rows would.

No `.pot` regeneration: the refusal reuses the msgid already carried by the
`ALREADY_REGISTERED` branch at `:433`. The event vocabulary is not mirrored in any
doc — grepped, not assumed.

### This guard outlives its cause

Once 14.4 lands, the state it detects — an address in `wp_users` with no row in the
directory — stops being producible, so the branch becomes near-unreachable. It
stays. Deleting it would remove the only thing watching for the two stores drifting
apart again, and the drift is the whole subject of this phase.

### The gate doors are still red, and still unrun

Unchanged by this sub-phase, which is the intended result: a green gate here would
mean the guard had been mistaken for the cure. They remain unexecuted for want of a
local WordPress.
