# 14.3 — A password step that can offer proof instead

Spec: [`../email-identity.md`](../email-identity.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Give the password screen a way forward for somebody who has no password
to type. **Must land before 14.4.** Granting the identity row first would route
provider-first accounts to this screen while it is still a box they cannot fill —
trading a false message for a true one that helps just as little.

## Files

- `templates/form-auth.php` — the password step
- `includes/Frontend/class-form-controller.php` — the route from that step
- `tests/identity/run-template-tests.php`, `tests/identity/run-contract-tests.php`

## Steps

1. The password step gains one affordance: *"Đăng nhập bằng mã xác thực"*, which
   starts `PasswordResetHandler::start()` for the identifier already held in the
   flow (`Flow::STEP_PASSWORD` carries it — `class-form-controller.php:366-368`).

2. No new intent, no new grant type. `INTENT_RECOVER` is what this is, and the
   handler already sets a password without knowing the old one
   (`class-password-reset-handler.php:179`). The screen is being pointed at an
   existing door, which is the entire design.

3. It is offered **unconditionally**, to every account reaching the password step.
   Deliberate, and this is the sub-phase where the marker meta would have been
   spent: the alternative is to detect "this account has no password the holder
   knows", which cannot be answered for existing accounts and is not worth a second
   source of truth to answer for new ones. Somebody who does know their password
   loses nothing by seeing a second route; somebody who does not gains the only one
   they have.

4. Rate limiting is unchanged. `PasswordResetHandler::start()` spends
   `check_identify()` (`:57`) and then `check_otp_send()`, which is what 9.4 put
   there. This adds a caller, not a bypass — asserted, because a new entry point to
   an OTP send is exactly the shape of 9.4's original defect.

## Acceptance

- From the password step, without typing a password, an account can obtain a reset
  code and set a password. Asserted end to end at unit level and again in the
  integration gate, because it crosses OTP storage.
- The new affordance spends a budget. Asserted by exhausting it and observing the
  refusal, not by reading the call site.
- 14.0's two gate doors remain red — this sub-phase does not touch resolution.
- Template suite renders `form-auth.php` in the password step with the new control
  present and no notice raised.

## Not in scope

Any change to how the password step **verifies** a password. Any change to the
security section of the account page — that is 14.6, and it is a different screen
with a different question.

### The brief planned a controller route and one was not required

It described starting `PasswordResetHandler::start()` from the password step, which
implied a new action and a new `handle_*` method. But `handle_forgot()`
(`class-form-controller.php:853`) already reads `$post['identity']` — so the screen
can post the **existing** `forgot` action with the identifier it is already holding,
and the whole sub-phase becomes one extra `<form>`.

That is a better outcome than the brief's for the reason the brief itself gave: no
new intent, no new grant, and — the part that matters for 9.4 — **no new entry point
to an OTP send**. There is nothing new to meter, because nothing new sends. The
acceptance's "assert the new route spends a budget" turned out to be unfalsifiable
in the good way: the route *is* the metered one. What is asserted instead is that
the markup posts `forgot` and carries the identifier, which is the claim that can
actually be wrong.

A separate `<form>` because a submit button inside the login form would submit the
login form. Guard fields are unprefixed here while the login form's are prefixed,
which is what `RequestGuard::fields()`'s prefix argument exists for.

### The brief's label promised something the flow does not do

It called the affordance *"Đăng nhập bằng mã xác thực"*. It is not a login:
`handle_reset_password()` ends at `Notices::flash( 'Đặt lại mật khẩu thành công. Vui
lòng đăng nhập bằng mật khẩu mới.' )` and redirects to the login step
(`class-form-controller.php:907-909`). The visitor sets a password and then signs in
with it. The shipped label is *"Chưa có mật khẩu, hoặc không nhớ?"* over a
**Gửi mã xác thực** button, which is what actually happens.

### The old link was replaced, not joined

*"Quên mật khẩu?"* linked to a screen that asked for the identifier the visitor had
just typed. Two recovery routes side by side would have been clutter, and the worse
one was the one that made you type again. Changing the identifier is still one click
away — the **Đổi** link in the identity chip above has always done that.

Reuses `.sl-btn--ghost` rather than earning a variant: the control should sit under
the primary action, not compete with it, and a variant with one caller is a rename
with extra steps. One new CSS rule, for the block's spacing.

### Found while regenerating the `.pot`: it is stale by 76 strings

The new string made the catalogue out of date, so `bin/build-pot.php` was run — and
it reported **605 → 681**. The catalogue has not been regenerated since Phase 8.6
recorded 605, so phases 9 through 13 added 75 strings that no translator can see.

Deliberately **not** folded into this commit: a 1,247-line generated diff would bury
the one string this sub-phase adds, and the working agreement asks for one commit
per sub-phase reviewable as "one rule turns green". Regenerated in its own commit
immediately after, so nothing is left stale.
