# 14.3 — A password step that can offer proof instead

Spec: [`../email-identity.md`](../email-identity.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Give the password screen a way forward for somebody who has no password
to type. **Must land before 14.4.** Granting the identity row first would route
provider-first accounts to this screen while it is still a box they cannot fill —
trading a false message for a true one that helps just as little.

## Files

- `templates/form-auth.php` — the password step
- `includes/Frontend/class-form-controller.php` — the route from that step
- `tests/identity/run-template-tests.php`, `tests/identity/run-contract-tests.php`

## Steps

1. The password step gains one affordance: *"Đăng nhập bằng mã xác thực"*, which
   starts `PasswordResetHandler::start()` for the identifier already held in the
   flow (`Flow::STEP_PASSWORD` carries it — `class-form-controller.php:366-368`).

2. No new intent, no new grant type. `INTENT_RECOVER` is what this is, and the
   handler already sets a password without knowing the old one
   (`class-password-reset-handler.php:179`). The screen is being pointed at an
   existing door, which is the entire design.

3. It is offered **unconditionally**, to every account reaching the password step.
   Deliberate, and this is the sub-phase where the marker meta would have been
   spent: the alternative is to detect "this account has no password the holder
   knows", which cannot be answered for existing accounts and is not worth a second
   source of truth to answer for new ones. Somebody who does know their password
   loses nothing by seeing a second route; somebody who does not gains the only one
   they have.

4. Rate limiting is unchanged. `PasswordResetHandler::start()` spends
   `check_identify()` (`:57`) and then `check_otp_send()`, which is what 9.4 put
   there. This adds a caller, not a bypass — asserted, because a new entry point to
   an OTP send is exactly the shape of 9.4's original defect.

## Acceptance

- From the password step, without typing a password, an account can obtain a reset
  code and set a password. Asserted end to end at unit level and again in the
  integration gate, because it crosses OTP storage.
- The new affordance spends a budget. Asserted by exhausting it and observing the
  refusal, not by reading the call site.
- 14.0's two gate doors remain red — this sub-phase does not touch resolution.
- Template suite renders `form-auth.php` in the password step with the new control
  present and no notice raised.

## Not in scope

Any change to how the password step **verifies** a password. Any change to the
security section of the account page — that is 14.6, and it is a different screen
with a different question.
