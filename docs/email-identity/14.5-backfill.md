# 14.5 — Backfill

Spec: [`../email-identity.md`](../email-identity.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Existing provider-first accounts get the row too, or the phase ships two
classes of user and the doors keep disagreeing for everybody who signed up before
the upgrade.

## Files

- `omniwp.php` — `OMNIWP_DB_VERSION` 5 → 6
- `includes/class-installer.php` — one migration, keyed off the version
- `tests/integration/run-wordpress-gate.php`

## Steps

1. `OMNIWP_DB_VERSION` to `6`. **No schema change** — the migration writes rows
   into `OmniWP_identities` as it stands. The bump exists because
   `maybe_upgrade()` (`class-installer.php:42`) is keyed on it and that is the only
   trigger available; `migrate_settings_shape()` (`:64`) is the pattern being
   followed.

2. The migration selects candidates and calls
   `UserManager::adopt_verified_email()` — the same writer, not bespoke SQL. A
   candidate is an account where **all** of the following hold:

   - the directory holds at least one federated row and **no** `email` row
   - `user_email` is non-synthetic (`UserManager::is_synthetic_email()`)
   - exactly one `wp_users` row holds that address, compared case-insensitively —
     the same query `auto_link_email` already uses (`class-account-provisioner.php:88-93`)
   - the provider whose row the account holds has `email_identity` on

   Any of these failing means skip, not repair. A migration that fixes things it was
   not asked to fix is a migration nobody can review.

3. Idempotent, and asserted so: running it twice produces the same table.
   `replace_in_channel()` retires before claiming, so a second run must be a no-op
   rather than a history entry — and history entries are the thing that would make
   this hard to reason about afterwards.

4. Batched, with the cursor in an option. An install with a large user table must not
   need the migration to complete inside one request.

5. It writes a count to the audit log. This grants a login route to a set of existing
   accounts; how many, and when, is evidence somebody will want.

## Acceptance

- Measured on the real WordPress, not the stub `$wpdb`. A provider-first account
  created before the upgrade can sign in by its address afterwards, and
  `pending_schema_changes()` is empty so `dbDelta` issues no `ALTER TABLE` on a
  healthy install — the shape Phase 2's acceptance established.
- Second run changes nothing: same row count, no new history rows.
- An account with a synthetic address is untouched. An address held by two users is
  untouched, and skipping it is asserted rather than assumed.
- Every required suite unchanged.

## Not in scope

Retro-granting anything to accounts whose provider has the flag off. Turning the
flag on for an existing install — the migration reads the setting, it does not
write it.

---

## Outcome

Red then green on WordPress 7.0.2, and the gate found two defects in the migration
before it was allowed to pass.

```text
--- before ---
OMNIWP_AUTH_INTEGRATION_FAILED
reason=integration assertion raised an exception: Call to undefined method
       OmniWP\Installer::backfill_provider_emails()

--- after ---
OMNIWP_AUTH_INTEGRATION_OK        db_version=6
OMNIWP_GOOGLE_STAGING_SMOKE_OK
OMNIWP_PROVIDER_LINKING_OK
OMNIWP_ZALO_STAGING_SMOKE_OK
OMNIWP_ABUSE_GATE_OK              db_version=6
OMNIWP_DELIVERY_GATE_OK
```

Every local suite unchanged: regression 322, core 175, contract 50, fitness 30,
templates 96, admin 123, account surface 7, abuse 30, delivery 46, mail 56.

### The cursor outlived the migration, and nothing would have resumed it

The gate asserts that the cursor option is gone once the upgrade finishes. It was not,
and that assertion is the only reason the real defect surfaced:

```text
reason=the backfill cursor outlived the migration, so a later pass would skip users
```

The batching was designed for repeated passes and **nothing scheduled a second one**.
`maybe_upgrade()` calls the backfill once and then bumps the version, so on any site
with more accounts than one batch the remaining users would never be visited again —
the migration would report success having done a fraction of the work, and the cursor
sitting in the options table would guarantee the rest were skipped for ever.

Two changes, and the pair is the fix:

1. A short batch means the end of the table, so the cursor is deleted then rather than
   waiting for an extra empty pass that nothing would run.
2. `maybe_upgrade()` gained a branch: when the version is already current **but the
   cursor exists**, run another batch. That is what makes the cursor's durability mean
   something instead of being a trap.

Found by an assertion I nearly did not write — the version round-trip was added only
because calling `backfill_provider_emails()` directly proves the migration works and
proves nothing about whether anything runs it. That is the same gap as 14.7, one
sub-phase later, in code written by somebody who had just recorded the lesson.

### A pinned version number in an unrelated gate

`run-abuse-gate.php` asserted `db_version` was the literal `5` — 9.1 owned the bump at
the time and pinned its number. Bumping to 6 turned that into a red on a phase 9.1
does not care about:

```text
OMNIWP_ABUSE_GATE_FAILED
reason=db_version is 6, expected 5
```

Now compared against `OMNIWP_DB_VERSION`. What the assertion is for is that the
option was written after the upgrade ran; whether the schema is current is
`pending_schema_changes()` two lines above, which stayed green throughout. The
wind-back value in this sub-phase's own assertion was derived from the constant for the
same reason, rather than repeating the mistake in the same commit.

**I should have grepped for the old value before bumping.** CLAUDE.md records five
occasions this project shipped a change that crossed a boundary no test covered; this
is a sixth, caught by a gate rather than by the sweep that should have preceded it.

### What it did to the real site, stated because it is not reversible by itself

On the Local install the backfill adopted addresses for two genuine accounts —
`hoacai.vi@gmail.com` (user 14) and `erubik.tool@gmail.com` (user 96) — plus several
leftover gate fixtures. Those two accounts can now be signed in and recovered by their
Gmail address. That is the intended effect of the sub-phase and the risk written below;
it is recorded here as what actually happened rather than what was expected to.

The per-provider gate held on real data: two Zalo accounts with real-looking addresses
were skipped because `providers.zalo.email_identity` is off, and one with a synthetic
`@phone.invalid` address was skipped for being synthetic.

### The installed copy and the working tree disagree about the version

Worth knowing for anybody reading `OMNIWP_db_version` on that site: the gate runs
against the working tree, where the constant is `6`, but `wp-content/plugins/omniwp`
is a checkout at an older commit where it is `5`. So a browser hit on the site rewrites
the option back to `5`, and the next gate run puts it to `6` again. Not a defect in
either — two copies, two constants. `git pull` in the plugin directory settles it.

## The risk, stated plainly

This widens how a set of existing accounts can be reached, without their holders
asking. That is the trade being made deliberately: those accounts are reachable at
that address by core's own login form already, and the widening is what stops the
plugin contradicting itself. An administrator who does not want it turns the
provider flag off **before** upgrading, and the help text from 14.4 has to say so.
