# 14.5 — Backfill

Spec: [`../email-identity.md`](../email-identity.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Existing provider-first accounts get the row too, or the phase ships two
classes of user and the doors keep disagreeing for everybody who signed up before
the upgrade.

## Files

- `smart-login.php` — `SMART_LOGIN_DB_VERSION` 5 → 6
- `includes/class-installer.php` — one migration, keyed off the version
- `tests/integration/run-wordpress-gate.php`

## Steps

1. `SMART_LOGIN_DB_VERSION` to `6`. **No schema change** — the migration writes rows
   into `smartlogin_identities` as it stands. The bump exists because
   `maybe_upgrade()` (`class-installer.php:42`) is keyed on it and that is the only
   trigger available; `migrate_settings_shape()` (`:64`) is the pattern being
   followed.

2. The migration selects candidates and calls
   `UserManager::adopt_verified_email()` — the same writer, not bespoke SQL. A
   candidate is an account where **all** of the following hold:

   - the directory holds at least one federated row and **no** `email` row
   - `user_email` is non-synthetic (`UserManager::is_synthetic_email()`)
   - exactly one `wp_users` row holds that address, compared case-insensitively —
     the same query `auto_link_email` already uses (`class-account-provisioner.php:88-93`)
   - the provider whose row the account holds has `email_identity` on

   Any of these failing means skip, not repair. A migration that fixes things it was
   not asked to fix is a migration nobody can review.

3. Idempotent, and asserted so: running it twice produces the same table.
   `replace_in_channel()` retires before claiming, so a second run must be a no-op
   rather than a history entry — and history entries are the thing that would make
   this hard to reason about afterwards.

4. Batched, with the cursor in an option. An install with a large user table must not
   need the migration to complete inside one request.

5. It writes a count to the audit log. This grants a login route to a set of existing
   accounts; how many, and when, is evidence somebody will want.

## Acceptance

- Measured on the real WordPress, not the stub `$wpdb`. A provider-first account
  created before the upgrade can sign in by its address afterwards, and
  `pending_schema_changes()` is empty so `dbDelta` issues no `ALTER TABLE` on a
  healthy install — the shape Phase 2's acceptance established.
- Second run changes nothing: same row count, no new history rows.
- An account with a synthetic address is untouched. An address held by two users is
  untouched, and skipping it is asserted rather than assumed.
- Every required suite unchanged.

## Not in scope

Retro-granting anything to accounts whose provider has the flag off. Turning the
flag on for an existing install — the migration reads the setting, it does not
write it.

## The risk, stated plainly

This widens how a set of existing accounts can be reached, without their holders
asking. That is the trade being made deliberately: those accounts are reachable at
that address by core's own login form already, and the widening is what stops the
plugin contradicting itself. An administrator who does not want it turns the
provider flag off **before** upgrading, and the help text from 14.4 has to say so.
