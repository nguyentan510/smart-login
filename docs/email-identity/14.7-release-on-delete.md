# 14.7 — Deleting a user releases its identities

Spec: [`../email-identity.md`](../email-identity.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Numbered last, sequenced before 14.5** — the same way 10.7 ran second and 9.10
landed before 9.8. Sub-phase numbers here are allocation order, not execution order.

**Goal.** Give back the subjects a deleted account was holding.

## Why this runs before the backfill

`wp_delete_user()` left `OmniWP_identities` rows live. Nothing hooked
`deleted_user` — grepped across `includes/`, not assumed. So:

- The subject stayed claimed by an account that no longer existed. `resolve()`
  answered KNOWN, and `create_verified_user()` then refused that phone number or
  address as *"Tài khoản đã tồn tại."* **permanently**.
- Login failed closed: `LoginHandler` asks `owner()`, `get_userdata()` returns
  `false`, and it returns the generic failure. A denial, not a takeover — which is
  exactly why it survived every gate for eleven phases.

`IdentityRepository::retire_all_for_user()` has existed since Phase 2 with a default
reason of literally `'user_deleted'`. It was written for this and never wired up; its
only callers were two teardown lines in the integration gate.

14.4 widened the blast radius: every provider account now has an email row, so
deleting such a user strands their address as well as their provider subject. And
14.5 is about to hand email rows to a whole population of existing accounts. Running
the backfill while deletion still strands rows would be knowingly multiplying a defect
that was found two hours earlier.

## Files

- `includes/class-plugin.php` — the hook and the handler
- `tests/identity/run-fitness-tests.php` — two structural rules
- `tests/integration/run-wordpress-gate.php` — the behavioural rule

## Steps

1. `add_action( 'deleted_user', … )`. **Not `delete_user`**: after the row is gone, so
   a deletion that fails leaves the identities where they were.

2. The handler calls `retire_all_for_user()` and audits the count under
   `IDENTITY_RETIRED` when anything was released.

   **Retire, not delete.** The history row is what makes the subject resolve RETIRED,
   and RETIRED is what lets a *different* person register it while keeping the trail
   that it was reused. Phase 3 built that distinction; this is the case it was built
   for.

3. Two structural rules, because the defect was not a wrong line but a missing one:
   `retire_all_for_user()` must have a production caller, and `deleted_user` must be
   hooked. Deliberately narrow — "every public repository method has a caller" would
   be the general form and would go red on things that are legitimately API surface.

4. One behavioural rule in the gate, with its own fixture: claim a subject, delete the
   user, assert no live row and that the subject no longer resolves KNOWN. Its own
   fixture rather than reusing the gate's accounts, because a rule about deletion must
   own the deletion.

## Acceptance

Both fitness rules red before, green after. The gate rule red before, green after,
measured on the real site rather than reasoned about. Every other suite unchanged.

## Not in scope

**Multisite.** `wpmu_delete_user` fires `deleted_user` too, so a network-wide delete
is covered. `remove_user_from_blog` is not, and whether leaving one site of a network
should release identities the network still owns is a decision rather than an
omission — written down here rather than left to be discovered.

Rows already stranded on existing installs. This stops new ones; a sweep for old ones
would be a migration, and 14.5 already owns the only DB version bump in the phase.

## Outcome

Red then green, on WordPress 7.0.2.

```text
--- before ---
Identity fitness: 28 passed, 2 failed
  FAIL     releasing a deleted user's identities has a production caller
  FAIL     and something is hooked to deleted_user to be that caller

OMNIWP_AUTH_INTEGRATION_FAILED
reason=deleting a user left its identity row live, so that subject can never be
       registered again

--- after ---
Identity fitness: 30 passed, 0 failed, 0 pending
OMNIWP_AUTH_INTEGRATION_OK
wordpress=7.0.2 · db_version=5
```

Every other suite unchanged: regression 322, core 175, contract 50, templates 96,
admin 123, account surface 7, abuse 30, delivery 46, mail 56.

### The defect was a missing caller, not a wrong one

Which is why the structural rules are shaped the way they are. A rule of the form
"this code is correct" could never have caught it: the code *was* correct, complete,
and named after the exact event it was meant to serve. Nothing invoked it.

That is a fourth variant of the lesson this project keeps relearning — Phase 7's
"rules of the form *the old thing is gone* are half a rule". The other half here is
**does anything call the new thing**, and for eleven phases the answer was no while
every test suite stayed green.

### Found by running the thing, not by reading it

It surfaced from 14.4's leftover rows: three identity rows pointing at users the gate
had deleted. Reading `AccountProvisioner` would never have produced it, because the
missing code is in neither the provisioner nor the repository — it is the absence of a
line in `Plugin::boot()`.
