# 14.0 — Guard rails

Spec: [`../email-identity.md`](../email-identity.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Land the drift as failing assertions before anything is fixed, so the
detector is proven rather than assumed.

Split across two suites, and the split is not tidiness. The consequence that can
be observed in PHP — a flow spending a real OTP on an address `wp_users` already
holds — goes in `tests/identity/run-contract-tests.php`, where it runs on every
commit. The two doors need a store that actually *stores*, and the stub `$wpdb`
does not parse SQL by written-down decision (`tests/stubs.php`, the class
docblock). Reversing that decision to suit one phase would be the wrong trade, so
those two live in `tests/integration/run-provider-gates.php`, which already
provisions a Google account with a verified address.

## Files

- `tests/identity/run-contract-tests.php`
- `tests/integration/run-provider-gates.php`
- `tests/stubs.php` — one function, `email_exists()`
- No production file is touched.

## Steps

Three rules in the contract suite, two doors in the gate.

1. **An address `wp_users` already holds must not buy an OTP.** Drive
   `RegisterHandler::start_identity()` with such an address; it must refuse with
   `OMNIWP_identity_taken` and write nothing. The error **code** is asserted,
   not merely that something failed — this call can refuse for at least three
   unrelated reasons and two of them would report success at guarding an address
   they never looked at.

2. **One writer for a verified email.** No file outside `UserManager` may pair a
   `wp_update_user()` call with a `META_EMAIL_VERIFIED` write. **Reports PENDING
   until 14.2 exists**: a rule naming a function nobody has written yet passes for
   want of a subject, which is the mistake 10.0 made and 11.0 repeated.

3. **Proof is required to reach the directory.** `IdentityDirectory::link()` and
   `replace_in_channel()` must take a `VerifiedClaim`, asserted by reflection on
   the parameter type rather than by grepping for a spelling. **Passes today** and
   must keep passing — it is what stops 14.2 becoming a way to mint identities,
   and a rule arriving beside the feature it guards cannot catch that feature
   breaking it. Same argument as 13.0's rule 4.

**Door 1 (gate).** After the gate provisions its Google account, resolving that
account's own verified address under `AuthAction::LOGIN` must yield
`ISSUE_SESSION`.

**Door 2 (gate).** The same resolution under `AuthAction::RECOVER` must yield
`ISSUE_RESET_GRANT`.

Both fail until 14.4, and both are what that sub-phase turns green.

## Acceptance

Rule 1 fails. Rule 2 reports PENDING. Rule 3 passes. Every other suite at its
previous count, compared against a worktree of `HEAD` rather than from memory.

The gate is run on the real site, and **a BLOCKED gate is not a pass** — 10.3
shipped with its tracker row unticked for exactly this.

## Not in scope

Any production change. Any message rewording.

## Outcome

Landed red. No production file touched.

```text
The email identity (Phase 14)
  FAIL     a registration OTP is refused for an address wp_users already holds
           expected: 'OMNIWP_identity_taken'
           actual:   'no refusal at all'
  FAIL     and nothing is written while refusing
           expected: 0
           actual:   5

  PENDING  one writer owns a verified email
           blocked on: UserManager::adopt_verified_email() (14.2)

Identity contract: 39 → 41 passed, 2 failed, 1 pending
```

Every other suite byte-identical, verified by stashing and re-running rather than
by reading: regression 322, core 175, fitness 28, templates 91, admin 123, account
surface 7, abuse 28, delivery 46, mail 56 — before and after.

**`actual: 5` is the part worth keeping.** The rule was written expecting to prove
a missing refusal; what it also printed is that five writes have already happened
by then. The flow is not merely wrong at the end, it has spent an OTP row and
audit rows before reaching the wall. That number is the argument for 14.1 shipping
alone and first, and it came out of the detector rather than out of reading.

### The brief was wrong about where rules 1–3 belong

It said the three doors were all integration work. Two of them are — but the
*expensive* symptom is assertable against the stub, and putting it in the contract
suite means it runs on every commit instead of only when a WordPress is up. The
brief has been rewritten to match what was built; this section is the record that
it changed and why.

### The rule passed for the wrong reason first, exactly as predicted

The first version of rule 1 asserted only `is_wp_error()`. It went green
immediately — and the error was *"Số điện thoại không hợp lệ."* The stub's default
settings leave the email channel disabled, so `claim_any()` could not build an
email claim at all and the refusal had nothing to do with the address being taken.

Found by probing what the call actually returned, not by trusting the green. The
rule now enables the email channel explicitly and asserts the error **code**. This
is the third time this project has recorded a rule that passes for want of a
subject; the difference here is that it was caught in the same sitting.

### `email_exists()` rather than `get_user_by()`

The brief said `get_user_by( 'email', … )`, to have the owner id for the audit
record. `email_exists()` **returns** that id, so it is one stub instead of a
`WP_User` class — and a `WP_User` in `tests/stubs.php` would have collided with the
richer one in `template-stubs.php`, which declares it unguarded. Smaller surface,
same information. 14.1 should use `email_exists()`.

### The two doors were written unrun, and were vacuous when they finally ran

There was no local WordPress when this sub-phase landed, so the doors were committed
as parsing code and nothing more, with the tracker row unticked — 10.3's precedent.

When a Local site arrived at 14.4 they ran, went green, and **proved nothing**: an
email row left behind by an earlier run satisfied them whether or not the code under
test did anything. See 14.4's Outcome. They assert the owner id now, and the row here
was ticked only after the red-then-green sequence existed.

The lesson worth carrying: "written but unrun" is the right thing to say, and it is
not the same as "will be right once it runs".
