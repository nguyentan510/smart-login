# 14.6 — The security section

Spec: [`../email-identity.md`](../email-identity.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Stop the account page presenting a box that cannot be filled. Last,
because its branch depends on what 14.4 and 14.5 make true.

Today `templates/partials/account/password.php:41-51` renders *"Mật khẩu hiện tại"*
to everybody, and `FormController::save_password()` requires it whenever a new
password is typed (`class-form-controller.php:211`). For an account whose password
is the 64-character string the provisioner generated, that box is unsatisfiable, and
the refusal — *"Mật khẩu hiện tại không đúng."* — reads as a typo.

## Files

- `includes/Frontend/class-account-form.php` — one predicate
- `templates/partials/account/password.php`
- `tests/identity/run-account-surface-tests.php`

## Steps

1. `AccountForm` gains a predicate answering **"does the directory hold an `email`
   or `phone` row for this user"**, via `IdentityDirectory::for_user()`.

   **Not `is_synthetic_email()`.** A Google-first account has a real address in
   `user_email`, so that test answers false and routes the exact population this
   phase is about into the branch that cannot serve it. The spec records this as the
   wrong predicate that suggested itself first; the acceptance below pins it.

2. No contact identity: render no password inputs. One line pointing at the contact
   section — a password is not the missing piece, an identifier is, and offering the
   second step first is what the current screen does wrong.

3. Contact identity present: the three inputs as they are, plus a route to the reset
   flow for somebody who has no current password to type. Same door 14.3 opened, on
   a different screen.

4. `save_password()` is **unchanged**. It still requires the current password. The
   fix is not to weaken re-authentication for a case the code cannot identify — it is
   to stop offering the form to accounts it cannot serve, and to route them to a
   flow that proves ownership by OTP instead. This is where the earlier proposal to
   drop the re-auth gate was wrong: on an account with a verified email, planting a
   password creates a working login route that did not exist, so a borrowed session
   gains something rather than nothing.

## Acceptance

- A provider-only account renders **no** `password_current` input. Asserted on the
  markup, and asserted specifically for an account with a **non-synthetic**
  `user_email` and no email row — the case a synthetic-email predicate would get
  wrong. That is the assertion that has to exist for the predicate to be pinned.
- An account with an email or phone row renders all three inputs, unchanged.
- Posting a new password with a wrong current password is still refused, on both the
  standalone and the WooCommerce save path.
- Account-surface suite stays required and moves only by the added assertions.

## Not in scope

Any change to `save_password()`. Any marker meta. The CSS overflow on those inputs
was fixed separately in `b3ac585` and is not part of this phase.

### The fixture is the case a synthetic-email predicate gets wrong

`template-stubs.php`'s user has `user@example.test` — a real address, not a
placeholder. That is deliberately the Google-first shape, and it is why the two
renders differ only in what the directory returns. A predicate built on
`is_synthetic_email()` would answer *"has a contact"* here and go on rendering the
unfillable form, which is the wrong turn the spec recorded before implementation
began. The assertion is what stops a later change quietly taking it.

### One deliberate reduction from the brief, and it is a deferral not an omission

The brief said the contact-identity branch gains "a route to the reset flow". It gains
a **sentence**, not a link, because **the plugin has no addressable URL for its own
recovery screen from another page**:

- `Flow::url()` appends a step to the *current* URL. On the account page that renders
  `[smart_account]`, not `[smart_login]`, so the step would go nowhere.
- `wp_lostpassword_url()` lands on `wp-login.php` — exactly the leak
  `run-account-surface-tests.php` already forbids with *"the profile summary never
  sends a customer into wp-admin"*.
- There is no "login page" setting to read: grepped `includes/` for
  `lostpassword`, `login_page`, `login_url` and found nothing.

So the honest deliverable is a sentence naming the control by the words on it, and the
reason is written into the template where it is configured. Making it a link means a
configuration surface — a login-page setting — which is a decision rather than a line
of markup. 14.3 put the same door on the login screen itself, where the flow is
already in scope, and that is where somebody who cannot type a password actually is.

### `save_password()` is untouched, and asserted to be

The temptation this sub-phase exists to resist is dropping the re-auth gate for
accounts that cannot satisfy it. On an account with a verified email — which 14.4 and
14.5 have just made the normal case — planting a password without re-authentication
creates a working login route that did not exist, so a borrowed session would gain
something rather than nothing. The rule greps for the `wp_check_password()` call, so
removing it turns the suite red.

### Both surfaces, one branch

`AccountForm::args_for( 'password' )` feeds the standalone renderer and the
WooCommerce one, so the branch could not land on one screen and miss the other — which
is the defect Phase 8.2 existed to make unrepresentable, still holding two phases
later.
