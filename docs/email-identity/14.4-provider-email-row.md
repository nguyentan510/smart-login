# 14.4 — The provider email earns its row

Spec: [`../email-identity.md`](../email-identity.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** New provider logins adopt their verified address as an `email` identity,
per provider. This is the sub-phase that makes the three doors agree — and the one
that changes what an address can be used for, so it is gated and argued rather than
switched on quietly.

## Files

- `includes/class-field-registry.php` — two new rows
- `includes/Auth/class-account-provisioner.php` — `create_provider_user()` and the
  linking path
- `templates/partials/account/providers.php` or the admin provider card, whichever
  the help text lands on
- `tests/identity/run-contract-tests.php`, `tests/identity/run-admin-tests.php`,
  `tests/integration/run-provider-gates.php`

## Steps

1. `providers.google.email_identity` and `providers.zalo.email_identity`, declared
   literally beside the existing per-provider rows (`class-field-registry.php:298-325`)
   — the registry is not generated for providers and this phase does not change that.

   **Defaults: Google `1`, Zalo `0`.** Google asserts `email_verified` and that is
   the assertion being relied on; Zalo generally returns no email, and where it does
   the guarantee is not equivalent. `providers.auto_link_email` shipping at `1`
   (`:328`) is the precedent for a consequential linking default being on when the
   condition guarding it is a provider's own verification.

   **The Zalo claim is a hypothesis.** It is read from the provider class and the
   OAuth scope, not from a live Zalo response. Confirming it is part of this
   sub-phase, and if Zalo does assert a verified address the default is a decision to
   revisit in writing, not to leave as an assumption.

2. In `create_provider_user()`, after the account and the federated row exist, call
   `UserManager::adopt_verified_email()` when the flag is on, the provider set
   `email_verified`, and the address is non-empty. The `VerifiedClaim` carries
   `PROOF_OAUTH`.

   Ordering: the federated row is claimed first (`:116`), so a failure to adopt the
   email leaves an account that still works exactly as it does today. The email row
   is an addition, never a precondition.

3. The `auto_link_email` path (`:86-110`) adopts too, when the flag is on. It is
   already asserting that this address identifies this account — that is what the
   branch is for — so leaving it without a row would recreate the split inside the
   one branch that has already made the judgement.

4. Help text on the setting states what it grants, in one sentence: the address
   becomes a way to sign in and to recover the account. An administrator turning this
   on is widening how an account can be reached, and that belongs on the screen, not
   in this file.

## Acceptance

- 14.0's **two gate doors** go green. Both, in the same run — they are one cause.
- With the flag off, a provider login produces byte-identical state to today,
  asserted on the identities table.
- A provider login whose email the provider did **not** mark verified produces no
  email row, flag on or off.
- The integration gate re-runs all four provider markers, not just the new
  assertions: this sub-phase edits the provisioner, which every one of them
  exercises. 10.3 re-ran the other five markers for the same reason.
- Admin suite: the two new fields appear on exactly one tab each, which is the
  property `FieldRegistry` exists to guarantee and which 10.6's acceptance walked.

## Not in scope

Existing accounts — 14.5. Any change to what happens when two WordPress users share
an address; `auto_link_email` already fails closed there (`:97-99`) and that stays.

### Both doors were vacuous, and the gate passing is what exposed it

The first run on the Local site came back with all four provider markers green. That
looked like confirmation. It was not: reverting `AccountProvisioner` to its pre-14.4
state and re-running produced **the same green**.

The cause was leftover state. The earlier run had created
`email / google.staging@example.test → user 310`, the gate's cleanup retires only the
*federated* claim, and `wp_delete_user()` removed the user while the email row stayed
live. So every later run resolved that address to KNOWN — a dead user id, but KNOWN
is all `AuthAction::LOGIN` needs to answer `ISSUE_SESSION`. The assertion was
satisfied by a row from a previous run, whatever the code did.

Two fixes, and the first is the one that matters:

1. **The doors now pin the owner id** to the account this run provisioned, not merely
   "somebody". A stale row points at a different user, so it can no longer satisfy
   them. This is what turns the assertion into a statement about the run.
2. The email rows join `$cleanup_rows`, on the provisioning branch and the
   auto-link branch, so the gate stops accumulating what it created.

Then the sequence that was missing: three orphan rows removed, gate red with 14.4
out, gate green with 14.4 in. Only the second of those is evidence, and it needed the
first to mean anything.

The general lesson, which is the same one Phase 4 recorded about renames and 10.0
about vacuous rules: **an integration assertion against a shared database is
green-by-default unless it names the thing it just made.** A fresh unit suite starts
empty; a real database remembers every earlier attempt.

### A production defect found on the way, deliberately not fixed here

`wp_delete_user()` leaves `smartlogin_identities` rows live. Nothing in the plugin
hooks `deleted_user` — grepped, not assumed. Consequences:

- The subject stays claimed by a user that no longer exists, so `resolve()` answers
  KNOWN and `create_verified_user()` refuses with *"Tài khoản đã tồn tại."*
  **permanently**. That phone number or address can never be registered again.
- Login itself fails closed: `LoginHandler` asks `owner()`, gets `false` from
  `get_userdata()`, and returns the generic failure. So it is not a takeover, it is a
  denial.

It predates Phase 14 — the same shape as the `uninstall.php` flat key found in 10.2
and fixed later in its own commit. But **14.4 widens its reach**: every provider
account now has an email row, so deleting such a user strands their address as well
as their provider subject. Recorded in the tracker as a finding with a risk row, for
its own guard rail and its own commit.

### Phase 9's rule 8 caught the first version, correctly

The natural spelling was
`Settings::is_on( 'providers.' . $identity->provider . '.email_identity' )`, and the
abuse suite went red:

```text
  FAIL     no Settings::get() reads a key FieldRegistry does not declare
           → includes/Auth/class-account-provisioner.php:…  →  providers.
```

A built dot path that misses resolves to the fallback in silence — which is how the
configured retention was ignored for months, the defect rule 8 was written for. This
is the fourth sub-phase that rule has caught (10.5, 12.1, and the `uninstall.php`
find before them).

Fixed with `AccountProvisioner::EMAIL_IDENTITY_FLAG`, a map of literal paths, the
same shape 10.2 used for its legacy secret locations. But the map **opens a hole in
the rule that just caught me**: rule 8 skips calls whose first argument is a
variable, deliberately, so the field renderer does not make it cry wolf. So rule 8b
asserts every path in the map is declared, plus that the map is not empty — a rule
that passes for want of a subject states the opposite of the truth, which this phase
has already recorded once.

A provider absent from the map gets no row. Fail closed: adding a third provider
should not silently widen how its accounts can be reached.

### The Zalo hypothesis resolved from code, and better than the brief expected

The brief flagged the Zalo default as a hypothesis to confirm against a live
response. It is still not a live observation, but the code is more decisive than a
guess: `ZaloProvider` reads `'email_verified' => ! empty( $data['email_verified'] )`
(`class-zalo-provider.php:138`) from a Graph profile response that is not documented
to send that field, and the existing gate fixture encodes the same expectation by
asserting Zalo's identity comes back with an **empty** email.

So for Zalo the condition guarded by the flag cannot be met today whatever the flag
says. Default `0` stays, because the flag states the intent, and the real gate is
`email_verified` — which is where it belongs.

### Adoption is deliberately not fatal

It runs after the federated row is claimed, and a failure is audited rather than
returned. The email row is an addition; a provider login that cannot have one must
keep working exactly as it did. A failure leaves the account in the state every
provider account was in before this sub-phase — which is the state the rest of the
phase is built to tolerate.

The `auto_link_email` branch adopts as well. That branch has already decided the
address identifies the account — that is the whole of what auto-linking means — so
leaving it without a row would rebuild the same split inside the one place that has
judged it.

### One environmental failure, isolated rather than explained away

A full run reported `FAIL data/wards/29.php` from the syntax lint — a generated data
file this sub-phase does not touch. `php -l` on that file passes, and the lint passed
on four subsequent runs including inside the aggregate runner. The lint spawns one
child process per file, so a momentary file lock on Windows presents as a syntax
error. Recorded because "two runs are not a comparison" cuts both ways: a failure
that does not reproduce still has to be chased before it is dismissed, and this one
was.
