# 14.2 — One writer for a verified email

Spec: [`../email-identity.md`](../email-identity.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Extract `UserManager::adopt_verified_email()` and route the existing
writers through it. **Behaviour does not change.** The identity row is still not
granted to a provider email here — that is 14.4. This sub-phase only makes there be
one place able to grant it.

## Files

- `includes/Identity/class-user-manager.php` — the new method
- `includes/Auth/class-contact-verification-service.php` — `verify()`, email branch
- `includes/Frontend/class-woo-integration.php` — `save_account()`
- `tests/identity/run-contract-tests.php`, `tests/identity/run-fitness-tests.php`

## Steps

1. `UserManager::adopt_verified_email( int $user_id, VerifiedClaim $claim ): bool`.
   A `VerifiedClaim`, not a string plus a proof constant — the type is the gate, and
   only the PROVE layer can produce one. It performs, in this order:
   `replace_in_channel()`, `wp_update_user( user_email )`, `META_EMAIL_VERIFIED`,
   `delete META_SYNTHETIC`, `ProfileSeeder::seed_if_empty( billing_email )`.

   Order matters and is asserted: the directory write is the one that can fail on a
   race, and it must fail before `user_email` has moved.

2. `ContactVerificationService::verify()` calls it, replacing `:204-229`. This call
   site is the definition of correct — it is the only one doing all five things
   today, so the extracted body is its body.

3. `WooIntegration::save_account()` (`:266-269`) calls it **only** to the extent it
   already did. It has no `VerifiedClaim` and must not manufacture one; the address
   it sees has already been adopted by the OTP flow, because
   `block_unverified_email_change()` (`:223`) rejects every other route. So this site
   keeps its two-line housekeeping and gains a comment saying why it is not a
   caller. A deferral written down where it is configured, not a silent exception.

4. `AccountProvisioner` is **not** changed here.

The four new assertions are 14.0's rule 2 leaving PENDING plus three the extraction

### The docblock said the order was asserted, so it had to be

`adopt_verified_email()` claims its ordering is load-bearing: the directory write
can lose a race, and `user_email` must not have moved when it does. That sentence
was written before any test held it up, which is precisely the pattern CLAUDE.md
records twice — a README asserting a control that does not exist.

So the order is now asserted by forcing the claim to fail and checking that
`wp_update_user()` was never reached. And the rule was proven able to fail rather
than assumed: reversing the two blocks in the writer produces

```text
  FAIL     and user_email has not moved when it is
           expected: 0
           actual:   1
```

which is the shape a rule has to demonstrate before it is worth anything. Reverted
immediately; the committed order is directory-first.

### Signature changed from the brief: `true|WP_Error`, not `bool`

The brief specified `: bool`. `ContactVerificationService` passed
`wp_update_user()`'s own `WP_Error` back to the caller, and a boolean return would
have flattened that into "something went wrong" — a small loss of fidelity, in the
one path where the address is being changed. The channel guard returns an error too
(`OMNIWP_not_an_email`), so a phone claim cannot be quietly treated as an
email, which a `bool` would also have hidden.

### `tests/stubs.php` gained `wp_update_user()`

Recording, not executing: the assertions are about whether a write happened and in
what order, not about what WordPress would store. Nothing previously reached it,
which is why its absence had never surfaced.

### What rule 2 deliberately does not catch

`AccountProvisioner:171` writes `META_EMAIL_VERIFIED` **without** a
`wp_update_user()` call, so the pairing rule does not flag it — and that partial
write is the defect this whole phase is about. It is left to the two gate doors,
which catch it behaviourally, and to 14.4, which routes the provisioner through this
writer. Strengthening rule 2 to "no file outside `UserManager` touches this meta key
at all" would have gone red here and stayed red until 14.4, which is a legitimate
alternative and would have re-scoped a sub-phase whose whole point is being
invisible. Recorded so the gap is a decision rather than an oversight.

### Sweep

`META_EMAIL_VERIFIED`, `META_SYNTHETIC`, `billing_email`, `replace_in_channel`
across `includes/`, `templates/`, `tests/`, `docs/`, `uninstall.php`, `README.md`
and `readme.txt`. No key changed name, so `uninstall.php:60` needs nothing.
`RegisterHandler:366` **reads** the meta and is not a writer. `$now` in
`ContactVerificationService` is still used by the phone branch after the email
branch left — checked, because a signature/body pair desynchronised by a move is
the failure Phase 7 recorded and `php -l` cannot see it.

**One stale claim found, not fixed here.** `create_verified_user()`'s comment says
the meta keys are documented in README "as a public contract for other plugins".
They are not: README names `OmniWP_ward_code` and nothing else of this family.
Out of scope for an invisible refactor, and the kind of sentence this project has
twice been bitten by.
