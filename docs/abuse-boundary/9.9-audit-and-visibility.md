# 9.9 — Audit cap, operator screen, and the settings-key rule

Spec: [`../abuse-boundary.md`](../abuse-boundary.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Stop the audit log amplifying the attack it records, make the data
usable, and pin the defect class that hid a live bug for a whole refactor.

Three things, one sub-phase, because they share a file and a test.

## Files

- `includes/Security/class-audit-log.php`
- `includes/Admin/Screens/class-audit-screen.php`
- `includes/class-installer.php` — the two-line fix
- `includes/OTP/class-otp-repository.php`
- `includes/class-field-registry.php`
- `tests/security/run-abuse-tests.php`

## (a) Cap the audit write

`AuditLog::record()` writes a row per failed request, so an attack costs an
unbounded `INSERT` stream and a table that outgrows its daily sweep. The audit
log is currently an amplification vector for the attack it is supposed to record.

1. Hourly counter per event type. Past `security.audit_max_per_event_hour`
   (default 500), stop writing individual rows and write **one aggregated row per
   hour** — `event = <name>_summary`, `meta.count = n` — so the signal survives
   even when the detail does not.
2. **Never sampled**, whatever the volume: `lockout`, `user_registered`,
   `password_reset`, `otp_budget_halted`, every `provider_*`. The spec explains
   why.

## (b) The operator screen

`AuditScreen` today is a flat list of 50 rows with no filter. The data exists and
cannot be used.

1. Filters: event type, date range, masked identity.
2. A summary strip above it: codes sent this hour and today, budget consumed
   against ceiling, failure rate, breaker state, kill-switch state.
3. Estimated spend, driven by a new `otp.sms_unit_cost` (default 0 = hide).

Point 3 is what makes [9.1](9.1-site-budget.md)'s ceiling tunable on evidence
rather than guessed at. Reuses `count_recent_all()` from 9.1 plus a new
`count_by_transport_since()`.

## (c) The settings-key rule, and the live defect that motivated it

`Installer::cleanup()` (`class-installer.php:362-363`) reads:

```php
$otp_days   = max( 1, Settings::get_int( 'otp_retention_days', 7 ) );
$audit_days = max( 1, Settings::get_int( 'audit_retention_days', 90 ) );
```

`FieldRegistry` declares those keys as **`advanced.otp_retention_days`** and
**`advanced.audit_retention_days`**. `Settings::get()` resolves by dot path, so
both reads miss, both fall back to the hardcoded literal, and **the retention
values an operator sets have never taken effect.** The migration map at
`class-installer.php:146-147` records the correct rename; the call sites two
hundred lines below were not updated with it.

The fix is two lines. The interesting part is that nothing could have caught it —
this is the fifth rename in this project to cross a boundary no test covered,
after `purpose`/`intent`, `$default`/`$fallback`, and the two the 8.1 brief
records.

So: **rule 8** extracts every string literal passed to `Settings::get()`,
`get_int()` and `is_on()`, compares against `FieldRegistry::all()`, and fails on
anything undeclared, with a declared allowlist for genuinely dynamic paths.

This is the same move the `FieldRegistry` rewrite already made for the four-way
schema drift: turn a class of bug into something the tree cannot represent
without going red.

## Acceptance

Rules 7 and 8 green. Rule 8 **fails on the tree before the `cleanup()` fix and
passes after** — demonstrated in that order, since a rule first observed passing
proves nothing. The screen reports a non-zero hourly count after a seeded send.

## Not in scope

Retention policy itself. This sub-phase makes the configured value take effect;
what the value should be is the operator's.

## Outcome

Rules 7 and 8 green. `Regression: 280 passed, 0 failed` (was 272). Abuse boundary
`19 passed, 1 failed` — only rule 6 (9.7) left. phpcs at baseline, and the full
integration chain green on WordPress 7.0.2.

### The kill switch was shedding less load than 9.1 claimed

Writing (a) turned up a correction to this phase's own record. The 9.1 commit
says a sustained attack "sheds load instead of adding to it". Half true:
`RateLimiter` does return before the three counting queries, but
`OtpService::issue()` still calls `AuditLog::record( RATE_LIMITED )` on **every**
blocked request (`class-otp-service.php:83`). A halted site was shedding three
SELECTs and keeping one INSERT.

So the audit cap is not polish sitting next to the kill switch — it is the other
half of the same mechanism. At 500 requests/second the log alone would take the
database down while the budget congratulated itself on having capped spending.

### The cap writes one row saying it stopped writing

Past the cap the event stops recording individual rows and writes a single
`<event>_summary` row for that hour, then nothing. Silence would be the wrong
failure: an operator reading the log during an attack must not conclude the
attack stopped because the rows did.

`NEVER_SAMPLED` covers lockouts, registrations, password resets, budget halts,
breaker openings, identity retirements and every provider event — all low-volume,
all forensically load-bearing. A cap that drops those to survive a flood has
discarded the record of the flood.

### The retention bug, and the proof it was real

Two lines. `Installer::cleanup()` read `otp_retention_days` and
`audit_retention_days`; the registry declares them under `advanced.`. Both reads
missed, both fell back to the hardcoded 7/90, and **the retention an operator
configured had never once taken effect** since the settings rewrite.

It is asserted through the SQL the stub captures — set 3 and 11 days, run
`cleanup()`, check the two `DELETE` statements carry those dates. That angle was
chosen because the bug was invisible from every other one: the code looked
correct, the setting saved correctly, the screen displayed it correctly, and the
sweep quietly ignored it.

Rule 8 is what makes the class unrepresentable rather than this instance fixed.

### Visibility without building the dashboard

The brief scoped a full operator screen. What shipped is smaller and, for the
risk that actually exists, most of the value: the readiness row now reports
**consumption** — codes sent this hour against the ceiling, SMS today, estimated
spend when `otp.sms_unit_cost` is set — and turns amber at 80% of the hourly
ceiling.

The reasoning: 9.1's ceilings shipped with numbers chosen for plausibility, not
measured from any real site. The operational risk is a legitimate campaign
tripping the switch, and an amber row at 80% addresses that at a fraction of the
cost of a dashboard. The filtered log view remains unbuilt and is recorded here
rather than quietly dropped.

### The kill switch finally has an off switch

`RateLimiter::resume()` shipped in 9.1 tested and unreachable — nothing outside
the tests called it. The overview screen now renders a warning while a halt is
active, with a nonce-protected `admin-post` button behind
`current_user_can( 'manage_options' )`, and the button's description says to read
the log first. A control that can only be waited out is not a control.
