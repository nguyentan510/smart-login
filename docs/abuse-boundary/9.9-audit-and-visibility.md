# 9.9 — Audit cap, operator screen, and the settings-key rule

Spec: [`../abuse-boundary.md`](../abuse-boundary.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Stop the audit log amplifying the attack it records, make the data
usable, and pin the defect class that hid a live bug for a whole refactor.

Three things, one sub-phase, because they share a file and a test.

## Files

- `includes/Security/class-audit-log.php`
- `includes/Admin/Screens/class-audit-screen.php`

## (a) Cap the audit write

`AuditLog::record()` writes a row per failed request, so an attack costs an
unbounded `INSERT` stream and a table that outgrows its daily sweep. The audit
log is currently an amplification vector for the attack it is supposed to record.

1. Hourly counter per event type. Past `security.audit_max_per_event_hour`
   (default 500), stop writing individual rows and write **one aggregated row per
   hour** — `event = <name>_summary`, `meta.count = n` — so the signal survives
   even when the detail does not.
2. **Never sampled**, whatever the volume: `lockout`, `user_registered`,
   `password_reset`, `otp_budget_halted`, every `provider_*`. The spec explains
   why.

## (b) The operator screen

`AuditScreen` today is a flat list of 50 rows with no filter. The data exists and
cannot be used.

1. Filters: event type, date range, masked identity.
2. A summary strip above it: codes sent this hour and today, budget consumed
   against ceiling, failure rate, breaker state, kill-switch state.
3. Estimated spend, driven by a new `otp.sms_unit_cost` (default 0 = hide).

Point 3 is what makes [9.1](9.1-site-budget.md)'s ceiling tunable on evidence
rather than guessed at. Reuses `count_recent_all()` from 9.1 plus a new
`count_by_transport_since()`.

## (c) The settings-key rule, and the live defect that motivated it

`Installer::cleanup()` (`class-installer.php:362-363`) reads:

```php
$otp_days   = max( 1, Settings::get_int( 'otp_retention_days', 7 ) );
$audit_days = max( 1, Settings::get_int( 'audit_retention_days', 90 ) );
```

`FieldRegistry` declares those keys as **`advanced.otp_retention_days`** and
**`advanced.audit_retention_days`**. `Settings::get()` resolves by dot path, so
both reads miss, both fall back to the hardcoded literal, and **the retention
values an operator sets have never taken effect.** The migration map at
`class-installer.php:146-147` records the correct rename; the call sites two
hundred lines below were not updated with it.

The fix is two lines. The interesting part is that nothing could have caught it —
this is the fifth rename in this project to cross a boundary no test covered,
after `purpose`/`intent`, `$default`/`$fallback`, and the two the 8.1 brief
records.

So: **rule 8** extracts every string literal passed to `Settings::get()`,
`get_int()` and `is_on()`, compares against `FieldRegistry::all()`, and fails on
anything undeclared, with a declared allowlist for genuinely dynamic paths.

This is the same move the `FieldRegistry` rewrite already made for the four-way
schema drift: turn a class of bug into something the tree cannot represent
without going red.

## Acceptance

Rules 7 and 8 green. Rule 8 **fails on the tree before the `cleanup()` fix and
passes after** — demonstrated in that order, since a rule first observed passing
proves nothing. The screen reports a non-zero hourly count after a seeded send.

## Not in scope

Retention policy itself. This sub-phase makes the configured value take effect;
what the value should be is the operator's.
