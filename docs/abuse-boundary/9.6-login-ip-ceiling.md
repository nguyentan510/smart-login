# 9.6 — Per-IP login failure ceiling

Spec: [`../abuse-boundary.md`](../abuse-boundary.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Blocked on [9.5](9.5-trusted-proxy.md).** Shipping this first turns a security
control into an outage: on a site behind a CDN with proxy trust off, every
visitor shares one edge address and the ceiling locks all of them out together.

**Goal.** Catch the horizontal sweep that the per-account lockout cannot see.

Lockout is keyed `md5( canonical_identity + IP )`
(`class-rate-limiter.php:100`). Collapsing `0969…`, `+84 969…` and `84969…` into
one counter is good work and stays. But password spraying — one common password
against ten thousand accounts from one address — never trips it: each account
records a single failure and none reaches 5. Spraying is the more common of the
two attacks, and it passes through untouched.

## Files

- `includes/Security/class-rate-limiter.php`
- `includes/Auth/class-login-handler.php`
- `includes/class-field-registry.php`
- `includes/Admin/class-readiness.php`

## Steps

1. **Two settings:** `security.max_login_failures_per_ip_hour` (default 30) and
   `security.ip_lockout_minutes` (default 15). Deliberately looser than the
   per-account 5/15 — a shared office NAT, a school or mobile CGNAT puts many
   legitimate people on one address. The per-account counter remains the tight
   control; this one exists only to catch the sweep.

2. `record_login_failure()` increments both counters.

3. `LoginHandler::gate_lockout()` checks the IP lock alongside the identity lock.
   Correctly on the `authenticate` filter, so `wp-login.php`, WooCommerce and
   application passwords are covered by one control.

4. **Count every failure**, including ones for identifiers that resolve to
   nothing. Spraying uses valid identifiers, and excluding unresolved ones would
   only add an oracle for free.

5. **Readiness WARN** when this ceiling is enabled while the proxy configuration
   looks wrong — trust off with CF headers present. That combination is what
   produces the mass lockout, and it is worth naming on screen rather than
   leaving to the ordering constraint alone.

## Acceptance

Thirty failures across thirty **distinct** identifiers from one IP produce a lock
on the 31st; a different IP is unaffected; the per-account counter still trips
independently at 5. All three asserted, because the first without the third would
mean the new ceiling had swallowed the old one.

## Not in scope

Changing the per-account lockout, its window, or its key.
