# 9.0 — Guard rails

Spec: [`../abuse-boundary.md`](../abuse-boundary.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Land the rules that detect every defect in this phase *before* any of
them is fixed, so each rule can be demonstrated red on the current tree.

The Postscript in the tracker already argues this for Phase 8, and Phase 9 has
its own reason to insist: seven of the eight rules below concern controls that do
not exist yet. A rule written after the control cannot fail, and a rule that has
never failed is a comment.

## What has to be built before any rule can be written

Measured, not assumed. Three of the eight rules cannot be expressed with the
harness as it stands, so 9.0 is mostly infrastructure and only then rules.

1. **Method-level granularity.** `sl_forbid_pattern` and `sl_require_companion`
   run `preg_match` over a whole file. Rule 4 is an *ordering* property and rule 6
   is a *per-callback* property; neither survives a file-level match — one
   `verify_rest` anywhere in `class-rest-controller.php` satisfies a file-level
   regex while nine of ten callbacks call nothing.

   Add `sl_method_body()` to the harness, using `token_get_all()`: walk tokens,
   catch `T_FUNCTION`, brace-count to the end. ~30 lines, shared by both rules.

2. **A filter registry in the stubs.** `apply_filters( $hook, $value )` returns
   `$value` and ignores registered filters, so rule 5 cannot turn
   `smart_login_trust_proxy_headers` on. Add `add_filter()` support, strictly
   backwards-compatible: an empty registry must behave exactly as today.

   **Blast radius:** `stubs.php` is loaded by four suites including
   `run-tests.php`, which `harness.php` calls a working asset that must not be
   destabilised. Run the full suite before and after and show it unchanged.

3. **A fake repository, not a smarter `$wpdb`.** The stub is deliberately dumb —
   `get_var()` returns one global regardless of the query, so
   `count_recent_by_destination`, `count_recent_by_ip` and the new
   `count_recent_all` are indistinguishable. Rule 1 would be theatre.

   No production change is needed: `RateLimiter::__construct( ?OtpRepository )`
   already injects, and none of the classes involved are `final`. Subclass the
   repository in the test and record which method was asked.

   Rule 7 needs none of this — `AuditLog::record()` writes through `$wpdb->insert`
   and the stub already records every write in `$wpdb->writes`.

## Why rule 3 is three assertions

The first draft of this brief said "clamps timeout ≤ 15s", which was wrong twice.
The clamp already exists — `sms.timeout` is `min 3, max 30`
(`class-field-registry.php:406`) — so the work is tightening 30 → 15, not adding
a ceiling.

And the clamp runs in `Settings::sanitize()`, i.e. **at save time**
(`class-settings.php:303`). A site that already stored `30` keeps `30` after the
maximum drops to 15, until somebody re-saves that tab. Asserting the registry
therefore does **not** prove the runtime timeout is bounded, which is why 3c
exists and why 9.3 gained a read-time clamp.

## Rule 4 depends on a uniqueness that must itself be asserted

`resolve(` appears exactly once in `class-form-controller.php` (line 327), so
comparing source offsets is sound. That is a property of today's tree, not a law.
The rule asserts the uniqueness too — otherwise a second `resolve()` added later
would silently make the ordering check meaningless while it kept reporting green.

## Rule 8 deserves its own note

It is the only rule here that fails on a defect **already shipped**:
`Installer::cleanup()` reads `otp_retention_days` while `FieldRegistry` declares
`advanced.otp_retention_days` (see [9.9](9.9-audit-and-visibility.md)). So it is
the one rule whose red output proves the detector works rather than merely
proving a feature is absent.

Scope was measured before committing to it — 57 keys declared, 54 read as
literals, **exactly 2 undeclared**, both the known pair. No collateral, so 9.9
stays the size it was scoped at.

Implement as a scan for string literals passed to `Settings::get()`, `get_int()`
and `is_on()`, compared against `FieldRegistry::all()`. It must **skip calls
whose first argument is a variable** — there are nine, in
`class-field-renderer.php` and `class-provider-credentials.php` — or it reports
false positives on day one.

## Acceptance

The suite reports **9 FAIL and 1 PENDING** on the current tree, names the
offending file and line for each static rule, and `run-all.php` still exits 0
because the suite is `spec`.

Ten, not eight, because rule 3 is three assertions. And rule 5 is `sl_pending()`
rather than a failure: until the stub registry lands it cannot be *evaluated*,
which is a different claim from "the control is missing" — the harness has that
vocabulary precisely so a red run reads as a to-do list, and "pending is not a
pass".

The eight remaining suites must be **byte-identical** before and after the
`stubs.php` change.

## Outcome

**`Abuse boundary: 4 passed, 11 failed, 0 pending`**, and `run-all.php` exits 0
with the suite registered `spec`. No production file was touched.

The Acceptance above is left as written, because it was the prediction and it was
wrong in both directions. What actually happened:

**The PENDING disappeared.** Rule 5 was forecast as unevaluable until the stub
gained a filter registry — but that registry landed *in this sub-phase*, so by
the time the rule was written it could be evaluated after all. It is two
failures, not one pending: `Client::in_cidr()` does not exist, and with trust
forced on the header is returned from an unverified peer.

**Eleven failures, not nine**, because rule 3 is three assertions and rule 5 is
two. The four passes are all *premise guards* rather than controls: a Vietnamese
mobile is still valid, `handle_identify()` performs exactly one lookup,
`register_routes()` yields callbacks to inspect, and trust-off returns
`REMOTE_ADDR`. They exist to keep the failing rules honest — the uniqueness check
in particular, without which a second `resolve()` would silently void rule 4
while it kept reporting green.

### The comment problem, which was not in the plan

The first working `sl_method_body()` returned `resolve(` **twice** from
`handle_identify()`: once as the call, once inside the sentence explaining that
`resolve()` cannot return `CONFLICT`. An ordering rule reading prose is a rule
that changes colour when somebody rewords a comment, so the extractor now strips
`T_COMMENT` and `T_DOC_COMMENT`.

Found by running the extractor against the real file before writing any rule with
it, rather than by reading it back.

### The stubs change is proven, not argued

`stubs.php` is loaded by four suites, one of which `harness.php` calls a working
asset that must not be destabilised. Full suite captured before and after with
the change stashed and unstashed:

```text
IDENTICAL — 8 suites unchanged by the stubs/harness change
```

`admin-stubs.php` lost its no-op `add_filter()` in the process — it is only ever
loaded after `stubs.php`, so leaving both would be a redeclaration fatal, and the
no-op would have won nothing.

### Rule 8's scope was measured before it was committed to

57 keys declared, 54 read as literals, **exactly 2 undeclared** — both halves of
the known `Installer::cleanup()` pair. No collateral, so 9.9 stays the size it
was scoped at. The rule skips the nine dynamic-path call sites in
`class-field-renderer.php` and `class-provider-credentials.php`; without that
exclusion it would have reported false positives immediately.

### What the red run says about the phase

Rule 6 is the one worth reading twice: **1 of 11** REST callbacks reaches
`verify_rest()`. That is a wider gap than 9.7's brief assumed when it was
written from a file-level reading, and it is the kind of thing only per-method
granularity can show.

`phpcs` is unaffected — `phpcs.xml` excludes `/tests/*` by design, and this
sub-phase changed nothing else.
