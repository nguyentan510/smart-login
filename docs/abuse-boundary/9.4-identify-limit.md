# 9.4 — Rate-limit the identify step

Spec: [`../abuse-boundary.md`](../abuse-boundary.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Close the enumeration oracle, and make the README true.

Two things are wrong and the documentation one is the more serious. README
§"Bước 1 dùng chung" states that `RateLimiter` blocks enumeration on both IP and
destination. It does not, on the branch that matters: `RateLimiter` is reached
only from inside `OtpService::issue()`, i.e. the *"no such account"* path. When
the subject exists, `handle_identify()` calls `password_step()`
(`class-form-controller.php:329`) and returns having passed through no limiter at
all.

So the site's registered phone numbers can be enumerated at zero cost and
unbounded rate, with one nonce that stays valid all day — and a reader auditing
the plugin concludes otherwise, because the README says so.

## Files

- `includes/Security/class-rate-limiter.php`
- `includes/Frontend/class-form-controller.php`
- `includes/class-field-registry.php`
- `README.md`

## Steps

1. **`RateLimiter::check_identify( string $identity ): true|WP_Error`**, keyed on
   **IP alone**. The identity is the attacker's variable; keying on it would hand
   out a fresh budget per guess, which is the defect being fixed.

2. **Fixed hourly bucket** (`date( 'YmdH' )`) in a transient — self-expiring, no
   sweeping. It allows roughly a 2× burst across the hour boundary. Accepted and
   recorded here rather than solved with a rolling window that costs more than
   the problem does.

3. **New setting** `security.max_identify_per_ip_hour`, default 30.

4. **Call site: top of `handle_identify()`**, after `RequestGuard::verify()` and
   **before** the `IdentityDirectory` lookup, so both branches are covered by
   construction. Placing it after the lookup leaves the oracle intact — the
   lookup *is* the oracle.

5. On exceed: generic error, `AuditLog::RATE_LIMITED` with `reason => 'identify'`.

6. **Correct the README.** After this sub-phase the sentence becomes true, so it
   is a correction, not a caveat.

## The rule guards the future, not just the fix

There is no `/identify` REST route today; the flow is form-only. Rule 4 should
therefore also assert that **no** REST callback reaches
`IdentityDirectory::resolve()` without passing `check_identify()`, so the gap
cannot be reopened by a route added later. A rule that only pins the current call
site would let the next one through.

## Acceptance

Rule 4 green. The 31st identify from one IP within the hour is refused **whether
the subject exists or not**, and the refusal is byte-identical in both cases —
asserted on the response, since a difference there is the oracle in another form.

## Not in scope

The challenge shown when the ceiling is approached — [9.8](9.8-adaptive-captcha.md)
reads this counter as one of its pressure signals.

## Outcome

Rule 4 green, both halves. `Regression: 245 passed, 0 failed` (was 238). Abuse
boundary `12 passed, 5 failed`. phpcs at baseline. The last of the four release
blockers.

### The rule found a second door, and it was the same door

The brief scoped this to `handle_identify()`. The future-proofing assertion — no
entry point resolves a subject without spending the budget — immediately named
two more files, and one of them was a real instance of the same defect:

**`PasswordResetHandler::start()`** resolves the subject, and when there is no
account it returns *without issuing a code*. So it never reaches
`RateLimiter::check_otp_send()`, and forgot-password was a free, unmetered
enumeration oracle sitting beside the one being closed. Closing only the identify
screen would have moved the attacker one form to the left.

It now spends the same budget. This is the working agreement's "prefer making a
bug class unrepresentable over fixing one instance" arriving as a concrete diff
rather than as a principle — and it was the rule that found it, not a reading of
the code.

**`UserManager::create_verified_user()`** is the other, and it is genuinely fine:
it resolves to check ownership during account creation, reachable only after an
OTP has been verified. Allowlisted with that reason written at the exemption, as
the fitness rules require.

### Keyed on IP, and the refusal is branch-blind

Two properties carry this control, and both are asserted rather than described:

- **One budget across identifiers.** Keying on the identity would hand out a
  fresh allowance per guess, which is the hole itself. Three distinct
  identifiers from one address share one counter; the fourth is refused.
- **The refusal cannot depend on whether the subject exists.** A limit that
  answered differently for known and unknown subjects would *be* the oracle it
  was built to close. The check runs before the lookup, so it cannot know.

### The hourly bucket, and what it gives up

A fixed `YmdH` bucket rather than a rolling window: it expires on its own, needs
no sweeping, and costs one transient read. It allows roughly a 2× burst across
the hour boundary. That is accepted and written down rather than solved — a
rolling window costs more than the problem does, and 60 lookups in the wrong two
minutes is not the attack this defends against.

### The README claim is now true

The sentence asserting that `RateLimiter` blocks enumeration on both IP and
destination was false for the branch that mattered. It has been replaced with
what the code actually does, including the forgot-password path. That was the
more serious half of this sub-phase: a reader auditing the plugin would have
concluded it was covered.
