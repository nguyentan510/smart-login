# 9.5 — Trusted proxy configuration

Spec: [`../abuse-boundary.md`](../abuse-boundary.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Make the plugin's IP correct on the deployment nearly every Vietnamese
site actually uses.

`Client::ip()` defaults to `REMOTE_ADDR` and reads proxy headers only when
`smart_login_trust_proxy_headers` returns true. The default is right and the
comment explaining it is right. The problem is that the filter is the **only**
interface — no settings control, no readiness check, one mention in a hook list
at the bottom of the README.

Behind Cloudflare with the filter untouched: unrelated visitors share one edge
address and hit `max_per_ip_hour` as a group, per-IP limiting stops meaning
anything, and every audit row records Cloudflare rather than the client.

The spec explains why a plain boolean would be worse than nothing.

## Steps

1. **Two settings:** `security.trust_proxy` (checkbox, default 0) and
   `security.trusted_proxy_cidrs` (textarea, default empty). No Cloudflare range
   list is shipped — the help text links <https://www.cloudflare.com/ips/>.

2. **Resolution order in `Client::ip()`:**
   1. read `REMOTE_ADDR`
   2. if `trust_proxy` **and** `REMOTE_ADDR` matches a configured CIDR → take the
      first syntactically valid address from the header chain
   3. otherwise `REMOTE_ADDR`

3. **`Client::in_cidr( string $ip, string $cidr ): bool`**, v4 and v6, kept pure
   so it is testable without WordPress.

4. **Back-compat.** `smart_login_trust_proxy_headers` returning true keeps working
   as an unconditional override, documented as the deployment-managed escape
   hatch. It is not removed: a filter that exists in a released README is an
   interface.

5. **Readiness — this is the part that closes the gap:**
   - `trust_proxy` on with an empty CIDR list → **FAIL**. That configuration is
     strictly worse than trusting nothing, because it is the spoofable one.
   - `trust_proxy` off while `HTTP_CF_RAY` or `HTTP_CF_CONNECTING_IP` is present
     → **WARN** with a direct link. Header presence detects the situation with no
     IP list to maintain, which is why it beats range matching here.

6. **Break the silence at `count_recent_by_ip( null )`.** It returns 0, so per-IP
   limiting switches itself off when the IP is unknown. Per the spec it **stays**
   fail-open; what it gains is an hourly-throttled audit warning so the condition
   is observable instead of invisible.

## Acceptance

Rule 5 green, asserted by stubbing `$_SERVER` in both directions: with trust on
and CIDRs set, a header from an in-range peer is honoured and the **identical**
header from an out-of-range peer is ignored. Readiness turns red on
trust-on-with-no-CIDRs.

## Not in scope

Any change to what the per-IP ceilings are. [9.6](9.6-login-ip-ceiling.md) adds
one and is blocked on this sub-phase for exactly that reason.
