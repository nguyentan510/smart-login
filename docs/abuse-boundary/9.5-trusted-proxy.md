# 9.5 — Trusted proxy configuration

Spec: [`../abuse-boundary.md`](../abuse-boundary.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Make the plugin's IP correct on the deployment nearly every Vietnamese
site actually uses.

`Client::ip()` defaults to `REMOTE_ADDR` and reads proxy headers only when
`smart_login_trust_proxy_headers` returns true. The default is right and the
comment explaining it is right. The problem is that the filter is the **only**
interface — no settings control, no readiness check, one mention in a hook list
at the bottom of the README.

Behind Cloudflare with the filter untouched: unrelated visitors share one edge
address and hit `max_per_ip_hour` as a group, per-IP limiting stops meaning
anything, and every audit row records Cloudflare rather than the client.

The spec explains why a plain boolean would be worse than nothing.

## Steps

1. **Two settings:** `security.trust_proxy` (checkbox, default 0) and
   `security.trusted_proxy_cidrs` (textarea, default empty). No Cloudflare range
   list is shipped — the help text links <https://www.cloudflare.com/ips/>.

2. **Resolution order in `Client::ip()`:**
   1. read `REMOTE_ADDR`
   2. if `trust_proxy` **and** `REMOTE_ADDR` matches a configured CIDR → take the
      first syntactically valid address from the header chain
   3. otherwise `REMOTE_ADDR`

3. **`Client::in_cidr( string $ip, string $cidr ): bool`**, v4 and v6, kept pure
   so it is testable without WordPress.

4. **Back-compat.** `smart_login_trust_proxy_headers` returning true keeps working
   as an unconditional override, documented as the deployment-managed escape
   hatch. It is not removed: a filter that exists in a released README is an
   interface.

5. **Readiness — this is the part that closes the gap:**
   - `trust_proxy` on with an empty CIDR list → **FAIL**. That configuration is
     strictly worse than trusting nothing, because it is the spoofable one.
   - `trust_proxy` off while `HTTP_CF_RAY` or `HTTP_CF_CONNECTING_IP` is present
     → **WARN** with a direct link. Header presence detects the situation with no
     IP list to maintain, which is why it beats range matching here.

6. **Break the silence at `count_recent_by_ip( null )`.** It returns 0, so per-IP
   limiting switches itself off when the IP is unknown. Per the spec it **stays**
   fail-open; what it gains is an hourly-throttled audit warning so the condition
   is observable instead of invisible.

## Acceptance

Rule 5 green, asserted by stubbing `$_SERVER` in both directions: with trust on
and CIDRs set, a header from an in-range peer is honoured and the **identical**
header from an out-of-range peer is ignored. Readiness turns red on
trust-on-with-no-CIDRs.

## Not in scope

Any change to what the per-IP ceilings are. [9.6](9.6-login-ip-ceiling.md) adds
one and is blocked on this sub-phase for exactly that reason.

## Outcome

Rule 5 green, both assertions. `Regression: 266 passed, 0 failed` (was 245).
Abuse boundary `14 passed, 3 failed`. phpcs at baseline.

### The brief's back-compat decision was wrong, and the rule said so

The brief committed to keeping `smart_login_trust_proxy_headers` as an
**unconditional** override — "a filter that exists in a released README is an
interface". Rule 5, written earlier in 9.0, asserts the opposite: with trust on
but no trusted range, the header must still be ignored.

The rule is right and the brief was wrong. An escape hatch that can reopen the
exact hole the control exists to close is not an escape hatch, and the security
property has to be absolute or it is not a property: *no configuration may make a
forwarded header trusted from an unverified peer.*

Resolved without stranding managed deployments: the filter now **enables**
proxy handling rather than granting it, and a second filter,
`smart_login_trusted_proxy_cidrs`, supplies the ranges from code. A deployment
that used only the old filter must add one line — documented in the README, and
worth the breakage because the old behaviour was the vulnerability.

Recorded at length because this is a decision being reversed, not a rule being
bent to fit code. The distinction is the whole reason 9.3's rule was rewritten
and 9.2's was not.

### The parse bug worth having a test for

`explode( '/', '10.0.0.0/oops' )` then `(int) 'oops'` is `0`, and `/0` matches
every address on the internet. A typo in the settings box would have silently
turned the allowlist into "trust everyone" — the precise configuration this
sub-phase exists to prevent, arriving through the field meant to prevent it.

`ctype_digit()` on the suffix rejects it, and there is a test named after the
failure rather than after the fix. Readiness also fails outright on any range
ending in `/0`, since that is the same hole spelled correctly.

### Both address families, and the mismatch case

`inet_pton()` normalises v4 and v6 into packed bytes of known length, so the
comparison is byte-then-bitmask with no string parsing. A v4 address tested
against a v6 range differs in packed length; that is checked rather than assumed,
because comparing four bytes against sixteen would otherwise match on prefix.

Non-byte-boundary prefixes are the ones that actually break naive
implementations, so `/20` is tested from both sides — `173.245.63.255` inside and
`173.245.64.0` outside.

### A test that was wrong, not a control that was

`the legacy filter alone does not grant trust` failed on first run. The cause was
in the test: it cleared `security.trust_proxy` but left the CIDR list populated
from the previous block, so the peer genuinely was trusted and the code was
right. Fixed the fixture, not the code — the same question 9.3 raised, answered
the other way this time.

### The silence at `count_recent_by_ip( null )` is broken, the behaviour is not

Still fails open, for the reason the spec gives. What changed is that it now
records an hourly-throttled audit warning, so a per-IP limit that has quietly
stopped applying is visible instead of inferred from a surprise.
