# 9.3 — Delivery timeout and circuit breaker

Spec: [`../abuse-boundary.md`](../abuse-boundary.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Stop a slow gateway from taking the whole site down.

`WebhookTransport::dispatch()` runs `wp_remote_request()` inside the visitor's
request at a default 10-second timeout, and the retry path adds
`usleep( 2000000 )` (`class-webhook-transport.php:134`) — up to ~22 seconds
holding one PHP worker. At 10 requests/second against a slow gateway, 100 workers
are occupied; a typical PHP-FPM pool is 20–50. Sign-in is not what goes down; the
site is. No attacker sophistication is required beyond noticing the gateway is
slow.

The spec explains why queueing is not the answer here.

## Files

- `includes/OTP/Transports/class-webhook-transport.php`
- `includes/OTP/Transports/class-circuit-breaker.php` — new
- `includes/OTP/Transports/class-transport-router.php`
- `includes/class-field-registry.php`
- `includes/Security/class-audit-log.php` — `TRANSPORT_BREAKER_OPEN`

## Steps

1. **Timeout** `sms.timeout` default 10 → **5**, and the registry maximum
   tightened **30 → 15** (`class-field-registry.php:406` — the clamp already
   exists at `min 3, max 30`; this is not a new ceiling).

2. **Clamp again at read time** inside `dispatch()`:
   `min( 15, Settings::get_int( 'sms.timeout', 5 ) )`.

   Not belt-and-braces. `Settings::sanitize()` applies the registry clamp **on
   save** (`class-settings.php:303`), so an install that already stored `30`
   keeps `30` after the maximum drops — until somebody happens to re-save that
   tab. Without the read-time clamp the tightening is advisory on exactly the
   sites that most need it.

3. **Backoff** `usleep( 2000000 )` → `usleep( 250000 )`. The single retry exists
   for a lost response on an idempotent gateway; an immediate retry serves that
   just as well, and two seconds of a held worker never did.

4. **Circuit breaker**, new class:
   - state in a transient keyed per transport — eviction resets it, which fails
     *safe* here: the breaker reopens and retries rather than staying stuck shut
   - `security.breaker_threshold` consecutive failures (default 5) opens it
   - `security.breaker_cooldown` seconds (default 300) shut
   - one half-open probe after the cooldown; success closes, failure re-opens
   - while open, `send()` returns the transport error **immediately** — no
     outbound call, no worker held
   - opening records the audit event and mails the admin once, on the transition,
     the same discipline as [9.1](9.1-site-budget.md)

## Acceptance

Rule 3 green. Five stubbed failures open the breaker; the sixth send returns in
under 50 ms **having made no HTTP call** — asserted against a stubbed transport
that counts invocations, not inferred from timing; after the cooldown exactly one
probe goes out.

## Not in scope

Queued delivery, and gateway failover. Both are recorded in the spec's out-of-scope
list; this sub-phase supplies the failure signal that failover would later
consume.

---

## Outcome

Rules 3a, 3b and 3c green. `Regression: 238 passed, 0 failed` (was 226). Abuse
boundary `10 passed, 6 failed`. phpcs back to the 17/15 baseline.

### The breaker went in the router, not the transport

The brief put it in `WebhookTransport`. `TransportRouter::send()` is the better
seam and it is where it landed, for two reasons the brief had not weighed:

- a hanging SMTP server holds a worker exactly as a hanging HTTP gateway does,
  and the router is the one place both go through
- `WebhookTester` — the admin "Gửi thử" button — calls `dispatch()` directly, so
  it stays **outside** the breaker. That is not an accident to tolerate but the
  behaviour you want: the test button is how an operator checks whether the
  gateway is back, and a breaker that blocked it would hide the recovery it
  exists to detect.

### Half-open as a count, not a flag

When the cooldown elapses the breaker closes but leaves the failure count one
below the threshold, so the next send *is* the probe and a single failure puts it
straight back. The obvious alternative — a `probing` boolean — is a race two
concurrent requests both win. Encoding it as a count costs nothing and has no
such state.

### Transient here, option in 9.1 — same question, opposite answer

The breaker stores state in a transient on purpose. Eviction resets it, which
fails *safe*: the circuit reopens and retries rather than staying stuck shut.
`RateLimiter`'s halt deadline is an option for the mirror-image reason — eviction
there would fail *open* on a spend limit. The storage choice follows the failure
mode, not a house style, and both classes say so at the decision.

### A guard rail that tested a spelling

Rule 3c stayed red against a working clamp. It matched
`min( <digits>, Settings::get_int( 'sms.timeout'` while the implementation reads
`min( self::MAX_TIMEOUT, max( 1, Settings::get_int( … ) ) )` — the rule was
pinned to one way of writing the expression rather than to the property.

Rewritten as two assertions: a named ceiling constant exists and is ≤ 15, and
`dispatch()` mentions both it and the setting it reads. The behaviour itself is
proved in `run-tests.php`, which drives a real dispatch with a stored timeout of
30 and reads the value off the outgoing request — a static rule was always the
weaker half of this, and it is now scoped to what it is good at: noticing if
somebody deletes the clamp.

Worth contrasting with 9.2, where a rule caught a genuine regression. A rule can
fail for being wrong as easily as for being right, and telling those apart is the
work — `is the code wrong, or is the rule?` was answered here by the behavioural
test already passing.

### The registry clamp was tightened, not added

`sms.timeout` was already `min 3, max 30`. The brief's first draft read as though
it were adding a ceiling; what it does is lower one — and the read-time clamp
exists precisely because lowering a registry maximum does nothing to values
already stored.
