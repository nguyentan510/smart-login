# 9.3 — Delivery timeout and circuit breaker

Spec: [`../abuse-boundary.md`](../abuse-boundary.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Stop a slow gateway from taking the whole site down.

`WebhookTransport::dispatch()` runs `wp_remote_request()` inside the visitor's
request at a default 10-second timeout, and the retry path adds
`usleep( 2000000 )` (`class-webhook-transport.php:134`) — up to ~22 seconds
holding one PHP worker. At 10 requests/second against a slow gateway, 100 workers
are occupied; a typical PHP-FPM pool is 20–50. Sign-in is not what goes down; the
site is. No attacker sophistication is required beyond noticing the gateway is
slow.

The spec explains why queueing is not the answer here.

## Files

- `includes/OTP/Transports/class-webhook-transport.php`
- `includes/OTP/Transports/class-circuit-breaker.php` — new
- `includes/OTP/Transports/class-transport-router.php`
- `includes/class-field-registry.php`
- `includes/Security/class-audit-log.php` — `TRANSPORT_BREAKER_OPEN`

## Steps

1. **Timeout** `sms.timeout` default 10 → **5**, and the registry maximum
   tightened **30 → 15** (`class-field-registry.php:406` — the clamp already
   exists at `min 3, max 30`; this is not a new ceiling).

2. **Clamp again at read time** inside `dispatch()`:
   `min( 15, Settings::get_int( 'sms.timeout', 5 ) )`.

   Not belt-and-braces. `Settings::sanitize()` applies the registry clamp **on
   save** (`class-settings.php:303`), so an install that already stored `30`
   keeps `30` after the maximum drops — until somebody happens to re-save that
   tab. Without the read-time clamp the tightening is advisory on exactly the
   sites that most need it.

3. **Backoff** `usleep( 2000000 )` → `usleep( 250000 )`. The single retry exists
   for a lost response on an idempotent gateway; an immediate retry serves that
   just as well, and two seconds of a held worker never did.

4. **Circuit breaker**, new class:
   - state in a transient keyed per transport — eviction resets it, which fails
     *safe* here: the breaker reopens and retries rather than staying stuck shut
   - `security.breaker_threshold` consecutive failures (default 5) opens it
   - `security.breaker_cooldown` seconds (default 300) shut
   - one half-open probe after the cooldown; success closes, failure re-opens
   - while open, `send()` returns the transport error **immediately** — no
     outbound call, no worker held
   - opening records the audit event and mails the admin once, on the transition,
     the same discipline as [9.1](9.1-site-budget.md)

## Acceptance

Rule 3 green. Five stubbed failures open the breaker; the sixth send returns in
under 50 ms **having made no HTTP call** — asserted against a stubbed transport
that counts invocations, not inferred from timing; after the cooldown exactly one
probe goes out.

## Not in scope

Queued delivery, and gateway failover. Both are recorded in the spec's out-of-scope
list; this sub-phase supplies the failure signal that failover would later
consume.
