# 9.2 — Country-code allowlist

Spec: [`../abuse-boundary.md`](../abuse-boundary.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Stop accepting phone numbers the site will never legitimately message.

The cheapest control in the phase and the one that removes most of the economic
incentive behind SMS pumping: an attacker who cannot aim at a premium range in a
revenue-sharing country is left burning the operator's money for no gain of their
own.

## Files

- `includes/Identity/class-phone.php`
- `includes/class-field-registry.php`
- `includes/Admin/class-readiness.php`
- `tests/run-tests.php` — pure-logic cases
- `README.md`

## Steps

1. **New setting** `identity.allowed_country_codes` (text, tab `auth`, section
   `identity`, default `''`). Empty means *only the configured default country
   code* — see the spec for why that reading is the safe default. The help text
   must state it outright.

2. **No prefix table.** E.164 country codes are 1–3 digits and variable-length,
   but the question here is only "does the canonical number start with an allowed
   code", which needs no table:

   ```php
   private static function country_allowed( string $canonical ): bool {
       foreach ( self::allowed_codes() as $cc ) {
           if ( 0 === strpos( $canonical, $cc ) ) {
               return true;
           }
       }
       return false;
   }
   ```

3. **Ordering inside `is_valid()`:** allowlist first, then the existing VN
   carrier-prefix branch or the generic length branch, then
   `OMNIWP_phone_is_valid` — which stays the last word, so a site with a
   genuinely unusual numbering plan keeps its escape hatch.

4. **Readiness.** More than five allowed codes is a WARN. Not because it is
   wrong, but because it is the configuration carrying the pumping exposure and
   the operator should have chosen it deliberately.

## Acceptance

Rule 2 green. `84969789475` valid; `254712345678` invalid at the default and
valid once `254` is added; the filter still overrides both directions. Cases go
in `run-tests.php`, which already owns phone normalisation and needs no
WordPress.

## Not in scope

Per-country spend caps. The spec records them as the finer-grained version, worth
having only if the allowlist is ever widened beyond a handful of codes.

---

## Outcome

Rule 2 green. `Regression: 226 passed, 0 failed` (was 217). Abuse boundary
`6 passed, 9 failed`. phpcs back to the 17/15 baseline after the detour below.

### A Phase 4 guard rail caught this sub-phase breaking it

The first working version put the allowlist rejection behind its own
`return apply_filters( 'OMNIWP_phone_is_valid', false, $canonical )`. The
required suite went red immediately:

```text
OMNIWP_phone_is_valid reaches Vietnamese numbers (Phase 4)
  FAIL     there is exactly one return path through the filter
```

That rule exists because the Vietnamese branch once returned *before* the filter,
making the documented hook dead on the configuration nearly every site uses. A
second exit through the filter is the same defect one step away — the next branch
added would have had two working examples of how to skip it.

Fixed by structure rather than by weakening the rule: the allowlist now sets
`$valid = false` and falls through to the single exit. The comment at the call
site records why, so nobody re-introduces the early return as a "simplification".

Worth stating plainly: a guard rail from five phases ago caught a regression in
new work, on the first run, and named it precisely. That is the argument for
9.0's whole existence, demonstrated on the author rather than on a hypothetical
contributor.

### The filter had to keep working in both directions

A filter that can only tighten is not the last word. Because the rejection is now
a `$valid` assignment rather than a return, `OMNIWP_phone_is_valid` can
still *admit* a number the allowlist refused — asserted directly, since the
obvious implementation silently removes that ability.

### phpcs went up by ten, all of it alignment

`identity.allowed_country_codes` is longer than every other key in
`auth_fields()`, so WPCS wanted the whole array's `=>` column moved. All ten were
auto-fixable; `phpcbf` on that one file returned the project to 17/15. The diff
was checked to be alignment only before it was accepted.

### Reading the empty value

`allowed_codes()` returning `array( '84' )` for an empty setting is asserted
first, before any validity check, because the entire no-migration argument rests
on it. If that reading ever flips to "unlimited", every site upgrading inherits
the exposure this sub-phase exists to close — and the failure would be silent.
