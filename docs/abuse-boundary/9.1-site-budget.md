# 9.1 — Site-wide OTP budget and kill switch

Spec: [`../abuse-boundary.md`](../abuse-boundary.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Give the plugin a ceiling that an attacker cannot rotate around, and a
stop that fires without waiting for a human.

This is the missing axis the spec describes. It also owns the **single**
`OMNIWP_DB_VERSION` bump for the phase — anything else needing a schema
change folds into this sub-phase rather than bumping again.

## Files

- `includes/Security/class-rate-limiter.php`
- `includes/OTP/class-otp-repository.php`
- `includes/class-installer.php` — index + version
- `includes/class-field-registry.php` — new `security` tab, `budget` section
- `includes/Security/class-audit-log.php` — `OTP_BUDGET_HALTED`
- `omniwp.php` — `OMNIWP_DB_VERSION`

## Steps

1. **Count from the table, not a transient.** The OTP table is already the source
   of truth for the other two limits — `RateLimiter`'s own class comment says so
   — and a transient can be evicted by a cache flush, which for a spend limit
   means failing open at the worst possible moment.

   Add `OtpRepository::count_recent_all( int $seconds ): int`.

2. **Add `KEY created_at (created_at)`** to the OTP table. The existing indexes
   are `dest_intent`, `expires_at` and `ip_created`; a site-wide
   `COUNT(*) WHERE created_at > ?` matches none of them and table-scans. Bump the
   DB version; `pending_schema_changes()` in the integration gate covers
   idempotency.

3. **Two ceilings** in `check_otp_send()`, after the existing IP check:
   `security.max_per_site_hour` and `security.max_per_site_day`. `0` disables,
   and readiness warns when it does.

4. **The kill switch.** Tripping either ceiling writes
   `OMNIWP_otp_halted_until` — an **option**, not a transient, because it
   must survive a cache flush. While it is in the future, `check_otp_send()`
   returns early *before touching the database at all*, so a sustained attack
   costs one option read per request instead of three counting queries. That
   load-shedding property is what makes the kill switch a DoS control as well as
   a spend control.

5. **Alert on the transition only.** Detect it by the option being absent or past
   at the moment of writing, so concurrent requests cannot produce a mail storm.
   Record `AuditLog::OTP_BUDGET_HALTED` and `wp_mail()` the admin once.

6. **Say nothing useful to the caller.** *"Hệ thống đang tạm thời không gửi được
   mã. Vui lòng thử lại sau."* Naming the budget tells an attacker the attack
   landed and tells a visitor something they cannot act on.

## Known limits, written down rather than hidden

- The check runs before the row is inserted, so a concurrent burst can overshoot
  by roughly the worker count. It is a ceiling, not an accountant.
- `add_identity` sends from signed-in members share the anonymous budget. The
  spec records splitting it as out of scope; this is where the cost lands.

## Acceptance

Rule 1 green. With `max_per_site_hour = 2`: the third send from a third distinct
destination on a third distinct IP is refused; the halt option is set once;
exactly one mail is sent; and a fourth request performs **no** counting query —
verified by `$wpdb->num_queries`, not by reading the code.

## Not in scope

Adaptive challenge behaviour on budget pressure — that is
[9.8](9.8-adaptive-captcha.md), which reads the state this sub-phase creates.

## Outcome

Rule 1 green. `Regression (pure logic): 217 passed, 0 failed` — up from 201, the
sixteen new ones pinning this control. Abuse boundary moved from `4 passed, 11
failed` to `5 passed, 10 failed`. phpcs unchanged at 17 errors / 15 warnings,
compared against the 9.0 tree rather than assumed.

### The acceptance was met with a different instrument than it named

It called for `$wpdb->num_queries` to prove the halted path runs no counting
query. The stub `$wpdb` has no such counter, and adding one would have measured
the stub rather than the limiter. The spy repository counts the calls that
actually matter instead — `a halted site runs no counting query` asserts
`$budget_repo->counted === 0` after a refusal.

That is a better instrument, not a weaker one: `num_queries` would also have
counted the option read, which is exactly the query the design intends to keep.

### The behavioural checks went into the required suite, not the spec one

The abuse suite stays `spec` until the whole phase is green, so a control pinned
only there could regress without the build saying so for weeks. `run-tests.php`
already owns a `RateLimiter` section, so the budget behaviour sits beside it and
blocks immediately — the same argument 8.1 used for putting its assertions in
the required fitness suite rather than the spec one.

### Two decisions worth recording

**`KEY created_at` is not redundant against `KEY ip_created`.** MySQL uses a
composite index only from its leftmost column, so a site-wide
`WHERE created_at > ?` with no IP predicate cannot use `(ip, created_at)` and
would scan the table on every send. The comment in `schema()` says so, because
the next person to read the index list will think it is duplication.

**A ceiling of `0` means unlimited, and that is now asserted.** The help text
says it, and reading it the other way round — 0 as "refuse everything" — would
take a site offline the moment somebody cleared the field. `a ceiling of 0
disables the limit` is a cheap test against an expensive misreading.

### What the stubs needed

`wp_mail()` and `delete_option()` did not exist. `wp_mail()` records into
`$GLOBALS['ow_mails']` so "exactly one mail per halt" is a count rather than a
claim — and it is what proves the transition detection works, since the naive
implementation mails on every blocked request during an attack.

`update_option()` gained its third parameter. The stub declared two, and
production now passes `$autoload`; PHP tolerates the extra argument, but a stub
whose signature has silently drifted from the real API is a trap for the next
test that depends on it.

### Verified against a real WordPress, after 9.5

The stub `$wpdb` never parses SQL, so nothing above proved the schema change or
the counter. `tests/integration/run-abuse-gate.php` now does, on WordPress 7.0.2
with PHP 8.2.29:

```text
9.1 — schema
  ok    KEY created_at exists (created_at)
  ok    MySQL chooses KEY created_at for the site-wide count
  ok    dbDelta is idempotent with the new index present
  ok    db_version is 5

9.1 — count_recent_all() as real SQL
  ok    count_recent_all() executes, returned 1
  ok    the counter moves with a real row (1 → 2)
  ok    probe row removed, count back to 1

9.1 — the kill switch, end to end
  ok    resume() clears the halt
  ok    a stored halt deadline is read back (600s)
  ok    a halted site refuses with OMNIWP_unavailable
```

Two of those were arguments before they were measurements. **The index claim was
checked with `EXPLAIN`**, not asserted from the leftmost-prefix rule — MySQL does
pick `created_at` for a `created_at`-only predicate. And **the counter is checked
by moving it**: a `COUNT(*)` that always returned 0 would satisfy every stub test
in this phase while capping nothing at all, which is precisely the failure a
stubbed database cannot see.

### Not done here, deliberately

The admin screen has no "resume sending" control yet — `RateLimiter::resume()`
exists and is tested, but nothing calls it outside the tests. It belongs with the
operator screen in [9.9](9.9-audit-and-visibility.md), where the halt state is
already scoped to be displayed. Until then a halt clears itself after
`halt_minutes`, so nobody is stuck.
