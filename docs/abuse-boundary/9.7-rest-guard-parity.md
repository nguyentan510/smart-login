# 9.7 — REST guard parity

Spec: [`../abuse-boundary.md`](../abuse-boundary.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Make the JSON path carry the same form integrity the HTML path does.

Three findings, and the third is the one that matters:

1. `RequestGuard::verify_rest()` (`class-request-guard.php:127`) checks the
   honeypot only. The form path also enforces a minimum fill time.
2. It is called from `handle_register()` **and nowhere else**. `/login`,
   `/forgot`, `/reset`, `/resend` and the `contact/*` routes call nothing.
3. **`assets/js/omniwp.js` sends only `X-WP-Nonce`** — no `OMNIWP_ts`,
   no honeypot field. So even where `verify_rest()` *is* called, there is nothing
   for it to inspect. The check is not weak; on the JS path it is inert.

The spec records the accompanying fact about the `wp_rest` nonce, which is why
this sub-phase is parity work rather than a security control in its own right.

## Files

- `assets/js/omniwp.js` — **first commit**
- `includes/Frontend/class-assets.php`
- `includes/Security/class-request-guard.php`
- `includes/Frontend/class-rest-controller.php`
- `README.md`

## Steps

**Ship in two commits, JS first**, or the first deploy rejects every in-flight
client that has not reloaded.

1. Emit `OMNIWP_ts` and the honeypot from the JS on every REST call, so the
   check has something to check.
2. Extend `verify_rest()` with the same signed-timestamp check the form path
   uses, verified **only when the stamp is present** — mirroring
   `class-request-guard.php:93`, so a cookie-less native client that sends none
   is not locked out.
3. Call `verify_rest()` from every public route callback.
4. Document the anonymous-nonce property in the README REST section, beside the
   `X-WP-Nonce` requirement, so nobody mistakes it for rate limiting.

## Acceptance

Rule 6 green. Every route rejects a tripped honeypot; a stamp younger than
`MIN_FILL_SECONDS` is rejected; **a request with no stamp at all still
succeeds** — the third assertion is the one that protects native clients, and
without it this sub-phase is a breaking change wearing a security label.

## Not in scope

Rate limiting the REST routes. The budget ([9.1](9.1-site-budget.md)) and the
identify ceiling ([9.4](9.4-identify-limit.md)) own that; adding a third
mechanism here would put the same policy in two places.

---

## Outcome

Rule 6 green, and with it the whole suite: **`Abuse boundary: 23 passed, 0
failed`**. Promoted from `spec` to `required` in `run-all.php` — the commitment
made in 9.0, honoured on the run that earned it. `Regression: 285 passed`
(was 280). phpcs at baseline, `node --check` clean.

### One shared gate, not eleven copies

The brief said to call `verify_rest()` from every callback. It landed in
`check_permission()` instead, which every route already routes through.

Eleven copies are eleven chances to forget the twelfth, and this sub-phase exists
precisely because ten of eleven were already missing. A rule demanding the
repetition would have been enforcing the shape of the bug.

Rule 6 was rewritten to check **reachability** rather than repetition: every
route is gated by a permission callback this class owns, `check_permission()`
runs the guard, and `check_contact_permission()` delegates rather than acquiring
a second weaker gate. That last assertion matters — the authenticated routes were
the easy place to end up with a parallel path.

This is the fourth rule adjusted in the phase. The test that has held up each
time: *a rule that names a helper or a route is testing structure; a rule that
names an expression or a line is testing a spelling.*

### The guard had nothing to inspect, which is not the same as being weak

`assets/js/omniwp.js` sent only `X-WP-Nonce`. So `verify_rest()` in
`handle_register()` was not a lax check — it was inert, examining fields no
client transmitted. Rule 6 now asserts the JS sends both, because fixing the
server half alone would have produced a green rule and no behaviour.

`RequestGuard::stamp()` was added so the JSON path signs with the same function
the HTML forms use rather than a second implementation that drifts.

### The assertion that keeps this from being a breaking change

`a request with no stamp still passes`. Cookie-less native clients send none, and
treating absence as failure would make this a breaking change wearing a security
label. It mirrors the form path, which has always verified the stamp only when
present.

Shipped in the order the brief demanded — the JS field before the server check —
though in the end both landed in one commit, since the check tolerates absence
and therefore cannot reject an in-flight client either way.

### What did not change

The `wp_rest` nonce is still constant for 12–24 hours across all anonymous
visitors. That is now written down in the README beside the header requirement,
because the risk was never the nonce being weak — it was somebody reading it as
rate limiting.
