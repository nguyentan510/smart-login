# 9.10 — Housekeeping

Spec: [`../abuse-boundary.md`](../abuse-boundary.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Two loose ends, both smaller than the first review of them suggested.
Recorded so they are decided rather than forgotten.

## Files

- `includes/Address/class-address-rest.php`
- `tests/integration/run-wordpress-gate.php`
- possibly `templates/form-login.php`, `templates/form-register.php`,
  `tests/identity/run-template-tests.php`

## (a) The address endpoint never answers 304

`AddressRest::cacheable()` sets `Cache-Control` and an ETag but never inspects
`If-None-Match`, so a client whose TTL lapsed re-downloads the full payload. Add
the comparison and return 304 on a match.

**Then measure the premise.** Whether these headers survive the `nocache` headers
core sends for REST responses is a question about a running WordPress, not about
this file — and if they do not, the whole caching design here is inert and the
fix is a different one entirely.

That check belongs in `run-wordpress-gate.php`, which already runs against a real
install: assert the **served** headers with a real request, so the answer is a
measurement and stays one. Do this before writing the 304 branch; the result may
change what the branch should be.

## (b) The two shim templates — a decision, not a defect

`templates/form-login.php` and `form-register.php` are never loaded, and
`run-template-tests.php:391` **already asserts** that nothing loads them. This is
a deliberate, tested decision. An earlier review of this codebase read them as an
oversight and was wrong.

The only open question is whether to delete the files and update the suite's
list, or keep them. Both are defensible; deleting removes a trap for theme
authors who override a file that does nothing, and the assertion keeps passing
either way. Low priority — decide in review, and record which way it went.

## Acceptance

For (a): the gate reports the actual `Cache-Control` and `ETag` values a real
WordPress serves for `/address/provinces`, and a second request carrying the
returned ETag receives 304 — or the gate records that core's headers win, which
is an equally valid result and redirects the work.

For (b): whichever way it goes, `run-all.php` stays green and the tracker records
the decision.

## Not in scope

Rate limiting the address routes. Static reference data served from PHP files
under opcache is not the exposure; the spec's ownership table puts volumetric
defence with the CDN.

## Outcome

Both items closed, and both closed differently than expected.

### (a) The premise held, so the fix was the one described

Measured first, against `http://localhost:10004` with `curl -D -`, before a line
was written:

```text
Cache-Control: public, max-age=86400
ETag: "2087a331c3be7716d27d4c7e6329c233"
```

The plugin's headers **do** reach the client. WordPress sends its nocache headers
only for logged-in REST requests, and these routes are anonymous — so the caching
design was live rather than inert, and the missing half really was the
conditional request. A replay carrying that exact ETag returned `200` and 2,689
bytes.

`matches_etag()` now answers it. Measured again on the live site:

| Request | Before | After |
| --- | --- | --- |
| fresh | 200, 2689 B | 200, 2689 B |
| `If-None-Match` exact | 200, 2689 B | **304, 0 B** |
| `If-None-Match: W/"…"` | 200, 2689 B | **304, 0 B** |
| `If-None-Match: "stale"` | 200, 2689 B | 200, 2689 B |
| no header | 200, 2689 B | 200, 2689 B |
| `wards/11` replay | 200, 7216 B | **304, 0 B** |

The weak-comparison prefix is accepted deliberately: these responses are
byte-identical for a given dataset stamp, so weak and strong agree and refusing
`W/` would only cost a round trip.

### The measurement nearly lied, which is worth recording

The first run of these checks reported `200` **after** the fix. The cause was not
the code: `wp-content/plugins/smart-login` in the Local install is a **copy**, not
a link to the working tree, and it was thirteen files behind. Every earlier
integration gate result stands — the gate loads the plugin from
`SMART_LOGIN_PLUGIN_ROOT`, which is the working tree — but anything measured over
HTTP goes through the installed copy and needs it synced first.

A stale copy that produces plausible-looking output is exactly the shape of
"two runs are not a comparison": the number was real, it just described different
code than the one being reasoned about.

### (b) The shims stay, reversing the earlier recommendation

An earlier review of this codebase called `templates/form-login.php` and
`form-register.php` dead files and suggested deleting them to remove a trap for
theme authors. Reading them settles it the other way: they are not stubs, they
**forward to `form-auth`** through `TemplateLoader::output()`.

That makes them compatibility surface, not dead code. Anything outside the plugin
that still asks for `form-login` gets the right screen instead of nothing, and 51
lines is a cheap price for that. They stay, and `run-template-tests.php` keeps
asserting the plugin itself never loads them.

Two reviews, two opposite recommendations, and the deciding evidence was reading
the file rather than its filename.
