# 9.8 — Adaptive captcha

Spec: [`../abuse-boundary.md`](../abuse-boundary.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Blocked on [9.1](9.1-site-budget.md) and [9.3](9.3-delivery-limits.md).**
Adaptive mode reads budget pressure and breaker state, so both have to exist and
be measurable. And verification is another blocking outbound call in the request
path — it must inherit 9.3's timeout discipline or it reintroduces the exact bug
9.3 fixes.

**Goal.** A challenge that appears when the site is under pressure and is
invisible the rest of the time.

## Files

- `includes/Security/class-captcha.php` — new, provider behind a small interface
- `includes/Frontend/class-form-controller.php`
- `includes/Frontend/class-rest-controller.php`
- `includes/class-field-registry.php` — `security` tab, `captcha` section
- `templates/partials/`, `assets/js/`
- `includes/Admin/class-readiness.php`

## Steps

1. **Provider interface**, so adding hCaptcha later is a class rather than a
   rewrite. Settings: `provider` (`off|turnstile|hcaptcha`), `site_key`,
   `secret`, `mode`.

2. **The secret is encrypted on save and never re-rendered**, exactly as the
   OAuth provider secrets already are. Reuse that path; do not invent a second
   one.

3. **`mode` is the design decision.** `always` challenges everyone. `adaptive` —
   the default — challenges only when the request is already suspicious:
   - the site budget is over a configurable fraction (default 50%) of its hourly
     ceiling, **or**
   - the kill switch tripped within the last hour, **or**
   - the circuit breaker is open, **or**
   - this IP has spent more than half of `max_identify_per_ip_hour`

   Ordinary visitors on an ordinary day see nothing. The challenge appears when
   the cost of an extra click is worth paying, and not before.

4. **Enforce at every entry that can cause an SMS:** `handle_identify`,
   `handle_forgot`, and REST `/register` and `/forgot`.

5. **Timeout ≤ 5 s, hard-clamped.** A captcha endpoint that hangs must not become
   the worker-exhaustion bug a second time.

6. **Fail closed.** Verification that cannot complete refuses the send. The spec
   explains why this points the opposite way to the `Client::ip()` decision, and
   why both are right.

## Acceptance

With `mode = adaptive` and the budget under pressure, the identify form renders a
widget and rejects a submission carrying no valid token. Under no pressure the
widget is **absent** and submissions pass untouched — the second half is the one
that decides whether this is shippable, since a challenge that shows up on a
quiet Tuesday is a conversion bug.

A stubbed verifier that times out refuses the send.

## Not in scope

Bot scoring, device fingerprinting, or anything resembling a WAF. The spec's
ownership table puts that with the CDN.

---

## Outcome

Rule 10 green, all four assertions. `Regression: 301 passed, 0 failed` (was 285).
Abuse boundary `28 passed, 0 failed`. phpcs at baseline. Full integration chain
green, **including the provider gates** — which is the check that mattered most
here, for the reason below.

### The secret store was extracted, not duplicated

The brief said to reuse the provider secrets' encryption path. That path had the
cipher inlined in `ProviderCredentials` behind an allowlist of `google` and
`zalo`, so reuse meant extraction: `Security\SecretBox` now owns seal/open and
both callers go through it.

**The stored record shape did not change.** `version`, `cipher`, `iv`, `tag`,
`ciphertext` — the same five keys the old code wrote. Renaming even one would
have left every already-stored provider secret undecryptable on upgrade, which is
this project's most-repeated failure mode and the reason `SMART_LOGIN_GOOGLE_STAGING_SMOKE_OK`
in the gate output is the line worth reading twice.

### Adaptive earns its default

The assertion that decides whether this is shippable is the negative one: on a
quiet day `under_pressure()` is false, `field_html()` is empty, and
`script_url()` is empty — so **no third-party script is registered at all**. A
captcha costs a request and a privacy footprint even when nobody looks at it, and
"invisible" has to mean not loaded rather than merely not shown.

Each pressure signal is one an earlier sub-phase already computes, which is why
this was blocked on 9.1 and 9.3 rather than merely sequenced after them. All four
are driven in the tests, including the one that subsides when the counter does.

### Fail closed, and the stub gateway proves it

`verify_token()` treats a network error, a non-200, an unparseable body and an
explicit rejection as the same answer. The test stub answers 500 to everything,
so `an unverifiable token is refused` is a real assertion rather than a
restatement — and the guard rail drives it against `127.0.0.1:9`, which nothing
listens on.

### A `secret` field type, so this is not a special case

Rather than bolting the captcha secret onto `absorb_provider_secrets()`,
`FieldRegistry` gained a `secret` type: the renderer draws a write-only password
box with a clear checkbox, and `Settings::sanitize()` diverts the value into its
own store and **prunes it from the option array**. The next secret needs a
registry row and nothing else.

An existing test caught this immediately — `saving "security" keeps every value
it posted` went red, because a secret by design does not round-trip. The
assertion was rewritten to state the real property: the submitted value must
never appear in the option array, while the empty default may.

### Two stub moves, both forced by the same shape

`esc_attr()` lived only in `template-stubs.php`, which `run-tests.php` does not
load; `wp_remote_post()` did not exist at all. Both now sit in `stubs.php`, with
`template-stubs.php` losing its copy — the same redeclaration reasoning that
moved `add_filter()` in 9.0.
