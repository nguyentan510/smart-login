# 22.0 — Guard rails, landed red

Spec: [`../in-plugin-guide.md`](../in-plugin-guide.md).
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Twelve rules, in a suite of their own, landed before a single
production file moves. A rule written after the screen exists cannot fail, and a
rule that has never failed is a comment.

Rules whose subject does not exist yet report **PENDING**, not PASS. Every rule
here is phrased over a rendered guide or over a catalog, and both are absent
today — so a rule that "passes" on this tree would be stating the opposite of
the truth. That is the 10.0 precedent, and 21.0 found the failure mode in
practice: three rules passed against an empty string because the thing they
were phrased as an *absence* in had never rendered.

## Files

- `tests/identity/run-guide-tests.php` — new suite
- `tests/run-all.php` — registered as `spec`

## Outcome

```text
Rule 4 — a tag is registered from the catalog and nowhere else
  FAIL     register() adds no shortcode by literal name
           A literal here is a second list: the catalog can then omit a tag
           that is still registered, which is exactly finding 2.

Guide tab: 0 passed, 1 failed, 18 pending
```

**Nothing passed.** One rule is red against the tree as it stands — rule 4 has a
subject today, and that subject is the defect — and the other eleven report
PENDING across eighteen assertions because neither the screen nor the catalog
exists. That is the state 21.0 aimed at and missed: no rule here can go green
without something being built.

### The subject is resolved before anything is counted

Every rule asks first. `class_exists()` for the screen, `defined()` for the
catalog constant, `ow_method_body()` returning `''` for a method that is not
there, `ow_capture()` never called when the class is absent. The alternative —
asserting `false === strpos( $html, … )` against an empty string — is how 21.0
shipped three rules that passed on the day they were written.

### Two rules changed while being written

**Rule 10 gained its second half.** Its first draft asserted that the shipped
aliases appear in the markup, which a hard-coded list on the screen satisfies —
and D4 says the list is *rendered from the method* precisely because that map is
filterable. The rule now adds an alias through `OMNIWP_dialog_aliases`,
re-renders, and requires it to appear. A typed list fails.

**Rule 12 replaced a rule that could not fail.** The first draft said "the guide
restates no setting value", which no test can hold: it would have to compare
every number in the prose against a registry the prose is not derived from. What
*is* checkable is the structural cause — the screen reads no settings at all —
so that is the rule, and D6 was rewritten to say so.

### Rule 7 nearly read its own subject back

The search for a quoted error string walks `ow_plugin_sources()`, which includes
the guide screen itself. Left alone, every quote would have been found in the
file that holds it and the rule would have passed by definition. The helper
`ow_sources_outside_guide()` removes that one file, and the reason is written
above it.
