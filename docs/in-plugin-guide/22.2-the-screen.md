# 22.2 — The screen

Spec: [`../in-plugin-guide.md`](../in-plugin-guide.md), D1 and D3–D7.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Turn the remaining ten rules green. A tab called **Hướng dẫn**, last in
the strip, that an administrator can read in two minutes.

## Files

- `includes/Admin/Screens/class-guide-screen.php` — new
- `includes/Admin/class-settings-page.php` — the route and the strip
- `assets/css/admin.css` — the layout of the cards
- `README.md` — a pointer to the screen
- `CHANGELOG.md`

## The content, in reading order

1. **Ba bước để chạy được** — identity, delivery channel, put the form on a
   page. Three lines, each a link to the screen that owns it, and a link to
   Tổng quan for the answer to "is it working". It does **not** restate the
   readiness rows (finding 3).
2. **Shortcode** — the nine tags from the catalog: what it is for, where it
   goes, its attributes and their defaults. `[smart_account]` and
   `[smart_address]` appear here for the first time anywhere.
3. **Mở hộp đăng nhập từ bất kỳ đâu** — the four triggers, and the alias list
   rendered from `LoginDialog::aliases()`.
4. **Nút tài khoản trên header** — the two states, the nav-menu location
   setting, the closed set of icon names from `IconSet::names()`.
5. **Khi có sự cố** — the troubleshooting table. Left column is the string the
   visitor sees, quoted exactly; then the cause; then a button to the screen
   that fixes it.
6. **Cho lập trình viên** — four filters and a pointer to `README.md`. Not a
   hook reference; the four that get asked about.

## Steps

1. `GuideScreen` with `SLUG = 'guide'`, rendering the six sections. It reads
   `Shortcodes::CATALOG`, `LoginDialog::aliases()`, `IconSet::names()` and
   `SettingsPage` — and **no settings** (rule 12).
2. `SettingsPage::tabs()` gains it after `FieldRegistry::tabs()`, and `render()`
   routes it before the Overview fallback. It stays out of `FieldRegistry`.
3. The troubleshooting rows are data: `quote`, `cause`, `fix`, `tab`. Rules 7
   and 9 walk that array, so a row whose message has drifted or whose slug has
   been renamed fails before an administrator follows it.
4. CSS: two-column cards, `widefat` tables, nothing new invented — the admin
   stylesheet already carries the readiness table and the provider cards.

## Outcome

`GuideScreen` — 630 lines, six sections, all rendered from live data. The
screen reads `Shortcodes::CATALOG`, `LoginDialog::aliases()`,
`IconSet::names()` and `SettingsPage`; it reads **no settings**.

`SettingsPage::tabs()` returns it after `FieldRegistry::tabs()`, and
`render()` routes it before the Overview fallback. It is not in
`FieldRegistry`, so there is no Save button and no form.

The troubleshooting table carries twelve rows. Seven quote a message verbatim
(rule 7 searches `includes/` for each one); five describe a symptom. Every
`tab` slug resolves through `SettingsPage::tabs()` (rule 9).

**Finding during implementation:** the test variable `$sl_filters` at global
scope *is* `$GLOBALS['sl_filters']` — the stub filter registry — and assigning
the guide's filter list over it turned every registered hook into a description
string. The suite fataled inside `add_filter()`. Renamed to
`$sl_guide_filters`.
