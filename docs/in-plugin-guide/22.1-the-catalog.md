# 22.1 — One list of shortcodes

Spec: [`../in-plugin-guide.md`](../in-plugin-guide.md), D2.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Turn rules 4 and 5 green. A tag is written down once, and everything
that needs the list reads that one.

Today `register()` names nine tags in nine `add_shortcode()` calls
(`includes/Frontend/class-shortcodes.php:21-29`), and two render methods carry
their own attribute defaults in a `shortcode_atts()` literal (`:46-56` and
`:151-157`). Nothing else can enumerate either, which is why finding 2 is
possible: the README lists six of the nine and nothing notices.

## Files

- `includes/Frontend/class-shortcodes.php`

## Steps

1. `const CATALOG` — tag → `array( 'callback' => …, 'atts' => … )`, where `atts`
   is the `name => default` array `shortcode_atts()` already wants. Structure
   only: **no labels, no help text**. A front-end request builds this array on
   its way to rendering a login form, and it must not be paying to translate
   admin copy.
2. `register()` walks it. The nine literals go.
3. `render_button()` and `render_address()` take their defaults from
   `self::CATALOG[ … ]['atts']` rather than from a literal. The `label` default
   stays computed in `render_button()` — `__( 'Đăng nhập' )` is not a constant
   expression and would not survive in a `const`, and pushing it into the
   catalog would mean translating it on every front-end request for the benefit
   of a screen in `wp-admin`.
4. Nothing else changes. Same tags, same defaults, same behaviour — the point of
   this sub-phase is that the list becomes readable, not that it becomes
   different.

## Acceptance

- Rules 4 and 5 green; rule 3 still pending (nothing documents the catalog yet)
- The nine tags registered are the same nine, asserted by the existing suites
  rather than by a new list
- `[smart_login_button]` and `[smart_address]` behave identically — the account
  menu suite covers the first and it must not move
- Every other suite at its previous count

## Not in scope

The screen. A catalog with no reader is verified only by the rules that describe
it, which is why 22.2 lands in the same phase rather than later.

### The account-menu suite caught the move, through the guard 21.7 wrote for it

```text
FAIL     the shortcode attribute list was actually found
         a rule that narrows to nothing passes vacuously — found:

Account menu: 37 passed, 1 failed, 0 pending
```

21.7's README rule reads the button's attributes off the shortcode rather than
off a list typed into the test, and in 21.7 the only way to do that was a regex
over `shortcode_atts( array( … )` in the source. Removing that literal narrowed
the regex to nothing — and the companion rule 21.7 added for exactly this,
"the list was actually found", failed instead of the real rule passing vacuously
over an empty set.

The fix is not a wider regex. The question "which attributes does this shortcode
accept" now has an answer that is data, so the rule reads
`Shortcodes::CATALOG['smart_login_button']['atts']` and the guard stays. Back to
**38 passed, 0 failed**.

This is the tracker's third risk row happening exactly as written, and it is the
argument for the catalog in miniature: the old rule had to parse PHP with a
pattern because there was nothing to ask.

### What the catalog deliberately does not hold

`label`'s real default is `__( 'Đăng nhập' )`, computed in `render_button()`
when the attribute comes through empty. A translated string is not a constant
expression, so it could not live in a `const` — and had the catalog been a
method instead, every front-end request would have translated a page of admin
copy on its way to rendering a login form. The catalog is structure; the prose
is 22.2's.
