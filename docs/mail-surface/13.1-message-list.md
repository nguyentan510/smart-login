# 13.1 — The message list

Spec: [`../mail-surface.md`](../mail-surface.md) (D1, D2). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Twenty fields in one column become a list of six messages with one
open at a time.

## Files

- `includes/Admin/Screens/class-settings-screen.php`
- `includes/Mail/class-mail-registry.php` — grouping helper
- `assets/js/admin.js`, `assets/css/admin.css`
- `tests/mail/run-template-tests.php`

## Steps

1. **A table, generated from the registry.** Columns: message name, when it
   fires, and state — *Đang dùng mẫu chung* or *Đã tuỳ chỉnh*. The state column
   is the one that earns its width; it is the question an administrator has on
   opening the screen and today it takes reading twelve boxes to answer.

   `MailRegistry::is_overridden( $id )` answers it, reading the same stored
   values `resolve()` does, so the list cannot claim a message is inheriting
   while the transport disagrees.

2. **Every panel renders; one is visible.** The section draws all six panels and
   marks one open. Hidden panels keep their inputs in the DOM — rule 2 asserts
   this, because rendering only the open one is the obvious optimisation and it
   would silently stop five messages being saved.

3. **Selection is a button, not a link.** A link would need a query argument, a
   query argument would need the screen to survive a reload mid-edit, and the
   simplest thing that does not lose typed text is to not navigate at all.

4. **No JavaScript, no problem.** With scripts off, every panel shows — the
   current behaviour, which is a long page rather than a broken one. The list is
   `<button>`s that do nothing and the panels are visible by default; the script
   hides the ones it is not showing. Progressive in the direction that fails
   safe.

5. **The admin alerts join the same list**, with their on/off switch drawn in the
   list row rather than inside the panel. It is the control that decides whether
   the panel matters at all.

## Acceptance

Rules 1 and 2 green.

Every registry row appears once in the list and once as a panel — asserted by
walking `MailRegistry::all()`, not by counting to six.

Every subject and body input is present in the rendered markup regardless of
which panel is open.

The state column says *Đã tuỳ chỉnh* for a message with an override and
*Đang dùng mẫu chung* for one without, and flips when the stored value changes.

Saving the tab still writes every message's fields — the existing round trip in
`run-tests.php` covers this and must not move.

## Not in scope

Copy-to-edit (13.2) and the layout (13.3). This sub-phase moves nothing but
where a field is drawn.
