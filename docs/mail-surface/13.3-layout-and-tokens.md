# 13.3 — The layout, and two tokens worth having

Spec: [`../mail-surface.md`](../mail-surface.md) (D4, D5, D6). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Make the email look like it was meant, and give the code the treatment
the message exists for.

## What is missing, in order of how much it costs

```
Mã xác nhận: {{code}}
```

An OTP email has one job — show six digits — and it currently renders them as
running text mid-paragraph. That is the biggest defect on this screen and it is
not a styling preference.

Second is the preheader: the grey line an inbox shows after the subject. There is
none, so every message this plugin sends previews as *"Xin chào,"*.

Third is a button, for the messages that will eventually carry a link. Fourth is
type and dark mode.

## Steps

1. **`{{code_block}}`** renders the code large, letter-spaced, selectable, in a
   bordered block. Selectable matters: a customer on a phone copies it, and
   anything clever with spans between the digits defeats that.

   In a plain-text message it renders as the bare code, so a body written for
   both does not carry markup into text mail — which rule 6 from 11.0 already
   pins and this must not break.

2. **`{{button:url|label}}`** renders a table-based CTA. Not a styled `<a>`:
   Outlook ignores padding on inline elements, so the button becomes underlined
   text. Ugly markup for the same reason `layout.php` is already ugly, and the
   file says so.

   In plain text it renders as `label: url`, because a link the reader cannot
   click has to be a link they can copy.

3. **Both tokens are opt-in.** A body using neither renders byte-identically to
   today. Rule 4 asserts it, and it is what keeps this from being a migration —
   the shipped bodies are **not** rewritten to use them in this sub-phase, so
   every existing install and every existing test sees exactly what it saw.

   They are offered in the token list for the messages that declare them.

4. **`preheader` on the registry row**, defaulted per message, no admin field.
   One shared setting would be wrong for six messages and six new fields would
   rebuild the wall this phase removes. Rendered as the standard hidden span
   followed by the zero-width padding that stops clients pulling body text in
   after it.

5. **Type, spacing and dark mode.** A larger body size, real line height, and
   `color-scheme` plus a `prefers-color-scheme` block.

   The comment says what that does not cover: Gmail's web client ignores both and
   applies its own inversion. Colours are chosen so the light rendering survives
   being inverted rather than pretending the query is enough.

## Acceptance

Rule 4 green, and still green — a body using neither token produces the same
bytes as before this sub-phase, asserted against a captured fixture rather than
by eye.

`{{code_block}}` in an HTML message renders the code inside a block; in a text
message it renders the bare digits and the message still passes
`wp_strip_all_tags()` unchanged, which is 11.0's rule 6.

`{{button:https://…|Đặt lại}}` renders a table in HTML and `Đặt lại:
https://…` in text.

The preheader appears once, before the visible content, and contains the row's
text rather than the body's first line.

Rendering goes through `tests/integration/` as well: the layout is a template,
templates are what four gates once missed a fatal in, and `TemplateLoader` asks
the theme first.

## Not in scope

Rewriting the shipped bodies to use the tokens. That is a content change with a
migration shape, and it belongs in its own commit where its diff is the whole of
what is being reviewed.
