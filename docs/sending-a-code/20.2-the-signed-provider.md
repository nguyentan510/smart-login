# 20.2 — The signed envelope becomes a provider, not a preset

Spec: [`../sending-a-code.md`](../sending-a-code.md) D2.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** The SMS channel can talk to a signed endpoint, so that 20.1 can delete
the routing table without taking a capability with it.

Runs **before** 20.1 for that reason: the destination has to exist before the
thing currently holding it is removed.

## What changed in the plan, and why

D2's first draft made this a `GatewayPresets` entry. Reading `EnvelopeSigner`
first — rather than after — showed that a preset is a *body template plus
credentials*, and the signed envelope is a *wire format built in code*. Four
controls do not survive the translation; they are tabulated in the revised D2.

The correction is recorded there rather than restated here.

## Files

- `includes/class-gateway-presets.php` — the `signed` entry, and `envelope()`
- `includes/OTP/Transports/class-webhook-transport.php` — branch on the format
- `includes/class-field-registry.php` — `sms.signed_url`, `sms.signed_secret`
- `tests/delivery/run-routing-tests.php` — rule 18

## Steps

1. **Rule 18 first, landed red.** A provider declaring a signed envelope must
   produce a body that `EnvelopeSigner` verifies, and administrator headers must
   not be able to replace the signature. Asserted on the request the transport
   builds, not on the source.
2. `GatewayPresets`: add `signed`, and `envelope( string $slug ): string`
   returning `'signed'` or `''`. `resolve()` writes no body, method, content type
   or success condition for a signed provider — there is nothing to template.
3. `FieldRegistry`: `sms.signed_url` (`type url`, `sanitize https_url`) and
   `sms.signed_secret` (`type secret`), both on `delivery-sms`, both shown only
   when the signed provider is chosen.
4. `WebhookTransport::dispatch()`: when the provider declares a signed envelope,
   build the payload, hand it to `EnvelopeSigner::sign()`, and apply
   administrator headers add-only. Otherwise, today's path unchanged.

## Acceptance

- Rule 18 fails before step 4 and passes after, with both outputs recorded
- The signature verifies against the **transmitted** bytes, asserted by
  recomputing the HMAC over the body the transport actually produced — not over a
  re-encoding of the payload
- A configured `X-Smart-Login-Signature` header does not reach the request
- `sms.signed_url` refuses `http://` at save and keeps the previous value, the
  same behaviour `automation.url` has today
- Rules 14–17 are **unchanged** by this sub-phase. 20.2 adds a capability; it
  deletes nothing, so Rule 15's intersection is still four and Rule 14 still
  fails. Anything else means scope leaked
- Every other suite at its previous count — Delivery routing 50/3, Admin screens
  139/5

## Not in scope

Deleting `AutomationTransport`, `automation.*`, or the routing table. 20.2 makes
the new home habitable; 20.3 moves the furniture and 20.1 demolishes the old one.
A site's configuration is still read from `automation.*` when this sub-phase
lands, and nothing about its behaviour changes.

Renaming `WebhookTransport`. It is internal and never a label, so D4 does not
reach it, and this project has been bitten by renames five times.

### What the plan got wrong

**D2 itself, and it was caught by reading rather than by a test.** The first
draft made this a `GatewayPresets` entry and claimed "nothing is lost". Opening
`EnvelopeSigner` before writing any code found four controls that do not survive
a template — the table is now in the revised D2. The correction cost an hour and
would have cost a security control.

Worth naming precisely, because the mistake is repeatable: both mechanisms end up
as "POST JSON to a URL an administrator supplies", so they looked like the same
kind of thing. They are not. **A preset is data; a wire format is code.** The
tell was that one of them has a rule about *when its bytes may be serialised*,
which no data structure can carry.

### What was found along the way

**`show_if` collided with an invariant that already existed.** Hiding the two new
fields broke *"tab draws every field it claims"* and *"every field is drawn by
exactly the tab that claims it"* — the gate that exists because a field claimed by
a tab and drawn by nothing is a real bug class.

The first instinct was to add `'conditional' => true`, the existing exemption
marker. That would have been wrong: `conditional` means "this row may legitimately
draw nothing" and is unverifiable by construction, while `show_if` says *which
setting decides* and is therefore checkable. So neither gate exempts these fields.
They are skipped while their condition is false and **required** while it is true,
and a third assertion sets each condition deliberately and demands the field
appear. A field that is never drawn under any value of its own condition still
fails.

The net is two more passing assertions than before the sub-phase, not two fewer.

**The two markers now coexist and mean different things.** `sms.credentials` keeps
`conditional` because its input count varies with the gateway, which `show_if`
cannot express. That is a genuine distinction rather than drift, but it is one
concept with two spellings on the same screen, and 20.5 should look at it.

**The pot is a required-suite dependency.** Adding three translatable strings
turned `Identity fitness` red — `languages/smart-login.pot is current` is a rule,
not a courtesy. `php bin/build-pot.php` is now part of finishing any sub-phase
that adds a string, and the earlier decision to defer it was only safe because
that phase added none.

### Not done, deliberately

`AutomationTransport`, `automation.*` and the routing table are all untouched and
still working. A site configured for automation delivery today behaves exactly as
it did before this commit; nothing has been migrated and nothing has been removed.
20.3 moves the data, 20.1 removes the table.
