# 20.6 — A channel that says what it is doing

Spec: [`../sending-a-code.md`](../sending-a-code.md) D5.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Rule 17 goes green, and with it the requirement
[`delivery-routing.md`](../delivery-routing.md) D2 wrote down two phases before
anybody hit it:

> *The screen must say which role is active rather than leaving the administrator
> to infer it, because "configured but not delivering" and "broken" look
> identical otherwise.*

## Rule 17's fixture is stale, and that has to be said out loud

20.0 wrote the rule against the tree as it stood, so its "not serving" case is:

```php
'sms.enabled'          => 1,
'sms.url'              => 'https://gateway.example/send',
'delivery.route_phone' => 'automation',
```

20.1 deleted that third setting. `Settings::update()` drops paths the registry
does not declare, so the fixture now describes a channel that **is** serving, and
asserting `idle` against it would be asserting something false.

The property does not change; its only remaining spelling does. After 20.1 a
channel is idle when it is **enabled but its identity channel is not** — a site
on `identity.mode = email_only` with the SMS gateway configured and switched on
is paying for a gateway nothing can reach, and no screen says so.

Rewriting a fixture to match a world the phase deliberately created is the third
time this has come up (20.1's sibling-nav, 20.4's tab hierarchy), so it is worth
naming the test: **the rule may be repointed, the property may not be weakened.**
Concretely, 20.6's version is *stronger* — it asserts both states, where 20.0's
asserted only one.

## The status

| State | When | Says |
| --- | --- | --- |
| `serving` | channel enabled **and** its identity channel enabled | which identity it carries |
| `idle` | channel enabled, identity channel not | enabled, but nothing can reach it, and where to change that |
| `off` | channel not enabled | nothing is delivered this way |

Rendered from `before_section()`, beside `automation_role()`, which already does
exactly this job for the event tab and is the precedent being followed rather
than a second mechanism.

## Files

- `includes/Admin/Screens/class-settings-screen.php`
- `tests/identity/run-admin-tests.php` — Rule 17's fixture

## Steps

1. Repoint Rule 17: `identity.mode = email_only` with SMS enabled and configured
   must render `idle`; `identity.mode = both` must render `serving`. Both states,
   not one.
2. `channel_status()` on the `sms` and `email` sections, emitting
   `data-sl-channel-status="serving|idle|off"`.

### What the plan got wrong

Nothing in the brief, which had already caught the stale fixture. What it did not
predict was the **integration gate**, which failed on four counts the moment
20.6's suites went green:

```text
reason=a stored route is ignored by the default router
reason=the signature does not match the body as WP_Http would have sent it
reason=the envelope is not the shape docs/delivery-routing.md D3 describes
reason=a delivery screen claims fields it does not draw:
       delivery-sms:sms.signed_url, delivery-sms:sms.signed_secret
```

All four were Phase 20 doing what it set out to do, against a gate written for
Phase 10 — and **not one of them appeared in `run-all.php`**, because the
integration gate is a separate runner that needs a real database. Five
sub-phases had gone green without it once.

That is the finding, and it is a process one: `php tests/run-all.php` is not the
gate this project's own working agreement describes. *"Anything involving a real
WordPress — schema, headers, hooks, template rendering — goes through
`tests/integration/`."* Four gates once missed a fatal that only a real WordPress
could show; this time four checks sat red for five sub-phases for the same
reason.

### What was found along the way

**The gate's own summary line had gone stale, and it was hard-coded.** It printed
`transports=sms,email,automation` — a transport 20.1 deleted — because the line
was a literal array somebody typed once. It now asks the router. A report that
states a fact nobody derives is a comment that will eventually be wrong, and this
one was wrong in the one place an operator would read it to confirm the opposite.

**The gate's field-coverage check needed `show_if` too**, exactly as the pure
suite did in 20.2 — the second copy of a rule needing the same amendment, which
is the cost the duplication buys and it was paid knowingly.

### Not done, deliberately

`Readiness` keeps the mail-path warning. It states more carefully than a status
line could that there is no honest synchronous probe for "can this site send
mail", and a second opinion on the same screen would be a fifth thing to disagree.
