# 20.4 — The bus gets its own tab

Spec: [`../sending-a-code.md`](../sending-a-code.md) D3.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** The event stream stops being filed under "Gửi mã", because it does not
send anything to anybody who is signing in.

## Why the slug changes too

`delivery-automation` is wrong twice over now. The `delivery-` prefix asserts the
association 20.1 removed, and it is visible — it is the `?tab=` value in the
address bar, which is the one part of a settings screen an administrator copies
into a support message.

The rename is contained: `FieldRegistry::tabs()`, `tab_parents()`, seven field
`tab` keys, and two test files. Nothing in `templates/`, `assets/` or `Readiness`
hardcodes it — Readiness builds its links from a variable. Greped before claiming
that, because this project has been bitten by a rename five times.

Old links are aliased rather than left to the Overview fallback. The fallback is a
soft landing, not a 404, but "my bookmark now shows a different screen" is a
support message somebody has to answer, and the alias is three lines.

## What "off by default" already means

D3 says the tab is off by default, and it already is, by construction: no events
are subscribed on a fresh install and no endpoint is configured, so the bus does
nothing. **No new `automation.enabled` flag.** A toggle whose only state is
implied by two other settings is a fourth way to have the screen disagree with
itself, which is the class of defect this phase exists to remove.

## Files

- `includes/class-field-registry.php` — `tabs()`, `tab_parents()`, seven fields
- `includes/Admin/class-settings-page.php` — the alias
- `tests/identity/run-admin-tests.php`, `tests/integration/run-delivery-gate.php`

## Steps

1. `integrations => 'Thông báo & Tích hợp'` in `tabs()`, placed after the delivery
   family so the strip reads in the order an administrator sets the plugin up.
2. Drop the `tab_parents()` entry — it is a top-level tab now.
3. Repoint the seven `automation.*` fields.
4. Alias `delivery-automation` to the new slug in `SettingsPage::render()`.
5. Update both suites.

## Acceptance

- The tab renders, names itself for the save, and draws every field it claims —
  the existing gate covers all three, and it must stay green through the move
- `SettingsPage::nav()` draws `integrations` in the top strip and no longer draws
  it inside the delivery family
- A request for `?tab=delivery-automation` lands on the integrations screen, not
  on Overview
- Rules 14, 15, 18, 19 unchanged. Rule 16 is **still red**: it fails on the
  section label and on `sms.preset`, which are 20.5's, and the tab label is only
  one of its three assertions
- Every other suite at its previous count — Delivery routing 72/0, Admin screens
  141/5

## Not in scope

The section heading, still `Automation / Webhook`, and every other label. That is
20.5, and this sub-phase deliberately leaves the screen reading inconsistently for
one commit rather than smuggling a vocabulary pass into a move.

The status line, which is 20.6.

## Outcome

Landed.

```text
Admin screens    141 passed, 5 failed  →  unchanged
Delivery routing  72 passed, 0 failed  →  unchanged
Every other required suite PASS.
phpcs 21 errors / 20 warnings / 16 files  →  21 / 17 / 15
```

Rule 16 now fails on two things instead of three: the tab label is fixed, and
what is left is `section:automation` and `sms.preset`, both of which are 20.5's.

### What the plan got wrong

**A test fixture was a consumer of the tab hierarchy, and the brief did not count
it.** *"A child tab must also link back to the rest of its family"* used
`delivery-automation` as its example child. Repointing the slug turned that
fixture into a **top-level** tab, so the rule went on passing right up until it
didn't — and had it been written slightly differently it would have kept passing
while proving the opposite of its own sentence.

Repointed to `delivery-sms`, which is still a child, with the reason written at
the fixture. This is the second time in the phase that a rule, rather than code,
turned out to be the thing depending on the structure being changed.

### What was found along the way

**The standards baseline moved down, and that needs saying out loud.** Renaming
the tab changed a string's length, which broke array alignment across
`class-field-registry.php` and added thirteen warnings. `phpcbf` fixed those —
and, in the same pass, three pre-existing alignment warnings that had been in the
documented baseline since Phase 19.

So the number is now **21 / 17 / 15**, not 21 / 20 / 16, and the file left the
report entirely. That is an improvement rather than drift, but an unexplained
baseline change reads exactly like drift, which is why it is written here and in
the tracker rather than left for the next person to re-derive.

**No `automation.enabled` flag was added,** and the brief's reasoning held up: a
fresh install subscribes to no events and configures no endpoint, so the bus is
already inert. A toggle whose only state is implied by two other settings would
have been a fourth way for the screen to disagree with itself.

### Not done, deliberately

The section still reads `Automation / Webhook` under a tab called *Thông báo &
Tích hợp*. The screen is inconsistent for exactly one commit, which is the price
of not smuggling a vocabulary pass into a move. 20.5 is next.
