# 20.3 — The migration that refuses to be silent

Spec: [`../sending-a-code.md`](../sending-a-code.md) D6.
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** A site delivering OTP through the automation endpoint today keeps
delivering it after 20.1 deletes the routing table — or is told, by name, what it
lost and where to fix it.

This is the load-bearing sub-phase of the phase. 10.1 shipped with defaults that
reproduced existing behaviour byte for byte, so no site changed on upgrade; this
phase deletes two settings that sites have deliberately set, and there is no
no-migration path.

## What has to move, and what cannot

20.2 established the destination. The intersection Rule 15 measured is exactly
`AutomationEndpoint`'s four settings, and only two of them are the OTP path's:

| Stored today | Becomes | Why |
| --- | --- | --- |
| `automation.url` | `sms.signed_url` | same value, and both are `https_url` |
| `automation.secret` | `sms.signed_secret` | both `secret`; travels through `SecretBox`, never through the option array |
| `delivery.route_phone = automation` | `sms.preset = signed`, `sms.enabled = 1` | the routing decision becomes a provider choice |
| `automation.timeout`, `automation.headers` | **stay** | the bus's own; the signed provider uses `sms.timeout` and `sms.headers` |
| `delivery.route_email = automation` | **nothing** | there is no email-side equivalent, and inventing one is a decision this hook must not make |

The last row is the whole reason this brief exists. An email channel routed at
the automation endpoint has no destination in the new model — D5 of
`delivery-routing.md` deferred an external email sender and this phase does not
add one. The site loses a capability, and the only honest thing an upgrade hook
can do is say so.

## Files

- `includes/class-installer.php` — the migration, beside `forget_unshipped_providers()`
- `includes/Admin/class-settings-page.php` — render and dismiss the notice
- `omniwp.php` — `OMNIWP_DB_VERSION` to `3`
- `tests/delivery/run-routing-tests.php` — rule 19

`maybe_upgrade()` already says in writing that the next migration goes here, in
the same commit as the change that needs it. This is that one, again.

## Steps

1. **Rule 19 first, landed red.** Three shapes: a phone-routed install arrives
   fully configured on the signed provider; an email-routed install produces a
   recorded notice naming `delivery.route_email`; a site that never used
   automation is untouched, including its `sms.preset`.
2. `Installer::migrate_automation_delivery()`. Reads the stored option directly
   rather than through `Settings::get()`, because after 20.1 the registry no
   longer declares `delivery.route_*` and a hydrated read would return nothing.
3. The secret moves through `Settings::store_secret()` / `read_secret()`, never
   through the option array — `absorb_secret_fields()` prunes plaintext, so
   copying the raw block would copy an absence.
4. Notices accumulate in one option, rendered dismissible. Dismissing deletes the
   option; nothing else clears it, because a notice that disappears on its own is
   a notice nobody read.

## Acceptance

- Rule 19 fails before step 2 and passes after, with both outputs recorded
- Migrating twice is the same as migrating once — the version guard is not the
  only thing standing between this and a double run, and the rule asserts a
  second call changes nothing
- A site that never used automation keeps `sms.preset` exactly as it was. A
  migration that rewrites a setting it was not asked about is the failure mode
  `Installer::cleanup()`'s flat retention keys already cost this project once
- The secret reads back through `Settings::read_secret( 'sms.signed_secret' )`
  after migration, asserted by reading it, not by asserting a write happened
- `automation.url` and `automation.secret` are **left in place**, not deleted.
  20.4 decides the bus's own fate; a migration that erases the source before the
  destination has been used in anger is unrecoverable
- Rules 14–17 unchanged. Rule 18 unchanged. Every other suite at its previous
  count — Delivery routing 57/3, Admin screens 141/5

## Not in scope

Deleting `delivery.route_*` or `AutomationTransport`. 20.1 does that, and it runs
after this so that the migration still has something to read.

Migrating anything for the **bus** role. Its settings are staying where they are;
20.4 moves the tab, not the data.

The three delivery failures are Rules 14 and 15, still red on purpose until 20.1.

### What the plan got wrong

**The brief listed three shapes and there were four.** The one it missed is the
one the reporting install is actually in: `delivery.route_phone = automation`
with `automation.url` **empty**.

The first implementation migrated it anyway, and the result was worse than doing
nothing. It set `sms.preset = signed` against an endpoint that does not exist,
and on the way past it overwrote `sms.url` and `sms.preset` — which on the
reporting install hold a configured n8n gateway. A site that was misconfigured in
a recoverable way would have come out of the upgrade misconfigured in a way that
had also eaten its previous settings.

Caught by adding the case to the rule and watching it fail:

```text
FAIL  an empty endpoint does not overwrite the configured gateway
      expected: 'generic'   actual: 'signed'
FAIL  a route pointing at nothing is reported instead
```

Now it migrates nothing and reports `delivery.route_phone` by name, because a
site routed at an endpoint it never configured has not been delivering — and
silence is how it stays that way.

This is the second time in this phase that the specific install in the original
report has been the case the plan forgot. It is worth carrying forward as a
habit: **the reported configuration is a test case, not an anecdote.**

### What was found along the way

**Idempotence is not the version guard's job.** The guard in `maybe_upgrade()`
only covers one call path; a support script, a second activation or a restored
database can all reach the migration directly. Asserting that a second call
changes nothing cost three lines and is the difference between a migration and a
hazard.

**Secrets cannot be migrated by copying the option array.**
`absorb_secret_fields()` prunes plaintext out of it, so a raw block copy would
have faithfully copied an absence and produced a signed provider with an empty
key — which fails closed, but silently and for the wrong reason. Both sides go
through `store_secret()` / `read_secret()`, and the rule asserts the key **reads
back** rather than asserting a write happened.

**Nothing is deleted.** `automation.url` and `automation.secret` stay. 20.4
decides the bus role, and a migration that erases its source before the
destination has been used in anger is unrecoverable.

### Not done, deliberately

`delivery.route_*` and `AutomationTransport` are untouched — 20.1 removes them,
and it runs after this so the migration still has something to read.
