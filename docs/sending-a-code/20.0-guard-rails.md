# 20.0 — Guard rails, landed red

Spec: [`../sending-a-code.md`](../sending-a-code.md).
Status: [`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Four rules that fail against the tree as it stands today, so that the
six sub-phases after this one have something that can tell them they worked.

The defect this phase answers was found by a person reading a screen, not by a
suite — the fourth time in two phases. These rules cannot replace that. What they
can do is stop the *structure* from drifting back, which is the part a rule is
good at.

## Files

- `tests/delivery/run-routing-tests.php` — rules 14 and 15
- `tests/identity/run-admin-tests.php` — rules 16 and 17

Both suites are `required` today, so all four land red in a required suite. That
is deliberate and it is the phase's own gate: nothing in 20.1–20.6 may be called
done while any of them is still red.

## Steps

### Rule 14 — no setting names a transport

The routing table is what 20.1 deletes, and the way it comes back is somebody
adding `delivery.route_something` for the next channel. Asserted against
`FieldRegistry::all()` rather than against a file, so a field added anywhere
fails it:

```
no field's key matches /^delivery\.route_/
```

Red today: two fields match.

Paired with the positive form, because a rule that only forbids leaves the
replacement unspecified — `TransportRouter::transport_for()` must answer from
`channel_for()` alone, asserted behaviourally by registering a transport map and
checking that no setting can change the answer.

### Rule 15 — the bus cannot reach the OTP path

Today's coupling is real: six of seven `automation.*` fields serve both roles, so
configuring an event stream configures a transport. After 20.2 the two must share
no setting at all.

```
the keys under automation.* and the keys the OTP path reads are disjoint
```

Asserted by resolving the `signed` preset's credential list and the bus's field
list and intersecting them. Red today — the intersection is six.

The existing Rule 6 ("a failing bus never reaches the OTP path") stays. It tests
the runtime coupling; this one tests the configuration coupling, and 10.4 shipped
the first while the second was still there.

### Rule 16 — one label per concept

The D4 table, enforced. Walks every label and help string in `FieldRegistry` and
every tab label, and fails when a concept's forbidden spellings appear:

| Concept | Owned by | May not appear in |
| --- | --- | --- |
| `Nhà cung cấp đăng nhập` | `providers` tab | any `sms.*` or `automation.*` label |
| `Nhà cung cấp SMS` | `sms.*` | the providers tab |
| `Webhook` | the event tab | any `sms.*` label |

Red today: the `sms.preset` label offers "Webhook JSON", and the providers tab
and the SMS tab both say "Nhà cung cấp".

This rule is a string check and will annoy somebody in six months. That is
accepted, and the reason is written into the rule: the defect it guards took a
working install down to zero delivered codes, and the diagnosis cost a full
session with database access.

### Rule 17 — an enabled channel that serves nothing says so

D5, and D2 before it. Renders the delivery screens through the existing admin
harness and asserts that a channel enabled with nothing routed to it produces a
visible status line naming that fact.

Red today, and it is red in the most useful way available: the exact
configuration from the report — `sms.enabled = 1`, a real `sms.url`, and routing
pointed elsewhere — renders a screen that says nothing is wrong.

## Acceptance

- All four rules fail before 20.1 and pass after 20.6, with both outputs recorded
- Rule 14 fails if `delivery.route_phone` is re-added under any name matching the
  pattern, verified by adding one
- Rule 15's intersection is asserted empty, not merely small
- Rule 17 is not satisfied by the string existing in a template: it renders the
  screen with the reported configuration and reads the output
- Every other suite at its previous count. Delivery routing is 49/0/0 as of
  `bd01471`; Admin screens and the rest per the tracker

## Not in scope

Deleting anything. 20.0 adds rules and touches no production file — the point is
that they are demonstrated failing against the tree that shipped the defect. The
first deletion is 20.2's, and it happens after the preset can hold a site's
configuration.

Rewording labels. Rule 16 declares the target vocabulary; 20.5 is what satisfies
it.

### What the plan got wrong

**The spec undercounted its own headline finding.** Finding 1 claimed "provider"
named three things and listed `TransportInterface` as one of them. Rule 16 asked
the registry instead and found three *settings* sharing the exact label **Nhà
cung cấp** — the identity section, `sms.preset`, and
`security.captcha_provider`, which the spec had not noticed at all. The
`TransportInterface` sense is real but never reaches a screen. Finding 1 has been
rewritten around what was measured; the captcha field is now in 20.5's scope and
was not before.

This is the third time in two phases that reading the code has corrected a
document written about the code, which is the argument CLAUDE.md opens with.

### What was found along the way

**Rule 15's intersection is exactly `AutomationEndpoint`'s four settings** —
`url`, `secret`, `timeout`, `headers`. Not a coincidence and worth stating: the
shared configuration surface *is* the shared class, so 20.2 removing
`AutomationTransport` from the OTP path removes the intersection in one move,
with no per-setting migration on this axis. Only `automation.url` and
`automation.secret` need to travel to the preset in 20.3; the other two are the
bus's own and stay.

**Rule 15 needed a companion or it was worthless.** The two paths are declared as
file lists, because `TransportRouter` does not expose its map and 20.0 changes no
production file — so the rule can be satisfied by deleting a line. The companion
check walks `includes/OTP/Transports/` for `implements TransportInterface` and
requires every hit to appear in the declared OTP list. It passes today, which is
correct: all three transports are declared.

**Rule 14's positive half is the one that will matter.** Forbidding
`delivery.route_*` in the registry is easy to satisfy and easy to work around
with a filter or a constant. The behavioural half — no stored value may move
`transport_for()`'s answer — is what actually pins the decision to the channel.

### Not done, and deliberately

No production file was touched. The first deletion is 20.2's.
