# 16.1 — One value, one place

Spec: [`../sign-in-card.md`](../sign-in-card.md) — decisions 1, 2, 3, 4 and 6 are
normative there and are not restated here. Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** The card stops printing one address twice, and stops offering to
unlink a value it can only replace.

## Files

- `templates/partials/linked-identities.php`
- `templates/partials/account/contact.php`
- `tests/identity/run-template-tests.php` — the fixture rule 5 asks for

## Steps

1. **Filter on `federated`.** The list renders only records where the flag is
   true. The flag has been in the payload since Phase 6
   (`class-identity-link-service.php:67`) and no template has read it.
   `linked()` itself is unchanged — see decision 2 for why the filter is
   presentational.
2. **Return early when nothing federated is left**, so an account with only a
   phone and an email renders no empty subtitle. The partial already returns on
   an empty list (`:22-24`); the condition moves after the filter.
3. **Drop the unlink control for self-asserted channels.** Falls out of step 1
   for this card. Stated as its own step because
   `partials/linked-identities.php` also renders on `profile-summary`, and the
   two must not diverge — one partial, one answer.
4. **The contact row carries the identity state.** Where the account holds an
   identity record for that channel, its row says the value is a way in, and
   carries `Chính` when the record is primary. The contact partial is already
   handed `$ow_providers` (`contact.php:145`), so the data is in scope without a
   new query.
5. **Remove the subtitle** with the second grid, per decision 1.

### The subtitle could not wait for 16.3, and the brief had it backwards

Step 5 said to remove the subtitle "with the second grid", which is 16.3's grid
merge. That ordering is wrong in a way the brief could not see and the render
makes obvious: once the list holds federated identities only, a heading reading
*Cách đăng nhập của bạn* sits over a list containing none of the ways this
account signs in. Leaving it for one sub-phase would ship a heading that is
actively false rather than merely redundant.

It says *Tài khoản đã liên kết* now. Whether a heading survives the grid merge
is 16.3's to decide.

### The verified badge was claiming something the directory had not said

The badge rendered on `'' !== $ow_row['value']`, and `ow_phone` is a
`user_meta` read (`AccountForm::args_for()`, the `contact` branch). So a number
seeded into meta by any path displayed **đã xác thực** on the strength of a meta
key. `has_contact_identity()` carries a long docblock about exactly this — the
directory is the only thing that knows — and the row three lines away was not
asking it.

The condition is the identity record now, and the copy says what the record
means: **dùng để đăng nhập**. Where no record exists, no claim is made.

### A JS line that had never been reachable

`omniwp.js:564` unhides `[data-sl-contact-verified]` after a successful
verification. The badge was only in the DOM when the row already had a value —
so for the one case that line exists for, an account adding its first phone or
email, there was nothing to unhide. The badge is now always rendered and
`hidden` when it does not apply.

That needed `.sl-badge[hidden] { display: none }`: `.sl-badge` sets a `display`,
and an author `display` beats the user agent's `[hidden]` rule. Without it the
attribute is decorative. **`assets/css/omniwp.css` therefore joined this
sub-phase's file list**, which the brief did not have — along with
`.sl-badge--primary`, since a new badge variant with no colour is an unstyled
pill.
