# 16.2 — A provider row a person can read

Spec: [`../sign-in-card.md`](../sign-in-card.md) — decision 5, including the
staleness trade, is normative there. Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** `Google 1171••••••` becomes a row that names the account it links to.

## Files

- `includes/Auth/class-identity-link-service.php` — one computed key
- `templates/partials/linked-identities.php`
- `tests/identity/run-sign-in-card-tests.php` — the resolution order
- `tests/identity/run-template-tests.php` — a fixture carrying meta

## Steps

1. **`linked()` gains `display`**, resolved in the service from the record's
   meta: `name`, else the masked `email`, else the linked date. Never `sub`,
   never an unmasked address.
2. **The service is where it is resolved**, not the template. A partial that
   reaches into `meta_json` would be a second place to know that a provider
   claim is stored there, and `profile-summary` renders the same partial.
3. **The masked subject stays in the payload** under `masked`. Nothing on this
   card renders it after this sub-phase, but the REST route and any integrator
   reading the array keep the value they have.
4. **State the staleness where the code is**, per decision 5 — a link-time
   snapshot, and why that is the right fact for this row.

## Acceptance

- All three resolution levels asserted **separately**, against a record built
  for each. 11.1's fallback order shipped as a no-op because one assertion that
  "something resolves" was taken for three that resolve differently
- A record with empty meta — every identity linked before this key was stored —
  falls to the date and renders a row, not an empty cell
- A row never contains the raw subject: asserted on the rendered markup, not on
  the payload
- Every other suite at its previous count

## Outcome

Rule 6 green, four assertions, `10 passed, 2 failed, 0 pending` — the two
failures are 16.3's. Every other suite at its previous count.

**Proven able to fail rather than assumed to work.** Rule 6 arrives with the
feature it guards, which 11.0 recorded as the one shape of rule that cannot
catch its own feature breaking. So the service and the partial were stashed and
the rule re-run against the tree without them:

```text
Rule 6 — a provider row names the account, not the number (16.2)
  FAIL     a stored display name wins
           expected: 'Cai Hoa'
           actual:   NULL
  FAIL     no name falls to the provider address, masked
  FAIL     no meta at all falls to the linked date
  FAIL     the rendered row carries no masked subject
```

All three levels are asserted against a record built for each, not one
assertion that something resolves — 11.1 shipped a fallback chain as a no-op
with its tests passing for exactly that reason. Exercised through `linked()` and
the stub `$wpdb`, so the real read path runs rather than a mock of it, which is
what Phase 6 added that stub for.

The masked-subject assertion is made on the **rendered markup**, not the
payload: `masked` stays in the array for the REST route and for integrators, and
it is the row that had to stop printing it.

### The unreachable branch is named as unreachable

`verified_at` is `NOT NULL` in the schema, so the date level always resolves and
the `'—'` fallback below it cannot be reached. It is there because a row with an
empty value cell reads as a rendering fault rather than as missing data, and the
comment says which of the two it is. A silent `return ''` would have been the
other kind of decision.

### The catalogue moved by one

689 → 690 strings: `Đã liên kết %s` is new and nothing was retired here.

## Not in scope

Avatars. `ProviderIdentity` carries `picture` and it is stored, but a remote
image on a profile page is a third-party request on every render, and this row
has no problem that an avatar solves.

Backfilling meta for identities linked before the claims were stored. There is
nothing to backfill from — the claims were never held anywhere else.
