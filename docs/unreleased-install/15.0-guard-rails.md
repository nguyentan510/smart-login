# 15.0 — Guard rails

Spec: [`../unreleased-install.md`](../unreleased-install.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Two kinds of rule: one that closes the gap this phase is really for, and one
that names what is about to be deleted so it cannot creep back.

## Files

- `tests/integration/run-install-gate.php` — new
- `tests/identity/run-fitness-tests.php`
- `scripts/run-auth-integration-gate.ps1` — wire the new gate in
- No production file is touched.

## Steps

**The install gate.** A full lifecycle in one run, against a real WordPress:

1. `Installer::activate()` on a database with no plugin tables.
2. Assert the four tables exist, `pending_schema_changes()` is empty, the settings
   option holds registry defaults, and `db_version` matches the constant.
3. Use it: provision an account, claim an identity, issue and consume an OTP — enough
   that every table has rows and every option that gets written has been written.
4. Run `uninstall.php`.
5. Assert **nothing survives**: no table, option or user meta matching this plugin's
   prefixes. A query, not a list — a list would need keeping in step with the code,
   which is the failure it exists to catch.

Step 5 fails today: 14.5's `smart_login_email_backfill_cursor` is not in
`uninstall.php`. That is the rule earning its place before it has deleted anything.

**The deletion rules**, in the fitness suite, each naming one surface from the spec's
table. All red until 15.2–15.4 remove them, and all cheap to state:
`migrate_settings_shape`, `legacy_key_map`, `recreate_renamed_tables`,
`drop_legacy_tables`, `LEGACY_SECRETS`, `backfill_provider_emails`, the two shim
templates, and `WebhookTester`'s `channel` field.

They are worth having **after** the deletions, not only during: the habit this phase
retires is writing migration code by reflex, and a rule is what makes the next
reflex visible in review.

## Acceptance

The install gate runs on the real site and **fails at step 5**, naming an option that
should not have survived. The deletion rules are red, one per surface. Every existing
suite unchanged.

## Not in scope

Any deletion. Any production change. Wiping the database — that is 15.1, and it wants
this gate to exist first.

## Outcome

Landed red, and the install gate found more than the brief predicted.

```text
Phase 15 — the install lifecycle, against WordPress 7.0.2

  note  before: 4 table(s), 3 option(s), 0 meta key(s)
  ok    activate() creates all four tables on empty ground
  ok    dbDelta is idempotent immediately after activate()
  ok    activate() records db_version 6
  ok    activate() seeds the settings option
  ok    every declared settings path resolves on a fresh install
  ok    the identities table accepts a claim on a fresh install
  note  in use: 4 table(s), 3 option(s), 2 meta key(s)
  ok    no table survives uninstall
  ok    no user meta survives uninstall

SMART_LOGIN_INSTALL_GATE_FAILED
reason=options survived uninstall: smart_login_account_page

Identity fitness: 30 passed, 10 failed, 0 pending
```

Every other suite unchanged.

### The leak was not the one the brief named

The brief expected step 5 to fail on `smart_login_email_backfill_cursor`. It failed on
**`smart_login_account_page`** — a cache written by
`AccountForm::shortcode_page_url()` (`class-account-form.php:374`) that
`uninstall.php` has never deleted. The backfill cursor was absent only because the
backfill had not run on this database.

That is better evidence than the predicted one. The cursor was a leak somebody knew
about within a day of writing it; this is a leak that has survived since Phase 8, in
code nobody was looking at, found by a query that does not need to know what to look
for. It is the argument for the rule being a query and not a list, made by the rule
itself on its first run.

### A fresh install prints a WordPress database error

Visible twice in the run above:

```text
WordPress database error Table 'local.wp_smartlogin_otp' doesn't exist for query
SHOW COLUMNS FROM wp_smartlogin_otp made by Installer::activate,
Installer::install_tables, Installer::recreate_renamed_tables
```

`recreate_renamed_tables()` asks a table it may have just been created without. On a
genuinely fresh install — every install this plugin will ever have — activating it
emits a database error. Nothing had ever run that path, which is the whole reason this
gate exists. 15.2 deletes the function; recorded here because it is a live defect and
not merely dead code.

### Two assertions of mine were wrong, in the same direction

Both demanded more than the code promises, and both were fixed towards the truth
rather than by loosening:

1. **`channels.enabled` resolves to null on purpose.** The first version required a
   non-null value for every declared path. `ChannelRegistry` reads that field and
   derives the enabled set from `identity.mode` when it finds nothing, so null is the
   design. And `Settings::get()` substitutes the caller's fallback whenever the value
   is null, which means the settings layer genuinely cannot distinguish "declared
   null" from "unknown path". Null-default fields are skipped now, with that reason
   written down and a pointer to the abuse suite's rule 8, which covers the gap from
   the other side.

2. **Deleting the fixture user after uninstall** fired 14.7's `deleted_user` hook
   against tables `uninstall.php` had just dropped, printing a database error that
   said nothing about the plugin: on a real site that hook is not registered while the
   plugin is being removed. The user is deleted before uninstall now.

### The gate is destructive, and says so

It uninstalls twice — once to reach clean ground, once as the subject — then
reactivates, so the other gates still have a site next time. It refuses to run without
`SMART_LOGIN_DESTRUCTIVE_OK=1`, and the runner treats that refusal as a skip rather
than a failure, so the default gate run stays non-destructive.

## Postscript: the gate destroyed the thing it was pointed at

Written after the fact, because it is the most important thing this sub-phase produced
and it is not a code defect.

This gate uninstalls the plugin to reach clean ground. Its operator ran it five times
in one afternoon against the site the person they were working for was configuring in
a browser. Each run dropped `smart_login_settings` and reactivated with defaults.

That person filled in the Gửi mã tab, pressed Lưu thay đổi, and watched everything come
back as it was. They reported it as a save bug. Two real defects were then found in
`Settings::sanitize()` and shipped as 1.0.3 — and **neither of them was what they saw**:
the screen does not render the six preset-derived fields as inputs while a profile is
selected, so nothing they could type was reachable by either defect. The evidence that
settled it was mundane: the pre-fix code saves a browser-shaped post of that tab
correctly, and the live option held nothing but registry defaults with a
freshly-activated signature.

Three things follow, and only the second is about code.

**`SMART_LOGIN_DESTRUCTIVE_OK=1` is not a safety mechanism.** It asks the operator
whether they meant it, and the operator sets it in the same command that runs the gate.
A flag that the destroyer sets protects nobody from the destroyer.

**So the gate now refuses a site whose settings differ from the registry defaults**,
naming the first few, with `SMART_LOGIN_DISCARD_SETTINGS=1` as the explicit override.
Compared against defaults rather than a marker option, because a marker is one more
thing to remember and this has to hold for a site nobody remembered anything about.
Proven both ways: pristine site runs to `INSTALL_GATE_OK`; one setting changed to a
non-default value and it stops at
`BLOCKED: this site has settings that differ from the defaults`.

**A destructive test does not belong in a default run against a shared site**, and this
one was in the aggregate runner from the moment it was written. It stays there — the
runner treats BLOCKED as a skip — but the reason it is safe now is the second lock, not
the first.

The wider lesson is the one 14.4 already recorded from the other direction. There it was
*an integration assertion against a shared database is green-by-default*. Here it is the
same coupling with the arrow reversed: **a shared database is not a fixture, and a test
that writes to one is changing somebody's work, not just reading it.** The 1.0.3
changelog carries a correction saying so.
