# 15.1 — A fresh database, and proof the install path works

Spec: [`../unreleased-install.md`](../unreleased-install.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Wipe the Local database of everything this plugin owns, then let 15.0's gate
run the whole lifecycle against genuinely empty ground.

## Why the wipe is the point, not a chore

The site has accumulated: identity rows from gate runs that never cleaned up, two real
accounts that 14.5 backfilled, a `db_version` option that two copies of the plugin
disagree about, and orphan `sl_gate_*` users going back several phases. Every
assertion made against it inherits that. 14.4's doors were vacuous for exactly this
reason, and the lesson recorded there — *an integration assertion against a shared
database is green-by-default unless it names the thing it just made* — has a second
half: a database nobody resets accumulates until the assertions stop meaning anything.

## Files

- No repository file changes. This sub-phase is an operation and its evidence.

## Steps

1. Read what is there before removing it, and write the counts into the Outcome. A
   deletion nobody looked at first is not reversible and not reviewable.
2. Drop the four tables, delete every option matching this plugin's prefixes, delete
   every user meta key `uninstall.php` names, and remove the `sl_gate_*` /
   `sl_legacy_*` / `sl_synth_*` fixture users left by earlier gates.
3. Leave the two genuine accounts alone: `hoacai.vi@gmail.com` and
   `erubik.tool@gmail.com` are real users of the site. Their identity rows go with
   the tables; the accounts themselves are not this phase's to delete.
4. `git pull` the installed copy so the site and the working tree stop disagreeing
   about `SMART_LOGIN_DB_VERSION`.
5. Run the install gate. It must reach step 5 and fail on the backfill cursor, which
   is 15.0's evidence and this sub-phase's confirmation that the ground is clean.

## Acceptance

Before-and-after counts pasted into the Outcome. The install gate reaches its final
assertion — reaching it at all is what a clean database buys.

## Not in scope

Deleting the two real accounts. Touching WooCommerce data.

---

## Outcome

Done, and smaller than the brief expected — because 15.0's gate had already wiped
what the plugin owns while proving it could.

```text
before                                    after
  identities            0 rows              0 rows
  identity_history      0 rows              0 rows
  options               3                   3
  usermeta (smartlogin) 0                   0
  users                 22                  10
```

The four tables were already empty: the install gate uninstalls to reach clean ground,
so running it in 15.0 did the wipe this sub-phase was written to do. What was left was
the thing the gate does **not** own — twelve `sl_gate_*` fixture users accumulated
across several phases of gate runs whose cleanup predates the one added in 14.4.

### What was removed, and what was deliberately not

Twelve fixture users, each re-read and confirmed to carry the `sl_gate_` prefix before
deletion; the script refuses the whole batch if any id disagrees with the database
rather than skipping the odd one out.

**Left alone:** `hoacai.vi@gmail.com`, `erubik.tool@gmail.com` and
`tranphongthuy973@gmail.com` are real accounts. So are the six manual test accounts
(`tester.smartlogin@example.test`, `sl_81_…`, `sl_83_…` and the two `@phone.invalid`
ones) — they were created by hand, not by a gate, and deleting somebody's test data
because it looks like clutter is not this phase's call.

Their identity rows went with the tables, which is the same reset every other row got.

### The installed copy caught up

`git pull` in `wp-content/plugins/smart-login` — the site and the working tree had
disagreed about `SMART_LOGIN_DB_VERSION` since 14.5, so the option flipped between 5
and 6 depending on which copy ran last. One constant now.
