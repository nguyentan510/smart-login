# 15.2 — Delete the migrations

Spec: [`../unreleased-install.md`](../unreleased-install.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Remove every path that exists to upgrade an install, and reset the version.

## Files

- `includes/class-installer.php`
- `omniwp.php` — `OMNIWP_DB_VERSION` → `1`
- `uninstall.php` — the `external_identities` drop, and the missing cursor option
- `tests/integration/run-wordpress-gate.php`, `tests/integration/run-abuse-gate.php`

## Steps

1. Delete `migrate_settings_shape()`, `legacy_key_map()`, `recreate_renamed_tables()`,
   `drop_legacy_tables()` and `backfill_provider_emails()` with its cursor constants.

2. `maybe_upgrade()` **stays**, reduced to: version differs → `install_tables()` →
   write the version. The mechanism is how the next schema change arrives; only its
   contents were about the past.

3. `OMNIWP_DB_VERSION` → `1`. There is nothing to upgrade from, and a version
   that starts at 6 tells a story about installs that do not exist.

4. `uninstall.php` loses the `external_identities` drop and gains whatever 15.0's step
   5 says is missing.

5. The 14.5 assertions in the WordPress gate go with the code they assert. **Not
   silently**: their Outcome recorded a real defect, and the tracker row is what keeps
   that finding after the code is gone.

## Acceptance

15.0's deletion rules for these five surfaces go green. The install gate passes end to
end, including step 5. `pending_schema_changes()` stays empty on a fresh activate at
version 1. Every other suite unchanged.

## Not in scope

`install_tables()` and `schema()`. Nothing about creating tables is legacy.

## Outcome

Green on the real site, and a fresh install stopped printing a database error.

`class-installer.php`: 411 → 254 lines. The four remaining fitness failures are
15.3's, and are meant to be red here.

### The database error is gone

15.0 recorded that a fresh activate emitted
`Table 'local.wp_OmniWP_otp' doesn't exist for query SHOW COLUMNS`, from
`recreate_renamed_tables()`. It no longer appears in the run above. That defect was
live on every install this plugin would ever have had, and it was removed by deleting
the code rather than by guarding it — which is the better fix available exactly once,
while there is nothing to migrate.

### `maybe_upgrade()` kept its shape and lost its contents

It is four lines now: version differs → `install_tables()` → write the version. The
docblock says why it survives and what would put code back into it — a migration, in
the same commit as the change that needs it, with the fitness rule edited alongside.
Deliberately and in writing, which is the whole difference from the habit retired here.

### A second pinned version number, two phases running

Resetting to `1` turned a Phase 2 fitness rule red: *"OMNIWP_DB_VERSION is at
least 3"*, a floor written when Phase 2 needed a bump for `maybe_upgrade()` to run at
all. Yesterday it was the abuse gate's literal `5`. Both rules were pinned to a number
that was current when they were written, and both went red on a change they have no
opinion about.

It asserts the constant is a positive integer now — which is what it is for, since
`maybe_upgrade()` compares against it on every load and a missing constant would make
every request think an upgrade is due.

### One stale allowlist, removed with the code that earned it

Phase 2's rule forbidding `external_identities` allowlisted two files and said in
writing that both should go *"once no installation can still be carrying the table"*.
This is that moment, so the rule is absolute now rather than absolute-except-here. An
allowlist that outlives its reason is the thing that teaches people to add entries.

### 14.5's gate assertions went with the code, and left a note

Their Outcome recorded a real defect — the cursor that outlived its migration — so the
block was replaced by a comment pointing at where the finding lives, rather than
deleted silently. The code is gone; the reason it mattered is not.
