# 15.3 — Delete the legacy reads

Spec: [`../unreleased-install.md`](../unreleased-install.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Remove the fallbacks that read values from where they used to live.

## Files

- `includes/class-settings.php` — `LEGACY_SECRETS` and its two private helpers
- `includes/Admin/class-webhook-tester.php` — the `channel` field
- `templates/form-login.php`, `templates/form-register.php`
- `tests/identity/run-template-tests.php` — the shim rules

## Steps

1. `Settings::LEGACY_SECRETS`, `legacy_secret()`, `forget_legacy_secret()`, and the
   two call sites that consult them. 10.2's Outcome records why they existed: a
   secret that did not fall back **came back on the next read**. On a wiped database
   there is no earlier location to fall back to.

2. `WebhookTester` stops accepting `channel` alongside `transport`. 10.2 kept it
   because the admin JS posted the old name; the JS ships `transport` now — verified
   by grep before deleting, not assumed.

3. Delete both shim templates. `form-register.php` has zero references;
   `form-login.php` is named only by the rule asserting nothing loads it. The
   template suite's two shim rules go with them, and the README note about
   overriding `form-auth.php` stays true without them.

## Acceptance

15.0's remaining deletion rules go green. Template suite drops the two shim rules and
moves by exactly that. Admin suite unchanged — the tester still works, it just accepts
one field name.

## Not in scope

`SecretBox`. Storing secrets is current; only reading them from the old place is not.

---

## Outcome

Green, and the brief was wrong about the one thing it said was verified.

```text
Identity fitness: 36 → 40 passed, 0 failed, 0 pending

SMART_LOGIN_AUTH_INTEGRATION_OK · GOOGLE_STAGING_SMOKE_OK
PROVIDER_LINKING_OK · ZALO_STAGING_SMOKE_OK
ABUSE_GATE_OK · DELIVERY_GATE_OK · INSTALL_GATE_OK
```

### "The JS posts `transport` now — verified by grep, not assumed" was false

It posts `channel`. `assets/js/admin.js:90` still appended the old name, and the screen
still rendered `data-channel`. Deleting the server's acceptance would have quietly
broken the **Gửi thử** button — it would have fallen back to `sms` and tested the wrong
transport, which is the kind of break nobody notices because the button still does
something.

The brief asserted the check had been done. It had not; this is a sentence written
from memory in a document whose whole subject is that documentation is not evidence.
Doing the grep is what turned a one-line deletion into a rename.

So: the attribute, the JS and the server read were renamed together, and
`SMART_LOGIN_VERSION` went to `1.0.2` — assets are enqueued with it, so a cached
`admin.js` cannot post a field nothing reads. That is the one place in this phase where
a version bump is the mechanism rather than the story.

### 10.2's fixture went with the fallback it tested

The delivery suite wrote a secret the way pre-10.2 code did and asserted the reader
still found it, then asserted clearing reached that copy too — because erasing only the
new location resurrected the secret on the next read. Both were real defects when
found. Both describe a database that no longer exists.

Replaced rather than deleted: what survives is the half still true of every install — a
secret written through the path-keyed store reads back, and clearing empties it. The
finding lives on in 10.2's Outcome; only the fixture for a location nothing has went.

`Captcha::SECRET_OPTION` went too. Its docblock said it was *"kept because
Settings::LEGACY_SECRETS points at it"*, so when that went, the reason went with it.

### The shims are gone and the rule that named them changed shape

`form-login.php` and `form-register.php` are deleted. The template suite's two rules
became one that matters after the deletion: nothing may reference a template that no
longer exists, because that is a fatal on the page that names it — which is exactly
the Postscript defect this project already survived once.

### One unreproduced failure, recorded rather than explained away

The first full-script run after these changes failed in the WordPress gate:

```text
SMART_LOGIN_AUTH_INTEGRATION_FAILED
reason=the first unlink failed: Mật khẩu không đúng.
```

It has not recurred: the gate passes alone, and the full script has since run green
twice end to end. A hypothesis was tested and **rejected** — that
`wp_generate_password( 24, true, true )` can emit a character that does not survive
`wp_insert_user`; 40 create-and-check cycles against the real site produced zero
mismatches.

What is left is a correlation and no mechanism: that run was the first to execute
against settings at their fresh defaults, immediately after the install gate
reactivated the plugin. Two runs are not a comparison, and neither are three — this is
written down so that if it returns, the second sighting starts from a note rather than
from surprise.
