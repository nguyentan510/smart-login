# 15.4 — Documentation is not allowed to describe things that do not exist

Spec: [`../unreleased-install.md`](../unreleased-install.md). Status:
[`../refactor-plan.md`](../refactor-plan.md).

**Goal.** Correct three false statements the plugin currently ships, and turn the class
of defect into rules. Then promote a suite the project's own agreement says should
already have been promoted.

## Why these three and not a general documentation review

Each was measured, not noticed in passing:

| Claim | Reality |
| --- | --- |
| `README.md:242` — *`form-login.php` and `form-register.php` are still in `templates/`* | 15.3 deleted them, yesterday |
| `readme.txt` — `Stable tag: 1.0.1` | `OMNIWP_VERSION` is `1.0.2` since 15.3, and there was no changelog entry for it |
| `create_verified_user()` — *"README documents these meta keys as a public contract"* | README names `OmniWP_ward_code` and nothing else of that family. Found in 14.2, not fixed there |

CLAUDE.md opens its research section with *"Documentation is not evidence. Twice now
this project has found the README asserting a control that does not exist."* This is
the third time, and the first where the plugin's own change created the falsehood.
Reading more carefully is not a fix.

## Files

- `README.md`, `readme.txt`, `includes/Identity/class-user-manager.php`
- `tests/identity/run-fitness-tests.php` — four rules
- `bin/build-pot.php` — a `--check` mode
- `tests/run-all.php` — one suite's kind

## Steps

1. **Three rules on documentation**, landed red: no `<name>.php` the README names may be
   missing from the tree; `readme.txt`'s Stable tag must equal `OMNIWP_VERSION`;
   the shipped version must have a changelog entry.

2. **A rule on the string catalogue.** It went stale by 76 strings across five phases
   and surfaced only because 14.3 regenerated it for an unrelated reason. `--check`
   compares without writing, and the fitness suite shells out to it rather than
   reimplementing the extractor — a second extractor would drift from the one that
   writes the file, and the rule would end up checking itself.

3. **Correct the three claims.**

4. **Promote `Mail templates` to `required`.** It has been 56 passed / 0 failed / 0
   pending since 13.3 and is still `spec`. The working agreement says a spec suite is
   promoted the moment it goes green.

## Acceptance

All four rules red before, green after. `Mail templates` blocks. Every other suite
unchanged, and the full gate green.

## Not in scope

phpcs. A general documentation review — the three corrections here are the ones that
could be pointed at.

### The catalogue rule was wrong twice, in the same direction

Both versions would have produced a rule nobody could live with, and both were caught
by running it rather than by reading it:

1. **Comparing whole files** compared `POT-Creation-Date`. A catalogue was stale one
   second after it was written.
2. **Comparing everything below the header** compared the `#:` source references. Any
   edit that shifted a line above a `__()` call demanded a regeneration — and it
   announced itself as `committed 689 msgid(s), tree would produce 689`, identical
   counts and still "stale", which is the tell.

It compares the sorted set of msgid literals now, because what a translator can
actually be missing is a string. Proven able to fail by adding one:
`first missing: "Chuỗi thử 15.4"`.

A rule that fires on noise is a rule somebody switches off, so getting this wrong
twice was worth the time it cost.

### The README rule pushed the documentation towards being shorter

The first correction replaced the false sentence with a true historical one — *"before
1.0.2 there were two files… they have been deleted"* — and the rule went red again,
because it names files that do not exist. Correctly, by its own logic.

The sentence went instead. README describes how to use the plugin today; a note about
two files nobody can override belongs in the changelog, which is where it now is. The
rule pushed towards less documentation debt rather than towards being gamed.

**Its limits are written into it rather than glossed:** WordPress core filenames are
skipped, and a name that resolves in *any* searched directory passes — so it cannot
catch a README claiming a file lives in `templates/` when it only lives in
`templates/woocommerce/`. `form-login.php` is exactly that case, and it is why line 242
had to be corrected by hand. What the rule catches is a name that exists nowhere.

### Four phases against its own rule

`Mail templates` landed `spec` in 11.0 with red rules, went green in 13.3, and stayed
`spec` through 13.3, 14 and 15. Nothing was wrong with the suite; the promotion step
was simply never taken. A green suite that cannot block can only hide the next
regression, which is the reason the agreement has the rule at all.

`Coding standards` is now the only `spec` suite, and its deferral is written into
`phpcs.xml` where it is configured.
